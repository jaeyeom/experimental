# factory

## When to use it

Use factory when the user asks to pick or start the next work item, inspect readiness, or file a follow-up. Do not use factory merely because a task exists.

## Learn the installed CLI

Run `factory --help`, then `factory <command> --help`. The installed binary wins over this text.

## Config

`--config PATH` overrides the search and is the only file tried. A missing file is an error. Otherwise factory reads `./factory.toml`, then `<git-root>/factory.toml` when inside a git repository, then `$XDG_CONFIG_HOME/factory/factory.toml` (`~/.config/factory/factory.toml` when `XDG_CONFIG_HOME` is unset). An empty `XDG_CONFIG_HOME` is an error. Run `factory init` inside a git repository to scaffold `<git-root>/factory.toml` (or `--global` to append to `$XDG_CONFIG_HOME/factory/factory.toml`, `--kind jira` for Jira, `--dry-run` to preview, `--force` to overwrite), or copy `factory.example.toml` or a file in `examples/`.

## Credentials

A Jira source sets exactly one of `token_file` or `token_env`. That file or variable is read when a command contacts Jira, not when config loads. `next`, `show`, `doctor`, `gate`, `logs`, and `priorities` work against the mirror without the token when `[sync] max_age` is `0` or omitted. On a Jira source, `sync` also fetches each blocker that is not in the mirror by key (`external_blocker_lookups`, default 100) and stores it. Readiness, `show`, and `doctor` use that record: a Done outside blocker does not block, and an open, missing, or unfetched one does, with a reason that says which. A positive `max_age` makes `next`, `show`, `doctor`, and `priorities` sync a source older than that age, and that sync needs the token. `--no-sync` skips the refresh. A failed refresh still answers from the mirror. `priorities --apply` contacts the source. `sync` fails and names the source and the field.

## Read-only commands

`next`, `show`, `doctor`, `gate`, `logs`, `stats`, `priorities` (without `--apply`), `close` (without `--apply`), `version`, and `skill` only read, except that a positive `[sync] max_age` refreshes a stale source before `next`, `show`, `doctor`, `priorities`, and `close`. `--no-sync` skips that refresh. An item with any open child in the mirror (GitHub sub-issues or Jira sub-tasks) is not ready: `has open child <id>` (sorted by id), and becomes ready once all children are done. An item with a not-before date after today (Jira `defer_field`, GitHub `defer_label_prefix` labels) is not ready: `deferred until YYYY-MM-DD`. `next` prints a `N deferred (earliest ...)` line, and `next --deferred` lists them. `stats` never syncs and makes no network calls. It reports throughput, backlog, per-epic progress, and flow from the local store. Use `stats --json` when you need to parse it. The text report adds a bar column to the throughput, backlog, and epics tables (`--bar-width N`, 0 for none) and a burndown when the output is at least 40 columns (one line with a legend; `--burndown-pace` adds a dotted reference line to zero; the projection line shows its formula and assumes no new items), uses local time (`--utc` for UTC), and colors only a terminal without `NO_COLOR` (`--color`); `--json` stays UTC. `next`, `stats`, `doctor`, `priorities`, `close`, `logs`, `sync`, `gate`, `tick`, and `run` scope to the source whose `cwd` holds the current directory (deepest when nested) and print `factory: showing KEY (current directory); --all for every source` (or `scoping to` for `sync`, `gate`, `tick`, and `run`) on stderr; pass `--all` for every source or `--source KEY` for one, and `--all` with `--source` is a usage error. Inside an unconfigured git repository (without `--config`, `--all`, or `--source`) they exit 1 naming the repo root; outside every git repository they cover every source. `sync` refreshes the local mirror only. Every `sync` also drops mirrored items that no longer match the source query. When that membership check fails or comes back empty, `sync` warns on stderr, removes nothing, and still exits 0. The calling pane in `HERDR_PANE_ID` is skipped, so that pane does not by itself block `start`. Another working pane still refuses when its `cwd` or `foreground_cwd` is a configured source `cwd` or a subdirectory of one, and the refusal lists every counted working tab. An agent whose paths are both outside every configured checkout does not count. `--log-level=debug` names each working agent ignored for that reason. When a counted tab still contains the calling pane, that line ends with `(this pane)`. `gate.ignore_panes` (pane ids) and `gate.ignore_tabs` (tab labels) skip more. When `gate.base_branch` is set, `gate` also refuses a checkout that is not on that branch, or that has commits not on `origin/<base_branch>` when `require` is `clean_against_base`. A path in `gate.hold_files`, or `~/.local/state/factory/hold` when that list is empty, refuses `gate`, `start`, and `tick` while the file exists. A `gate.hold_tabs` label does the same while a tab with that label exists and is not `done`. The refusal names the hold. A stale hold, one older than `gate.hold_ttl`, is still a refusal.

`gate`, `start`, and `tick` also read the agentbus workdir lease of the checkout unless `[lease] gate` is `off`. A lease that is not `free`, and not held by the agent `start` is starting, refuses, and the reason names the holder, the deadline, and the queue length. Under the default `auto`, a lease that cannot be read, such as a missing `agentbus`, keeps the old checks and adds a `note:` line to `gate` output. Under `required` it refuses. A remote lane's lease is not read.

With `[lease] mode = "prompt"` or `"prompt+check"`, the start prompt begins with the lease rule, or has it where `start_prompt` says `{{lease_rule}}`. A worker started that way runs `agentbus lease claim --for <claim_for> --why '<id> <title>'` before it changes the checkout, ends its turn when queued, and runs `agentbus lease release` when the tree is clean and pushed; `restore = true` enables `agentbus lease restore` alongside claim. With `"prompt+check"`, an applied `start` also prints one `lease: ...` line and records the lease in the run log. It never refuses the start. The default `mode` is `"off"`. `[claim]` (and per-source `[source.claim]`) configures start safety checks (`require_leaf`, `require_unblocked`, `source_containment`), ownership (`assign`, `ownership_rule`: `"unassigned_or_me"`, `"unassigned"`, `"any"`), in-progress marking (`mark_in_progress`, `in_progress_rule`: `"block"`, `"allow"`, `create_label`, plus per-source `status`, `transition`, `label`), and claim comments (`comment`, `nickname`, `comment_template`); legacy `claim_*`/`assignee_ok` keys stay compatible unless both forms are set on the same source, and `mark_in_progress = false` allows empty `claim_status`/`claim_label`. `[worker]` configures `spawner` (`"agentbus"` default, `"subagent"`, or `"herdr"`), `agent` (such as `"agy"`, `"claude"`, `"codex"`, or `"grok"`), `agent_args`, `max_workers` (default `1`, orthogonal to `spawner` and `max_in_flight`), and `worktree` (`false` default: isolates each worker in its own git worktree, inspected by `verify`, and removed by `settle` or `release` only when clean so dirty worktrees stay on disk with a warning); `[output]` configures `mode` (`"pr"` default or `"merge"` to rebase onto `base` and push linear history; `verify`, `settle`, `tick`, `show`, and `doctor` inspect `origin/<base>` for a matching linear commit instead of pull requests), each overridable per source and per lane. `start` sets `FACTORY_OUTPUT_MODE=<pr|merge>` alongside `FACTORY_ITEM_SOURCE` and reports `output_mode` and `keep_worker` in `--json`: under `"pr"` (`keep_worker: true`), workers stay alive for review feedback until settled; under `"merge"` (`keep_worker: false`), local tab workers run `factory settle <id>` on completion, remote-lane tab workers close their tab (`herdr tab close "$HERDR_TAB_ID"`) after reporting back, and subagent workers return immediately so the coordinator settles and discards them.

An applied start retries `herdr agent start` while the new pane is busy (`agent_busy_timeout`), and when it still fails it closes the tab, releases the claim, and prints the re-run command. It then waits for the agent to be idle (`agent_ready_timeout`, `agent_ready_settle`) before the prompt. A stalled prompt gets one recovery: Enter when the text sits in the input box, or one resend when it is not there; otherwise the claim is `failed` and the tab is left for inspection. Under `[defaults] wake_before_prompt = "auto"` (the default), an applied `start` or `tick` runs `agentbus wake --if-hibernated --wait` on the pane before it types the prompt. A missing `agentbus` skips the wake. A failed wake fails the start and sends no prompt. `"off"` never wakes.

## Starting an agent

`start`, `tick`, and `run` are dry-run unless `--apply` is set or config `dry_run` is false. The default prints a plan (including the claim comment preview when `claim.comment = true`) and does not claim or start an agent. `start` scopes to the current git repository's configured source by default (refusing unconfigured git repositories unless `--source` or `--config` is passed), enforces `FACTORY_ITEM_SOURCE` containment when `claim.source_containment = true`, and resolves `<number>`, `#<number>`, and GitHub/Jira issue URLs against the scoped source. When the gate refuses, a dry run still prints that plan, marked `blocked  yes`, without `--force`. `--force` skips queue checks and the start gate, naming each skipped check, while still refusing closed/done items (never bypassed), non-leaf items (`claim.require_leaf`), blocked items (`claim.require_unblocked`), foreign ownership (`claim.ownership_rule`), already in-progress items (`claim.in_progress_rule`, including foreign `claim.nickname` claim comments), and an existing tab. Pass `--force-taking-ownership` to take over foreign assignees, in-progress state, or foreign-nickname claims (replacing prior assignees with `@me` / `Me`). On `--apply`, `start` posts `Claimed by <agent> [on <nickname>] at <timestamp>.` matching `claims.claimed_at` unless `claim.comment = false` or re-running on this machine's own claim. `--caller NAME` sets `{caller}` in that plan. Otherwise factory uses `[defaults] caller`, then the pane id read from `HERDR_PANE_ID` at startup. An unknown caller expands to empty and is logged. Do not pass `--apply` unless the user asked to start an agent. `[defaults] agent_args` is appended after `--` on `herdr agent start`. The first `[[agent_rule]]` whose `labels` match the item replaces that list. `start --agent-arg` (repeatable) or `start --model` replaces both for that start. The plan and `next --explain` name which one was used. In `start_prompt`, `{report_back}` is `agentbus send <caller's agentbus name or handle> "<message>"` (it reaches another machine), else `herdr agent prompt {caller} "<message>"`; `{caller_bus}` is that name or handle. A remote-lane start whose prompt uses only `{caller}` warns. With `[worker] spawner = "subagent"`, `factory start --apply` claims the item, skips `herdr` tab/agent spawning, records `spawner = "subagent"` on the claim, and prints the worker brief (`id`, `source`, `output`, `FACTORY_ITEM_SOURCE`, `FACTORY_OUTPUT_MODE`, `cwd`, `agent`, `agent_args`, and rendered `start_prompt`); pass `--json` on `factory start` for a single JSON outcome object containing those fields plus `output_mode` and `keep_worker` so the coordinator can launch its subagent tool directly and know whether to retain it for review (`"pr"`) or settle and discard it on completion (`"merge"`), and `doctor` and `settle` handle `subagent` claims without expecting a `herdr` tab.

With `[[lane]]` config, `start` picks the first lane routed to the item that passes its gate and runs every herdr call for the worker as `herdr --machine <machine>` in that lane's checkout. The plan has a `lane` line. `start --machine LANE` picks one lane and is refused when the item's labels route it elsewhere. An item whose labels match two lanes is a config error. `gate` then prints one line per lane after the global result, such as `linux: OK workers 1/2 (running), active 3` or `mac: unreachable (skipped): ...`. With lanes, `tick` and `run` check the global gate once and then start at most one item per lane, in `[lanes] default` order then config order, printing one `lane NAME: ...` or `started ... (lane NAME)` line per lane; an unreachable lane is skipped with a note. `settle` closes each tab on the lane recorded on its claim. `max_workers` counts running workers (an open tab on the lane machine, the lane lease, or a start under way), not handed-off claims; the optional lane `max_active` caps every open claim on the lane.

`tick --enqueue` prints one `start-item` job per ready item as JSON lines on stdout (summary on stderr) and starts nothing; it still syncs and settles like `tick`. `owner ID [--json]` prints the machine and tab of the item's latest claim from the local store, or `null` when it was never claimed.

## Writes

`adopt` records a claim for an existing tab or pull request, including the head branch when the open pull request has one. It does not create a tab, start an agent, or send a prompt, and it ignores `dry_run`. `claim-pr ID URL` records that pull request on an active claim. The second argument is `owner/repo#N` or a pull request URL. It copies the head branch when `gh` lists that open pull request. It does not start an agent, and it ignores `dry_run`. `settle` finishes merged work and ignores `dry_run`. It does not start an agent. Under `output.mode = "pr"`, it closes the item's tab when the agent is not working and leaves a working tab open. Under `output.mode = "merge"`, tab closing runs last after database, tracker, worktree, and stdout updates: self-settle from inside the worker's tab (`HERDR_PANE_ID`) closes that tab even while `working`, and external `settle` or `tick` waits briefly for a `working` agent to become `idle` or `done` before closing the tab. `show` searches merged pull requests by the item key in the title, with no merged-after date, when no open pull request matches, and keeps titles that match `pr_title_pattern`. On a remote lane, `verify` runs its checkout checks on that machine through the lane's `exec` prefix (such as `["ssh", "mac1"]`) and prints `checked on MACHINE:CHECKOUT`; an unreachable machine fails, and a remote lane without `exec` is an error. `verify ID` checks a worker report. Under `output.mode = "pr"` (the default), it requires `pr_template` and records each pull request it sees on the active claim: the pull request must be a draft with no labels and no reviewers, every section of `pr_template` must have content in the body (ignoring lines that are only HTML comments; sections are ATX `#`–`######` or setext `===`/`---` headings matched by text), and the merge-base of `HEAD` and `origin/<base>` must be an ancestor of that ref and no older than 7 days. Under `output.mode = "merge"` (recorded on the claim or configured on the source/lane), `verify` skips the pull request and `pr_template` checks and instead checks that `origin/<base>` contains a linear commit (no merge commits) referencing the item. In both modes, `verify` does not fetch, the checkout (or recorded worktree) must be clean, and `git stash list` must have the same number of entries `start` recorded. `orphan_ignore` and `orphan_ignore_labels` silence `has no parent` for those ids and labels. Other doctor checks still report that item. `link`, `unlink`, `file`, `release`, `priorities --apply`, and `close --apply` write to the source and ignore `dry_run`. `close` without `--apply` only detects eligible open parents (or evaluates named IDs) from the local cache (`--json` supported). `close [ID...] --apply` closes eligible parents, optionally posting `--comment TEXT` or `--comment-file PATH` (mutually exclusive; warns on literal `\n` in `--comment`), refreshes each mirror row, and records the run. `close --apply` has no `--force` flag and strictly refuses with zero writes if any item is missing from the local cache, already done, has no known children, has any open children, or is outside `FACTORY_ITEM_SOURCE`. After `release`, the item's mirror row is reread at once, and an item that no longer matches the source query leaves the mirror, so `next` stops listing it. `priorities` without `--apply` only prints. `next`, `tick`, `start`, and `run` do not change priority. `file` prints only the new id. Pass a multi-line body with `--body-file`, not `--body "a\nb"`: a shell keeps `\n` as two characters, and `file` warns on stderr when the body has a literal `\n` and no newline. A Jira body is Markdown and is converted to Jira formatting. A Jira `file` takes its project from `--project KEY`, then `create_project`, then the parent's key, then the first `--blocks` or `--blocked-by` key; pass `--project` when none applies. `file` files only into the item's own source: `start` sets `FACTORY_ITEM_SOURCE=<kind:name>` in each worker's tab, and any other `--source` is refused with no override. A source not configured on this machine is refused too: report back instead. Without `FACTORY_ITEM_SOURCE`, `--source` is required. A public GitHub repository that is the item's own source gets a warning. On a remote lane, never run `file`, `link`, or `release`; report follow-ups back to your coordinator. Get the user's explicit approval before running `file`, `link`, `unlink`, `release`, or `priorities --apply`, the same way `--apply` needs approval. `hold` and `release-hold` write the local hold file and ignore `dry_run`. `hold` prints the path it created. `release-hold` removes that file. Do not run `hold` or `release-hold` unless the user asked to hold or release the checkout.

## Exit codes

`factory start` exits 3 when the gate refuses. `factory start` exits 4 when it fails after claiming and keeps the claim, or 5 when it closes its tab and releases the claim it made. `factory gate` prints `OK: <n> in flight (max <limit>)` when it passes. `factory gate` exits 0 even when it prints reasons. `tick` and `run` also exit 0 on a gate refusal. `1` is a tool error. `2` is a usage error.
