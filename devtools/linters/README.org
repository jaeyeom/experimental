#+TITLE: Linters
#+DATE: 2026-11-15

* Overview

This directory holds seven linters. ~org-lint~ runs Emacs's built-in
Org-mode linter from the command line, so ~.org~ files can be checked in
CI. ~agents-md-size~ enforces per-file and cascading ancestor byte size
limits on ~AGENTS.md~ files with ratchetable baselines.
~migration-immutability~ fails when a change edits a database migration
the base branch already has. ~py-sibling-import~ flags a Python file
that imports a module from its own package bare, which loads a second
copy of that module. ~py-module-import~ flags ~from pkg.mod import Name~
from first-party code and asks for ~from pkg import mod~. The two Go
linters catch patterns ~go vet~ doesn't: interface assertions that guard
nothing, and package-level variables that should be constants or that
run code at init time.

~make lint~ runs ~pkgvar~, ~py-sibling-import~ and ~py-module-import~.
[[file:../devcheck/README.org][devcheck]] runs
~unnecessary-interface-assertion-linter~ when it falls back to Go tools.
Emacs packages for ~org-lint~ come from
[[file:../setup-dev/README.org][setup-dev]].

Go 1.26 or later for the Go tools. ~py-sibling-import~ and
~py-module-import~ need Python 3.11 or later and git.

* Tools

** org-lint

Runs Emacs's built-in ~org-lint~ on one or more ~.org~ files. Pass every
file in one command. One Emacs process checks all of them.

Emacs starts in batch mode, adds the current Emacs version's ELPA
directory to ~load-path~ (both =~/.emacs.d= and =~/.config/emacs=), and
loads the ~ob-*~ and ~*-mode~ packages it can. A package that fails to
load is skipped. That is what lets source blocks be checked.

*** Install

Emacs with Org mode. [[file:../setup-dev/README.org][setup-dev]] installs
those packages with ~./ensure.sh org-lint~ from
~devtools/setup-dev/ansible/~.

#+BEGIN_SRC bash
go install github.com/jaeyeom/experimental/devtools/linters/cmd/org-lint@latest
#+END_SRC

*** Usage

#+BEGIN_SRC bash
org-lint README.org
org-lint file1.org file2.org
DEBUG=1 org-lint README.org
org-lint --skip-if-no-emacs *.org
#+END_SRC

*** Output

~org-lint sample.org~ prints one line per finding. ~sample.org~ had a
link to a missing file, two headings with the same custom id, and
~#+ATTR_ORG: :align nowhere~ on a paragraph:

#+BEGIN_EXAMPLE
sample.org:3: (low) Link to non-existent local file "missing.org"
sample.org:7: (nil) Duplicate CUSTOM_ID property "same"
sample.org:12: (nil) Duplicate CUSTOM_ID property "same"
sample.org:15: (high) "nowhere" not a supported value for #+ATTR_ORG keyword attribute ":align".
#+END_EXAMPLE

~(low)~ is a weaker check, ~(high)~ is a stronger one, and ~(nil)~ means
the check set no trust level. The level is only a hint from Emacs.

*** Parity harness and checker survey

~make org-lint-parity~ is for a Go reimplementation of this linter. It
needs Emacs, so ~make check~, ~make test~ and ~bazel test //...~ never
run it. It builds ~org-lint~ and runs ~cmd/org-lint-parity~ with it. Both
linters are started as ~CMD files...~ with ~ORG_LINT_NORMALIZED=1~. Each
must print ~file:line: checker-name: message~. Set ~GO_LINT~ to compare
the Go linter with Emacs. The harness then lists missed findings (Emacs
only), extra findings (Go only) and line differences, for every tracked
~.org~ file and every fixture:

#+BEGIN_SRC bash
make org-lint-parity                      # survey, and check goldens against Emacs
go build -o .tmp/org-lint-go ./devtools/orglint/cmd/org-lint-go
make org-lint-parity GO_LINT=.tmp/org-lint-go
make org-lint-parity-update               # regenerate the fixture goldens
#+END_SRC

The Go linter lives in ~devtools/orglint~ (a small org parser plus the
checker list) with the command ~org-lint-go~. ~make check~ runs it over every ~.org~ file in the
checkout as one Bazel test, ~//devtools/orglint:go_default_test~, which
takes well under a second and never starts Emacs. Checkers for syntax no
tracked file uses (footnotes, ~id:~ links, citations, macros,
~#+INCLUDE~, ~#+OPTIONS~, planning lines) are not ported; the Emacs
~org-lint~ stays as the reference for ~make org-lint-parity~.

Fixtures are in ~testdata/orglint/~. Each ~NAME.orgtest~ triggers the
checker ~NAME~ (some also trigger a second one). The extension keeps
the deliberately broken files out of the pre-commit org-lint hook;
~org-lint~ switches such buffers to Org mode. ~NAME.golden~ holds
Emacs's findings, generated by ~make org-lint-parity-update~. Go tests
compare against these goldens, so they never start Emacs.

Survey, with Org 9.7.11 on all 65 tracked ~.org~ files: no checker fires.
The repository is clean, so the checkers are scoped by the syntax the
files use: ~file:~, ~*heading~ and ~#custom-id~ links, ~bash~, ~json~,
~toml~ and other src blocks, ~example~ blocks, ~CUSTOM_ID~ property
drawers, ~#+TITLE~, ~#+CAPTION~, ~#+NAME~, ~#+TODO~, ~#+TAGS~, ~TODO~
keywords and inactive timestamps. No file uses footnotes, ~id:~ links,
citations, macros, ~#+INCLUDE~, ~#+OPTIONS~ or planning lines.

Every checker with a fixture is in scope, grouped by the checker issue
that implements it:

- Links and references: ~link-to-local-file~, ~invalid-fuzzy-link~,
  ~invalid-custom-id-link~, ~invalid-coderef-link~, ~duplicate-custom-id~,
  ~duplicate-name~, ~duplicate-target~, ~percent-encoding-link-escape~,
  ~file-application~, ~trailing-bracket-after-link~,
  ~unclosed-brackets-in-link-description~, ~duplicate-footnote-definition~,
  ~undefined-footnote-reference~, ~unreferenced-footnote-definition~,
  ~extraneous-element-in-footnote-section~.
- Structure and syntax: ~incomplete-drawer~, ~misplaced-heading~,
  ~invalid-block~, ~invalid-keyword-syntax~,
  ~orphaned-affiliated-keywords~, ~combining-keywords-with-affiliated~,
  ~obsolete-affiliated-keywords~, ~item-number~, ~spurious-colons~,
  ~obsolete-properties-drawer~, ~special-property-in-properties-drawer~,
  ~invalid-id-property~, ~invalid-effort-property~, ~planning-inactive~,
  ~timestamp-syntax~, ~misplaced-planning-info~,
  ~mismatched-planning-repeaters~, ~indented-diary-sexp~, ~quote-section~,
  ~invalid-image-alignment~, ~LaTeX-$~.
- Src blocks and options: ~missing-language-in-src-block~,
  ~suspicious-language-in-src-block~, ~empty-header-argument~,
  ~wrong-header-value~, ~wrong-header-argument~, ~named-result~,
  ~invalid-babel-call-block~, ~missing-backend-in-export-block~,
  ~deprecated-header-syntax~, ~deprecated-export-blocks~,
  ~invalid-macro-argument-and-template~, ~misspelled-export-option~,
  ~unknown-options-item~, ~wrong-include-link-parameter~,
  ~obsolete-include-markup~, ~non-existent-setupfile-parameter~,
  ~deprecated-category-setup~.

The Go linter implements these src block and option checkers:
~missing-language-in-src-block~, ~suspicious-language-in-src-block~,
~empty-header-argument~, ~wrong-header-argument~, ~wrong-header-value~,
~deprecated-header-syntax~, ~invalid-babel-call-block~, ~named-result~
(only an empty ~#+RESULTS:~), ~missing-backend-in-export-block~,
~deprecated-export-blocks~ and ~unknown-options-item~. The tables of
header arguments, their values, OPTIONS items and languages in
~devtools/orglint/srcblocks.go~ were read from Org 9.7.11
(~org-babel-common-header-args-w-values~, ~org-export-options-alist~ and
the options of the export backends). They leave out language specific
header arguments and languages that Emacs knows only through a major
mode. Extend them when a file in this repository needs more.

Out of scope, without fixtures: the citation checkers
(~incomplete-citation~, ~invalid-cite-export-declaration~,
~missing-print-bibliography~, ~non-existent-bibliography~) and
~beamer-frame~, because no file uses them. ~invalid-id-link~ also has no
fixture. It rebuilds the ~org-id~ database, which writes under the user's
Emacs directory.

*** Exit codes

- ~org-lint~ exits 0 when every file is clean. It also exits 0 when
  ~--skip-if-no-emacs~ is set and ~emacs~ is not on ~PATH~.
- It exits 1 when a file has a finding, a file is missing, ~emacs~ is
  not on ~PATH~, or no file was given.

** unnecessary-interface-assertion-linter

Flags ~var _ Iface = (*T)(nil)~ when two things are both true: only one
type implements ~Iface~, and the name ~Iface~ appears only on that line.
A use of the name, such as a function parameter, keeps the line. A second
implementation keeps it too.

#+BEGIN_SRC go
package iface

type Runner interface{ Run() }

type runner struct{}

func (*runner) Run() {}

var _ Runner = (*runner)(nil)
#+END_SRC

The path is absolute. A run of this file ends with:

#+BEGIN_EXAMPLE
bad.go:9:1: Unnecessary interface assertion
#+END_EXAMPLE

Adding ~func start(r Runner) { r.Run() }~ uses the name, and the finding
goes away.

*** Install

#+BEGIN_SRC bash
go install github.com/jaeyeom/experimental/devtools/linters/cmd/unnecessary-interface-assertion-linter@latest
#+END_SRC

*** Usage

#+BEGIN_SRC bash
unnecessary-interface-assertion-linter ./...
unnecessary-interface-assertion-linter --json ./...
unnecessary-interface-assertion-linter --dir path/to/module ./...
#+END_SRC

~--json~ is what [[file:../devcheck/README.org][devcheck]] reads.

*** Exit codes

- The command exits 0 when there is no finding.
- It exits 1 when there is a finding or a package fails to load.
- It exits 2 when the flags are invalid.

** pkgvar

A package-level ~var~ that never changes should be a ~const~. ~pkgvar~
also flags an initializer that calls a function or receives from a
channel when the package is loaded.

#+BEGIN_SRC go
package sample

import (
	"os"
	"regexp"
)

func loadConfig() string { return os.Getenv("CFG") }

var maxRetries = 3
var re = regexp.MustCompile(`x`)
var cfg = loadConfig()
var version = "dev" //nolint:pkgvar // set with -ldflags -X
var _ = regexp.MustCompile(`x`)
#+END_SRC

~maxRetries~ is never assigned and the package never takes its address,
so it should be a constant. ~re~ is quiet: ~regexp.MustCompile~ is on the
allowlist and the result is stored in ~re~. ~cfg~ is flagged because
~loadConfig~ calls ~os.Getenv~, which runs when the package is
initialized. ~version~ stays a variable. The ~nolint~ comment names
~pkgvar~ and gives a reason, which is how a string set with ~-ldflags -X~
is kept. A comment with no reason does not suppress the finding. The
blank ~var _~ is flagged even though ~regexp.MustCompile~ is on the
allowlist, because the result is discarded.

The message says "impure" when the call is not on the allowlist and is
not one of the builtins ~len~, ~cap~, ~complex~, ~real~, ~imag~, ~min~,
~max~, ~new~, and ~make~. A function in the same package is allowed only
when its body stays within those calls and does not change other
package-level variables, take their addresses, start a goroutine, defer,
send, or receive.

A compile-time interface assertion is not a ~pkgvar~ finding. The other
Go linter in this directory reports those.

The default allowlist is every name in the command below except
~example.com/config.Load~. The ~-allowlist~ flag replaces the whole list.
It does not append.

*** Install

#+BEGIN_SRC bash
go install github.com/jaeyeom/experimental/devtools/linters/cmd/pkgvar@latest
#+END_SRC

*** Usage

#+BEGIN_SRC bash
go vet -vettool=$(which pkgvar) ./...
#+END_SRC

#+BEGIN_SRC bash
go vet -vettool=$(which pkgvar) -allowlist errors.New,fmt.Errorf,regexp.MustCompile,strings.Join,strings.Repeat,strings.ReplaceAll,strings.Split,example.com/config.Load ./...
#+END_SRC

*** Output

~go vet~ prints paths relative to the package directory:

#+BEGIN_EXAMPLE
sample.go:10:5: package-level variable can be a constant
sample.go:12:5: package-level initializer calls an impure function or receives from a channel
sample.go:14:5: package-level initializer discards its result
#+END_EXAMPLE

~re~ and ~version~ produce no line. The ~pkgvar~ binary prints an
absolute path for the same three lines.

*** Exit codes

- ~go vet -vettool~ exits 0 when there is no finding and exits 1 when
  there is a finding or the package did not load.
- The ~pkgvar~ binary exits 3 when it prints a finding. It exits 1 when
  no package is given.

** agents-md-size

Checks per-file (default 4096 bytes) and cascading ancestor (default
16384 bytes) byte size limits for ~AGENTS.md~ files across a repository.
Supports the standard checker baseline format in
~.baselines/agents-md-size.json~ (see
[[file:../docs/checker-baseline.md][checker-baseline.md]]).

*** Install

#+BEGIN_SRC bash
go install github.com/jaeyeom/experimental/devtools/linters/cmd/agents-md-size@latest
#+END_SRC

*** Usage

#+BEGIN_SRC bash
agents-md-size
agents-md-size --root /path/to/repo
agents-md-size --update-baseline
agents-md-size --tighten-baseline
agents-md-size --strict-baseline=false
#+END_SRC

*** Exit codes

- Exits 0 when all ~AGENTS.md~ files pass and no stale baseline entries
  exist (under ~--strict-baseline=true~).
- Exits 1 when a size limit is violated or stale/ratchetable baseline
  entries exist under ~--strict-baseline=true~.
- Exits 2 on invalid flags, malformed baseline JSON, or I/O errors.

** migration-immutability

Fails when a change edits, deletes, or renames a database migration file
that the base branch already has. Adding a migration is always fine.
Once a migration merges, some environment may already have applied it,
and editing the file does not re-run it there: a database that applied
the old text silently drifts from a fresh one. Put schema changes in a
new migration.

Built-in patterns: ~django~ (~migrations/NNNN_*.py~), ~alembic~
(~migrations/versions/*.py~), ~sql~ (~migrations/*.sql~), and ~prisma~
(~prisma/migrations/*/migration.sql~). Add more with ~--pattern
NAME=REGEXP~, turn one off with ~--disable-pattern NAME~, and skip paths
edited in place by design with ~--exclude GLOB~.

It diffs the working tree against the merge-base with the base ref:
~--base~, else ~origin/$GITHUB_BASE_REF~, else the current branch's
upstream when it names a different branch, else ~origin/HEAD~. It never
fetches; in GitHub Actions use ~actions/checkout~ with ~fetch-depth: 0~.
A symlink at a migration path is always blocked. With no base, or no
tracked file matching a pattern, it errors instead of passing.

Reviewed exceptions live in ~.baselines/migration-immutability.json~ as
~transitions~ pinning the exact blob before and after (see
[[file:../docs/checker-baseline.md][checker-baseline.md]]). Any other
edit to the same file still fails.

*** Install

#+BEGIN_SRC bash
go install github.com/jaeyeom/experimental/devtools/linters/cmd/migration-immutability@latest
#+END_SRC

*** Usage

#+BEGIN_SRC bash
migration-immutability
migration-immutability --base origin/main
migration-immutability --exclude 'db/init/**' --pattern 'flyway=(^|/)db/migration/V[^/]+\.sql$'
migration-immutability --update-baseline --reason "black reformat" --issue "#123"
#+END_SRC

*** Exit codes

- Exits 0 when no migration the base already has was changed, or every
  change is allowed by the baseline.
- Exits 1 when a change is blocked.
- Exits 2 on invalid flags, an unresolvable base, no matching migration
  files, malformed baseline JSON, or git errors.

** py-sibling-import

Flags a bare import of a sibling module inside a package:

#+BEGIN_SRC python
# tools/rr/policy_test.py, where tools.rr.policy exists
import policy                    # flagged
from tools.rr import policy      # preferred
#+END_SRC

The bare import does not fail. pytest and ~python file.py~ put the file's
directory on ~sys.path~, so ~import policy~ loads a second module object,
separate from the ~tools.rr.policy~ the code under test reads.
~monkeypatch.setattr(policy, ...)~ then patches the copy nobody reads.

No setup is needed. A directory is a package when it has an
~__init__.py~ or when any tracked file imports into it by a dotted name
(e.g. ~from tools.rr import policy~), which covers namespace packages.
Flat script directories are never flagged. Every import counts,
including function-local and ~try~ imports. Relative imports are fine.
Generated files (~*_pb2.py~, ~*_pb2_grpc.py~) are skipped by default.
Only git-tracked files are checked.

It lives in [[file:pylinters/][pylinters]], a Python project that also
holds ~py-module-import~.

*** Install

#+BEGIN_SRC bash
uvx --from "git+https://github.com/jaeyeom/experimental@<tag>#subdirectory=devtools/linters/pylinters" py-sibling-import
#+END_SRC

*** Usage

#+BEGIN_SRC bash
py-sibling-import
py-sibling-import path/to/file.py
git diff --name-only -z origin/main | py-sibling-import --stdin0
py-sibling-import --exclude 'legacy/**' --generated '**/*_pb2.py'
#+END_SRC

A directory argument checks the tracked ~.py~ files below it (~.~ is the
whole tree).

A genuine exception carries ~# py-sibling-import: allow~ on any line of
the import statement.

*** As a pytest gate

#+BEGIN_SRC python
from pylinters import sibling_import
from pylinters.core import files


def test_no_bare_sibling_imports():
    fs = files.GitResolver.from_repo(".")
    cfg = sibling_import.load_config(f"{fs.root}/pyproject.toml")
    result = sibling_import.check(fs, cfg)
    assert not result.violations, sibling_import.format_report(result, cfg)
#+END_SRC

*** Configuration

Optional, in the repo root's ~pyproject.toml~. Unknown keys are errors.

#+BEGIN_SRC toml
[tool.pylinters]                 # shared by every pylinters checker
roots = ["src"]                  # default: ["src"] if src/ has Python
exclude = ["**/testdata/**"]
generated = ["**/*_pb2.py", "**/*_pb2_grpc.py"]   # the default

[tool.pylinters.sibling-import]
exclude = []                     # added to the shared list
allow-directive = "py-sibling-import: allow"
#+END_SRC

*** Exit codes

- Exits 0 when no scanned file imports a sibling bare.
- Exits 1 when there are violations.
- Exits 2 on invalid flags or config, a scanned file that does not
  parse, a path outside the repo, or git errors.

** py-module-import

Flags a symbol imported out of a first-party module, and asks for the
module instead:

#+BEGIN_SRC python
from myapp.types import CheckResult   # flagged
from myapp import types               # preferred
result = types.CheckResult()
#+END_SRC

The use site then shows where a name comes from, and
~monkeypatch.setattr(types, ...)~ patches the object the code reads.

#+BEGIN_EXAMPLE
main.py:1:25: from myapp.types import CheckResult: import the module instead (from myapp import types)
#+END_EXAMPLE

A ~from M import n~ is flagged when ~M~ is a git-tracked module or package
and ~n~ is not itself a submodule. Imports that resolve to no tracked file
(stdlib, third-party) are left alone. Absolute imports resolve against the
file's own source root, the repo root, then the configured ~roots~. A
stdlib or ~third-party~ name never resolves against those extra roots.
Relative imports, imports inside functions and ~if TYPE_CHECKING:~ blocks
all count. Not flagged: ~from . import x~, star imports, a package's
~__init__.py~ re-exporting its own submodules, and names matching the
~generated~ globs (~foo_pb2~). Only git-tracked files are checked.

*** Install

#+BEGIN_SRC bash
uvx --from "git+https://github.com/jaeyeom/experimental@<tag>#subdirectory=devtools/linters/pylinters" py-module-import
#+END_SRC

*** Usage

#+BEGIN_SRC bash
py-module-import
py-module-import path/to/file.py
git diff --name-only -z origin/main | py-module-import --stdin0
py-module-import --exclude 'legacy/**' --exempt-marker manage.py --third-party requests
#+END_SRC

Positional paths are relative to the current directory; ~--stdin0~ paths
are relative to the repo top level, as ~git diff --name-only~ prints them.
A directory checks the tracked ~.py~ files below it (~.~ is the whole
tree, still reported as a path run). Paths that are not tracked ~.py~
files, deleted, excluded, or under an exempt marker are skipped.
~--root-dir~, ~--generated~, ~--exempt-marker~ and ~--third-party~ replace
the configured lists; ~--exclude~ adds to the configured shared and checker
excludes. Exempt markers, from the flag or the config, must be plain ~.py~
file names such as ~manage.py~, with no directory part.

A genuine exception carries ~# py-module-import: allow~. On the line of
an imported name it exempts that name. On another line of the statement
(the ~from~ line or the closing parenthesis) it exempts the whole
statement.

*** Baseline

Existing violations can be recorded as debt in
~.baselines/py-module-import.json~, a per-file ~max_violations~ count
(see [[file:../docs/checker-baseline.md][checker-baseline]]).

- ~--baseline FILE~ picks another file, relative to the current directory.
- ~--update-baseline~ records the current counts.
- ~--tighten-baseline~ only removes stale entries and lowers limits.
- ~--strict-baseline=false~ stops failing on stale entries (default ~true~).

The two rewrite flags scan the whole tree; passing paths with them is a
usage error. They print ~baseline written to <path>~. A run with paths
reports stale entries only for those paths.

A file over its limit prints its violations and
~baseline exceeded: <path>: N violation(s), baseline allows M~. A passing
run that still has baselined debt says so:

#+BEGIN_EXAMPLE
PASSED: no new module symbol import (120 file(s) scanned, 4 baselined violation(s)).
#+END_EXAMPLE

A stale entry names a file that is now clean, below its limit, or deleted
or out of scope (excluded or under an exempt marker); ~--tighten-baseline~
removes or lowers it.

*** Configuration

Optional, in the repo root's ~pyproject.toml~. Unknown keys are errors.

#+BEGIN_SRC toml
[tool.pylinters]                 # shared by every pylinters checker
roots = ["src"]
exclude = ["**/testdata/**"]
generated = ["**/*_pb2.py", "**/*_pb2_grpc.py"]

[tool.pylinters.module-import]
exclude = []
exempt-markers = ["manage.py"]   # a tree holding manage.py is exempt
third-party = ["requests"]
allow-directive = "py-module-import: allow"
#+END_SRC

*** Exit codes

- Exits 0 when no scanned file has more violations than the baseline
  allows and no baseline entry is stale.
- Exits 1 when there are violations or stale baseline entries.
- Exits 2 on invalid flags, config or baseline, a scanned file that does
  not parse, a path outside the repo, or git errors.
