#+TITLE: decide
#+DATE: 2026-11-05

* Status

~decide status~ stores agent rows in the decide state directory, in
~status.json~, separate from the decision ledger.

- ~decide status set --agent <name> [--state working|idle|paused|blocked] "<text>"~
  writes one row. A new row with no ~--state~ is ~working~. A later set
  with no ~--state~ keeps the stored state.
- ~decide status list [--json]~ prints each name, state, age, and text.
  ~--json~ is an object with an ~agents~ array. Each agent includes
  ~updatedAt~.
- ~decide status clear --agent <name>~ removes that one row.
- ~decide status set --resource <name> free|busy ["<note>"]~ writes a shared
  resource flag. ~list~ prints ~<name>: free (<note>)~, or ~<name>: free~
  when the note is empty.
- ~decide status clear --resource <name>~ removes that one flag.
  ~--json~ includes a ~resources~ array.

In the inbox, ~g~ then ~s~ opens the same rows. The view reloads on the
inbox tick. A row older than five minutes is dim.

** Checkout leases

~"checkouts": [{"name": "checkout", "path": "/abs/repo"}]~ in the config
maps a resource name to a checkout path. ~status list~, ~--json~, the
inbox and ~decide.el~ then show that checkout's agentbus workdir lease:

- ~decide~ first runs ~agentbus lease status --guarded --path <path>~,
  which reads only local agentbus config. An unguarded path shows the
  stored row as before and makes no daemon call.
- For a guarded path, ~agentbus lease status --json --path <path>~ wins
  over any stored row for that name. ~list~ prints ~checkout: free~,
  ~checkout: held by <name> until 14:20~, ~checkout: paused by user~, or
  ~checkout: needs adopt (backup <ref>)~, plus ~, <n> queued~. In
  ~--json~ the row has ~"source": "lease"~, ~availability~ ~free~ or
  ~busy~, and the lease text in ~note~.
- When ~agentbus~ is missing or the lease cannot be read, the stored row
  from ~decide status set --resource~ shows with ~(guess)~ after it. Its
  JSON has ~"source": "stored"~ and ~"guess": true~. Other rows have
  ~"source": "stored"~.

Hub mode does not read the lease on the display machine yet: ~decide
status list~ runs on the hub, so it uses the hub's ~checkouts~ config and
the hub's ~agentbus~.

~decide targets [--json]~ prints the compose recipients from the config.
Plain output is one name per line. ~--json~ is an array of ~name~ and
~pane~. It does not print the notify template or the send template.

~decide send --to <name> [--json] "<text>"~ sends a note to one recipient
through the same command the inbox uses. The text is one argument. An
unknown name or an empty note sends nothing.

In the inbox compose box the recipient list is a dropdown of at most
eight rows, and at most a third of the screen. Typing filters it by name
or ~when~ text, ignoring case. ~Backspace~ widens it, ~Esc~ clears the
filter, and a second ~Esc~ leaves compose. ~↑~/~↓~ or ~C-p~/~C-n~ move
and ~Enter~ picks. A list longer than the dropdown shows the match count
and groups names by prefix.

With ~"recipients": {"agentbus": true}~ in the config (off by default)
the list adds the names from ~agentbus list --json~ after the configured
targets, with their ~when~ text and liveness. Dead names come last. A
configured target whose pane a bus name holds is shown once, as the bus
name. The listing is cached for 30 seconds. If ~agentbus~ is missing,
the daemon is down, or the call takes over 500ms, the list holds only the
configured targets and no error shows. A note to a bus name runs
~agentbus send <name> <note>~. The thread pane is ~agentbus:<name>~ and
~busMessage~ is the bus message id. Replies in that thread from the
inbox also go through ~agentbus send~. When the send fails the draft
stays and no thread is kept.

* Archive and outcome

~e~ or ~y~ in the inbox list or an open item archives a notification: it
is marked done with the outcome ~archived~, the same as ~decide done~. An
item with pending options still needs an answer. In an open item, ~d~
asks for an outcome, then marks the item done with it. ~g~ then ~d~
still opens the Done folder.

* Snooze

~b~ in the inbox list or an open item snoozes it: ~1h~, ~3h~, ~tomorrow
9:00~, ~next Monday 9:00~, or a custom time. A snoozed item keeps its
state and is hidden from every folder but Snoozed (~g~ then ~z~), which
sorts by wake time. It comes back, unread, at that time or as soon as a
message lands on its thread, such as an agent ~decide reply~. In
Snoozed, ~b~ also offers ~unsnooze~.

- ~decide snooze <id> <when>~ takes ~2h30m~, ~HH:MM~ (today, or tomorrow
  once passed), ~YYYY-MM-DD HH:MM~, or ~mon 9:00~, in local time. A done
  or withdrawn item is refused.
- ~decide unsnooze <id>~ returns it now.
- ~decide list~ hides snoozed items. ~--snoozed~ lists only them, and
  ~decide inbox --snoozed~ opens on that folder. ~show~ prints
  ~snoozed until:~ and ~--json~ carries ~snoozedUntil~ and ~snoozedAt~.

* Sending from a composer

~Ctrl+Enter~, ~Alt+Enter~, or ~C-s~ sends from every composer: the note,
reply, answer, and outcome boxes. In the note box it does the same as
~Tab~ to ~[Send]~ then ~Enter~. ~Enter~ and ~C-j~ keep their meaning:
~C-j~ inserts a newline, ~Enter~ inserts one in the note box and sends
in the others. The inbox runs the terminal in raw mode, which turns off
XON/XOFF flow control, so ~C-s~ reaches it.

~Ctrl+Enter~ works where the terminal sends it as its own sequence with
no keyboard mode switched on: exactly =ESC [27;5;13~= (xterm
modifyOtherKeys) or =ESC [13;5u= (kitty). The inbox rewrites those two
sequences to ~Alt+Enter~ before bubbletea parses the input, and every
other sequence passes through unchanged. When a read stops partway into
one, the inbox waits up to 25ms for the rest, so a lone ~Esc~ is at most
that late. The inbox does not turn on modifyOtherKeys or the kitty
keyboard protocol: either mode would also change how ~Shift~ and ~Ctrl~
letters, or ~Esc~, arrive, and bubbletea v1 does not parse those
sequences. A terminal that sends ~Ctrl+Enter~ as plain ~Enter~ or ~C-j~
gets that key's meaning.

What one terminal sends (herdr, ~TERM=xterm-256color~, no mode switched
on):

| Key        | Arrives as                                      |
|------------+-------------------------------------------------|
| Ctrl+Enter | ="\x1b[27;5;13~"= (xterm modifyOtherKeys form)  |
| Alt+Enter  | ~alt+enter~                                     |
| C-j        | ~ctrl+j~                                        |
| Enter      | ~enter~                                         |

To see what a terminal sends, run the inbox with ~DECIDE_KEYDEBUG~ set
to a log file path, or to ~1~ for ~decide-keys.log~ in the temp
directory:

#+begin_src sh
DECIDE_KEYDEBUG=/tmp/decide-keys.log decide inbox
tail -f /tmp/decide-keys.log  # in another pane
#+end_src

Each key is one line with its bubbletea type, ~alt~, runes, and name,
such as ~key type=13 (enter) alt=true runes="" str="alt+enter"~. A
rewritten ~Ctrl+Enter~ adds a line before its ~alt+enter~ key, such as
~ctrl+enter bytes="\x1b[13;5u" as alt+enter~. Other input bubbletea does
not parse is logged with its bytes, such as
~unknown tea.unknownCSISequenceMsg bytes="\x1b[13;2u"~.

* Avatars

The inbox can show a 10x6 avatar for the other party: in an open item,
left of the ID and header fields; in compose, left of the recipient
list, for the selected recipient. Map names to files in
~$XDG_CONFIG_HOME/decide/config.json~:

#+begin_src json
{
  "avatars": [
    {"match": "coord/primary", "file": "~/avatars/coord.png"},
    {"match": "pm-*", "file": "avatars/pm.txt"}
  ],
  "avatarDefault": true,
  "avatarMono": "hide"
}
#+end_src

- ~avatars~ matches the item owner, compose target, or bus name. An
  exact ~match~ wins, then the first ~path.Match~ glob. ~file~ may start
  with =~/= for the home directory and is otherwise relative to the config file. A PNG or WEBP
  image is drawn as colored characters; any other file is text, and its
  ANSI colors are kept.
- ~avatarDefault~ (off by default) shows a built-in round face for names
  no rule matches.
- ~avatarMono~ is ~"hide"~ to hide avatars under ~NO_COLOR~ or on a
  monochrome terminal. Otherwise they show without color.

An open item from ~coord/primary~ then looks like this:

#+begin_example
┌────────────────────────────────────────────────────────┐
│  .----.   D-007                                        │
│ /      \      From: coord/primary                      │
│|  o  o  |     Kind: relay                              │
│|  \__/  |    State: open                               │
│ \      /   Created: 2026-11-10T09:00:00Z               │
│  '----'   Answered:                                    │
│                                                        │
│coord/primary  5m  latest                               │
│  merge the release branch?                             │
#+end_example

The avatar is hidden, and the layout is the same as without one, when
no rule matches and ~avatarDefault~ is off, when the terminal is under
60 columns, or when fewer than 30 columns would be left beside it. A
file that cannot be read or decoded is hidden too, and the status line
shows the error once. Rendered avatars are cached, so moving the
selection or reloading does not decode the file again.

* Emacs

~devtools/decide/emacs/decide.el~ is a plain Emacs frontend. Load that
file and run ~M-x decide-list~. It calls ~decide list --json~ and
~decide show --json~. ~o~ answers with an option key. ~0~ opens a
normal buffer to reply with free text. ~C-c C-c~ sends that buffer and
~C-c C-k~ closes it without answering.

~c~ composes a note. The recipient comes from ~decide targets --json~.
~C-c C-c~ runs ~decide send --to~ with the buffer text as one argument.
~C-c C-k~ closes the buffer and does not send. ~s~ shows
~decide status list --json~. A row older than five minutes is dim.
The status buffer refreshes every two seconds while it is visible, and
the timer stops when the buffer is killed.

* Notify

After a relay answer is saved, ~notifyTemplate~ runs as a shell command.
The environment is how a template reads the answer. Nothing is written
into the command string.

- ~DECIDE_ID~ is the item id.
- ~DECIDE_ANSWER~ is the saved answer. An option answer is the option key.
  A multi-line free-text answer is stored unchanged, including quotes.
- ~DECIDE_ANSWER_LABEL~ is the label the chosen option had when it was
  answered. A later follow-up does not change it. It is empty for free text.
- ~DECIDE_OWNER~ is the item owner.
- ~DECIDE_PANE~ is the notify pane. An item pane overrides the config pane.
- ~DECIDE_KIND~ is the item kind, ~relay~ or ~type-in~.
- ~DECIDE_QUESTION~ is the first line of the question, at most 200 characters.
  The next line is not included, and a character is not split.
- ~DECIDE_ANSWERED_AT~ is ~answeredAt~ in RFC3339.
- ~DECIDE_ANSWERED_BY~ is the stored ~answeredBy~, for example ~human~.
- ~DECIDE_THREAD_HEADER~ is one line such as ~[decide D-123 from human]~,
  with the thread id and the author.
- ~DECIDE_REPLY_HINT~ is one line such as
  ~Reply in this thread: decide reply D-123 "..." (add --option key:label for a follow-up question; decide done D-123 "outcome" when finished). Do not answer only in your terminal.~
- ~DECIDE_MACHINE~ is the herdr machine ~DECIDE_PANE~ is on, for an
  item asked in hub mode from another machine. It is empty for a pane on
  this machine. A template that reaches either kind of pane:

  #+begin_src sh
  herdr ${DECIDE_MACHINE:+--machine "$DECIDE_MACHINE"} agent prompt "$DECIDE_PANE" "$DECIDE_THREAD_HEADER $DECIDE_ANSWER"
  #+end_src

An empty ~notifyTemplate~ runs nothing. There is no default notify command.

A parent value of the same name does not win.

~{id}~, ~{answer}~, ~{owner}~, and ~{pane}~ are not substituted. Braces
are not replaced. An old ~notifyTemplate~ that still uses those braces
runs the command and does not insert the answer.

* Hub mode: a second machine

One machine, the hub, holds the ledger. A second machine can run the
same ~decide~ commands against it over ssh. Set the hub in
~$XDG_CONFIG_HOME/decide/config.json~ on the second machine, or set
~DECIDE_HUB~, which wins:

#+begin_src json
{"hub": "me@hub", "hubTimeout": "5s", "machine": "laptop"}
#+end_src

~machine~ is this machine's herdr label on the hub, the same label
agentbus uses; ~DECIDE_MACHINE~ wins over it. An ~ask~ from a herdr
pane needs it: the ask sends this pane as
~DECIDE_AS_HANDLE=herdr:<machine>/<session>/<pane>~. The hub trusts that
handle only when ~SSH_CONNECTION~ is set and the handle names another
machine, as agentbus does. On the hub, the item stores the caller's
pane as ~notifyPane~ when ~--notify-pane~ is not given, and the
caller's machine as ~notifyMachine~ either way, because a bare pane id
names a pane on the machine the command came from. An ~agentbus:~
notify pane gets no machine. An ask on the hub itself stores no
machine, as before.

The hub then reaches that pane through ~herdr --machine <machine>~: the
built-in compose send (~decide send --id~ and a reply from the inbox)
puts ~--machine <machine>~ after the send template's program, with a
5s deadline, and fails with
~machine <machine> unreachable: host unreachable~ or
~... authentication locked (unlock your SSH/gpg agent)~ as agentbus
does. The notify template reads the machine from ~DECIDE_MACHINE~; see
[[*Notify]].

Then every command except ~help~ and ~skill~ runs as
~ssh -o BatchMode=yes -o ConnectTimeout=<n> <hub> decide <args>~, with
each argument quoted. ~hubTimeout~ is the connect timeout (default 5s).
stdout, stderr, and the exit code come back unchanged, and the local
ledger is never read or created. ~decide inbox~ refuses; run it on the
hub.

The hub needs an SSH key the agent holds, because ~BatchMode=yes~ never
asks for a passphrase; ~decide~ on its ~PATH~ for a non-interactive ssh
command; and a POSIX login shell (sh, bash, or zsh). The call has a
deadline of twice the connect timeout until the hub's shell starts, so
a locked key cannot hang it. A hub that cannot be reached fails with
~decide: hub me@hub unreachable: host unreachable~ when a one-second
TCP connect to its SSH port fails, or with
~... unreachable: authentication locked (unlock your SSH/gpg agent)~
when the host answers.
