#+DATE: 2026-11-05

* Status

~decide status~ stores agent rows in the decide state directory, in
~status.json~, separate from the decision ledger.

- ~decide status set --agent <name> [--state working|idle|paused|blocked] "<text>"~
  writes one row. A new row with no ~--state~ is ~working~. A later set
  with no ~--state~ keeps the stored state.
- ~decide status list [--json]~ prints each name, state, age, and text.
  ~--json~ is an object with an ~agents~ array. Each agent includes
  ~updatedAt~.
- ~decide status clear --agent <name>~ removes that one row.
- ~decide status set --resource <name> free|busy ["<note>"]~ writes a shared
  resource flag. ~list~ prints ~<name>: free (<note>)~, or ~<name>: free~
  when the note is empty.
- ~decide status clear --resource <name>~ removes that one flag.
  ~--json~ includes a ~resources~ array.

In the inbox, ~g~ then ~s~ opens the same rows. The view reloads on the
inbox tick. A row older than five minutes is dim.

** Checkout leases

~"checkouts": [{"name": "checkout", "path": "/abs/repo"}]~ in the config
maps a resource name to a checkout path. ~status list~, ~--json~, the
inbox and ~decide.el~ then show that checkout's agentbus workdir lease:

- ~decide~ first runs ~agentbus lease status --guarded --path <path>~,
  which reads only local agentbus config. An unguarded path shows the
  stored row as before and makes no daemon call.
- For a guarded path, ~agentbus lease status --json --path <path>~ wins
  over any stored row for that name. ~list~ prints ~checkout: free~,
  ~checkout: held by <name> until 14:20~, ~checkout: paused by user~, or
  ~checkout: needs adopt (backup <ref>)~, plus ~, <n> queued~. In
  ~--json~ the row has ~"source": "lease"~, ~availability~ ~free~ or
  ~busy~, and the lease text in ~note~.
- When ~agentbus~ is missing or the lease cannot be read, the stored row
  from ~decide status set --resource~ shows with ~(guess)~ after it. Its
  JSON has ~"source": "stored"~ and ~"guess": true~. Other rows have
  ~"source": "stored"~.

In hub mode ~decide status list~ runs on the hub, so it uses the hub's
~checkouts~ config and the hub's ~agentbus~. A plain entry is a checkout
on the hub itself. For a checkout on another machine that uses the
agentbus hub, name that machine:
~{"name": "checkout", "machine": "mac", "path": "/abs/repo"}~. ~decide~
then runs ~agentbus lease status --all --json~ once and shows the lease
whose ~checkout~ is ~mac:/abs/repo~, the same text with ~"source":
"lease"~. The path must be the checkout's git top-level on that machine.
There is no ~--guarded~ check for such an entry, since it would read the
hub's config: when no lease is known under that key, or ~agentbus~
cannot be read, the stored row shows with ~(guess)~.

~decide targets [--json]~ prints the compose recipients from the config.
Plain output is one name per line. ~--json~ is an array of ~name~ and
~pane~. It does not print the notify template or the send template.

~decide send --to <name> [--json] "<text>"~ sends a note to one recipient
through the same command the inbox uses. The text is one argument. An
unknown name or an empty note sends nothing.

In the inbox compose box the recipient list is a dropdown of at most
eight rows, and at most a third of the screen. Typing filters it by name
or ~when~ text, ignoring case. ~Backspace~ widens it, ~Esc~ clears the
filter, and a second ~Esc~ leaves compose. ~↑~/~↓~ or ~C-p~/~C-n~ move
and ~Enter~ picks. A list longer than the dropdown shows the match count
and groups names by prefix.

With ~"recipients": {"agentbus": true}~ in the config (off by default)
the list adds the names from ~agentbus list --json~ after the configured
targets, with their ~when~ text and liveness. Dead names come last. A
configured target whose pane a bus name holds is shown once, as the bus
name. The names load in the background when the inbox starts and again
every 30 seconds, so opening compose never waits for ~agentbus~: the list
shows the configured targets and the names loaded so far, and names that
arrive later join it without moving the selection. The top-level
~"recipientsTimeout": "5s"~ bounds each load (default 3s). When a load times out the status line
shows ~agentbus: slow (>3s)~, and when ~agentbus~ is missing or fails it
shows ~agentbus: unavailable (<error>)~, once until a load succeeds. The
last good names stay in the list. A note to a bus name runs
~agentbus send <name> <note>~. The thread pane is ~agentbus:<name>~ and
~busMessage~ is the bus message id. Replies in that thread from the
inbox also go through ~agentbus send~. When the send fails the draft
stays and no thread is kept.

* Archive and outcome

~e~ or ~y~ in the inbox list or an open item archives a notification: it
is marked done with the outcome ~archived~, the same as ~decide done~. An
item with pending options still needs an answer. In an open item, ~d~
asks for an outcome, then marks the item done with it. ~g~ then ~d~
still opens the Done folder.

* Snooze

~b~ in the inbox list or an open item snoozes it: ~1h~, ~3h~, ~tomorrow
9:00~, ~next Monday 9:00~, or a custom time. A snoozed item keeps its
state and is hidden from every folder but Snoozed (~g~ then ~z~), which
sorts by wake time. It comes back, unread, at that time or as soon as a
message lands on its thread, such as an agent ~decide reply~. In
Snoozed, ~b~ also offers ~unsnooze~.

- ~decide snooze <id> <when>~ takes ~2h30m~, ~HH:MM~ (today, or tomorrow
  once passed), ~YYYY-MM-DD HH:MM~, or ~mon 9:00~, in local time. A done
  or withdrawn item is refused.
- ~decide unsnooze <id>~ returns it now.
- ~decide list~ hides snoozed items. ~--snoozed~ lists only them, and
  ~decide inbox --snoozed~ opens on that folder. ~show~ prints
  ~snoozed until:~ and ~--json~ carries ~snoozedUntil~ and ~snoozedAt~.

* Sending from a composer

~Ctrl+Enter~, ~Alt+Enter~, or ~C-s~ sends from every composer: the note,
reply, answer, and outcome boxes. In the note box it does the same as
~Tab~ to ~[Send]~ then ~Enter~. ~Enter~ and ~C-j~ keep their meaning:
~C-j~ inserts a newline, ~Enter~ inserts one in the note box and sends
in the others. The inbox runs the terminal in raw mode, which turns off
XON/XOFF flow control, so ~C-s~ reaches it.

~Ctrl+Enter~ works where the terminal sends it as its own sequence with
no keyboard mode switched on: exactly =ESC [27;5;13~= (xterm
modifyOtherKeys) or =ESC [13;5u= (kitty). The inbox rewrites those two
sequences to ~Alt+Enter~ before bubbletea parses the input, and every
other sequence passes through unchanged. When a read stops partway into
one, the inbox waits up to 25ms for the rest, so a lone ~Esc~ is at most
that late. The inbox does not turn on modifyOtherKeys or the kitty
keyboard protocol: either mode would also change how ~Shift~ and ~Ctrl~
letters, or ~Esc~, arrive, and bubbletea v1 does not parse those
sequences. A terminal that sends ~Ctrl+Enter~ as plain ~Enter~ or ~C-j~
gets that key's meaning.

What one terminal sends (herdr, ~TERM=xterm-256color~, no mode switched
on):

| Key        | Arrives as                                      |
|------------+-------------------------------------------------|
| Ctrl+Enter | ="\x1b[27;5;13~"= (xterm modifyOtherKeys form)  |
| Alt+Enter  | ~alt+enter~                                     |
| C-j        | ~ctrl+j~                                        |
| Enter      | ~enter~                                         |

To see what a terminal sends, run the inbox with ~DECIDE_KEYDEBUG~ set
to a log file path, or to ~1~ for ~decide-keys.log~ in the temp
directory:

#+begin_src sh
DECIDE_KEYDEBUG=/tmp/decide-keys.log decide inbox
tail -f /tmp/decide-keys.log  # in another pane
#+end_src

Each key is one line with its bubbletea type, ~alt~, runes, and name,
such as ~key type=13 (enter) alt=true runes="" str="alt+enter"~. A
rewritten ~Ctrl+Enter~ adds a line before its ~alt+enter~ key, such as
~ctrl+enter bytes="\x1b[13;5u" as alt+enter~. Other input bubbletea does
not parse is logged with its bytes, such as
~unknown tea.unknownCSISequenceMsg bytes="\x1b[13;2u"~.

* Avatars

The inbox can show a 10x6 avatar for the other party: in an open item,
left of the ID and header fields; in compose, left of the recipient
list, for the selected recipient. Map names to files in
~$XDG_CONFIG_HOME/decide/config.json~:

#+begin_src json
{
  "avatars": [
    {"match": "coord/primary", "file": "~/avatars/coord.png"},
    {"match": "pm-*", "file": "avatars/pm.txt"},
    {"match": "review/*", "builtin": "owl"}
  ],
  "avatarDefault": true,
  "avatarMono": "hide"
}
#+end_src

- ~avatars~ matches the item owner, compose target, or bus name. An
  exact ~match~ wins, then the first ~path.Match~ glob. ~file~ may start
  with =~/= for the home directory and is otherwise relative to the config file. A PNG or WEBP
  image is drawn as colored characters; any other file is text, and its
  ANSI colors are kept. A rule may name a built-in figure with
  ~builtin~ instead of a ~file~; a rule with both is a config error.
  A rule with ~"hide": true~ shows no avatar for the names it matches.
- ~avatarDefault~ (off by default) gives each name no rule matches a
  built-in figure. The same name always gets the same figure, on every
  run and machine, with no other config. Built-ins come in generations,
  each a fixed list of ids that never changes once shipped. A second
  hash of the name draws a generation, weighted by its size; then the
  FNV-1a hash of the name, mod that generation's size, picks the id.
  Each added generation of /new/ figures moves only about
  new/(old+new) of the unpinned names, each to one of the new figures;
  every other name keeps its figure. A ~builtin~ rule pins a name for
  good.
- ~avatarMono~ is ~"hide"~ to hide avatars under ~NO_COLOR~ or on a
  monochrome terminal. Otherwise they show without color.

decide ships 42 original built-in figures, each 10x6 in truecolor
half-block and box characters with no background fills, so they read on
light and dark themes. Generation 1: ~bee~, ~bun~, ~cactus~, ~cat~,
~crab~, ~fox~, ~frog~, ~ghost~, ~glasses~, ~headphones~,
~knight-helmet~, ~lighthouse~, ~mushroom~, ~octopus~, ~owl~,
~penguin~, ~planet~, ~robot~, ~rocket~, ~snail~, ~teapot~, ~tree~,
~whale~, and ~wizard-hat~. Generation 2 (which moved about 18/42 of
unpinned names): ~banker~, ~beer-mug~, ~bishop~, ~book~, ~cook~,
~dog~, ~general~, ~hammer~, ~jester~, ~king~, ~merchant~, ~peasant~,
~physician~, ~pirate~, ~queen~, ~scholar~, ~spy~, and ~witch~. The
people tell apart by hat, hair, or what they hold. Preview them,
several per row as the terminal allows, and see which one a name gets:

#+begin_src sh
decide avatars list
decide avatars list --name coord/primary
#+end_src

An open item from ~review/docs~ then looks like this (without color):

#+begin_example
┌────────────────────────────────────────────────────────┐
│▗▖      ▗▖ D-007                                        │
│▐█▀▀▀▀▀▀█▌     From: review/docs                        │
│▐ (o)(o) ▌     Kind: relay                              │
│▐   \/   ▌    State: open                               │
│▐ ▀▄▀▄▀▄ ▌  Created: 2026-11-10T09:00:00Z               │
│ ▀▘ ▀▀ ▝▀  Answered:                                    │
│                                                        │
│review/docs  5m  latest                                 │
│  merge the release branch?                             │
#+end_example

The avatar is hidden, and the layout is the same as without one, when
no rule matches and ~avatarDefault~ is off, when the terminal is under
60 columns, or when fewer than 30 columns would be left beside it. A
file that cannot be read or decoded, or an unknown ~builtin~ id, is
hidden too, and the status line shows the error once. Rendered avatars are cached, so moving the
selection or reloading does not decode the file again.

** Changing an avatar from the inbox

~A~ in the item view opens a picker for the owner's avatar: every
built-in figure with its id under it, ~*~ on the figure shown now and
~>~ on the cursor. ~h~ ~j~ ~k~ ~l~ or the arrows move, ~Enter~ saves,
and ~Esc~ cancels; the grid scrolls when it does not fit. Two extra
entries come first: ~default~ removes the owner's exact rule, so glob
rules or ~avatarDefault~ apply again, and ~none~ hides the owner's
avatar. The new avatar shows at once, and the status line says
~avatar for <owner>: <id> (saved to config)~. The same change from a
script, or ~A~ in ~decide.el~:

#+begin_src sh
decide avatars set ops/x owl
decide avatars set ops/x default
decide avatars set ops/x none
decide avatars list --ids
#+end_src

This is the only time decide writes its config, and it writes only the
~avatars~ section. Choosing a figure writes ~{"match": "<owner>",
"builtin": "<id>"}~, or ~"hide": true~ for ~none~. An existing rule
whose ~match~ is exactly the owner keeps its place and other keys and
has its ~file~ or ~builtin~ replaced; otherwise the new rule goes first
in ~avatars~. Glob rules are never changed. Every other key, known or
not, keeps its value and order; the file is rewritten with a 2-space
indent. The write goes to a temp file in the same directory, is
synced, then renamed over the config; when ~config.json~ is a symlink,
its target is replaced and the link stays. A config that does not parse
or cannot be written is left as it is, and the error goes to the status
line (or stderr).

The config is this machine's, the one the inbox reads its avatars from.
In hub mode the inbox runs here, so the change is local and the hub's
config is not touched; ~decide avatars~ also runs locally.

To undo a change, pick ~default~ (or ~decide avatars set <name>
default~), edit the ~avatars~ rule by hand, or restore the copy of the
original: before its first write, each inbox session (or each
~decide avatars set~) copies ~config.json~ to ~config.json.bak~ next to
it.

* Opening links

An item's links are its ~--link~ URLs plus the URLs in its question and
messages, in the order the item view draws them. ~l~ in the item view
opens the only link straight away. With several, ~l~ opens a picker
that lists every link, numbered, with long URLs shortened in the
middle to keep the host and the end of the path. ~j~ / ~k~ or the arrow
keys move and ~Enter~ opens the row. With nine links or fewer a digit
opens its link at once; with more, type the number and press ~Enter~
(~1~ ~2~ ~Enter~ opens the 12th). ~Esc~ cancels.

The opener is ~openCommand~ in ~$XDG_CONFIG_HOME/decide/config.json~,
an argument list. The URL is appended as the last argument and no shell
runs. The default is ~["xdg-open"]~, or ~["open"]~ on macOS:

#+begin_src json
{"openCommand": ["firefox", "--new-tab"]}
#+end_src

The opener runs on the machine running the inbox, in the background
with a 5 second limit, so the inbox never waits for it. The status line
then shows ~opened <url>~ or ~open failed: <error>~. There is no
clipboard fallback; ~L~ copies the link.

** Clicking links

The inbox captures the mouse by default, so a click reaches the inbox
rather than the terminal. A click or a ~Ctrl~ click on a URL in the item
view opens it with the same opener and status line as ~l~. Each line of
a wrapped URL opens the whole URL. A ~Ctrl~ click anywhere else does
nothing, while a plain click there keeps its usual meaning, such as
opening a row or answering an option. ~Shift~ drag still selects text.

~M~ toggles mouse capture. With capture off, the terminal or the
multiplexer handles clicks itself: drag selects text, and a terminal
that opens links on ~Ctrl~ click or ~Cmd~ click does so.

The item view and the link picker wrap every URL they draw in an OSC 8
hyperlink to the full URL, including a URL that is wrapped across lines
or shortened, so a terminal that supports OSC 8 opens the whole URL from
any visible part. The sequences take no columns, and ~NO_COLOR~ keeps
them. Turn them off in the config:

#+begin_src json
{"hyperlinks": false}
#+end_src

* Where the owner lives

The item view has an ~Owner:~ header line: the owner and the herdr
workspace, tab, and pane of the item's stored ~notifyPane~, looked up
live when the item opens:

#+begin_example
Owner: review-load at experimental / review (w6:pM)
#+end_example

- No stored pane: ~at unknown~. An ~agentbus:~ name is not looked up
  and shows as the pane id.
- A pane herdr no longer lists: ~at (w6:pM) — tab closed~.
- A ~notifyMachine~ other than this machine's label (~machine~ in the
  config, or ~DECIDE_MACHINE~): the lookup runs through
  ~herdr --machine <m>~ and the line starts with the machine, as in
  ~at mac: experimental / review (w6:pM)~. A machine that does not
  answer shows ~at mac: (w6:pM) (unreachable)~.
- herdr missing, not running, or failing: only the pane id.

A lookup is one ~herdr pane list~ (which maps the pane to its tab),
one ~herdr tab list~, and one ~herdr workspace list~ per machine, each
with a 5s deadline. The inbox never waits for it: the line shows the
pane id until the lookup returns. The result is cached per item for
the session and looked up again each time the item is opened; the
ledger reload tick does not ask herdr.

~decide show --json~ adds ~ownerLocation~ with ~machine~ (empty for
this machine), ~workspace~, ~tab~, ~pane~, and ~state~: ~live~,
~closed~, ~unknown~, or ~unreachable~. A live pane also has
~workspaceId~ and ~tabId~. Emacs shows the same line from it, so an
Emacs item buffer is drawn after the lookup, and ~g~ looks it up again.

** Jump to the owner

~o~ in the TUI item view, or ~O~ in an Emacs item buffer, brings the
owner's herdr tab to the front from the location already looked up:
~herdr workspace focus <workspaceId>~, then ~herdr tab focus <tabId>~.
herdr 0.9 focuses a pane only by direction from another pane, not by
id, so the tab is the target. The TUI runs the calls off the update
loop. The inbox stays where it was, and the item is not marked read or
answered.

- Success: the status line says ~focused experimental / review~.
- Another machine: the calls run through ~herdr --machine <m>~, and the
  status line says ~focused mac: experimental / review~. When herdr
  refuses, it says ~owner is on mac; not focusable from here~.
- A closed tab, a machine that did not answer, or an unknown location:
  no herdr call, and the status line says why, such as
  ~owner tab closed; nothing to focus~.
- In the TUI, before the lookup returns: ~owner location still loading~.

* The owner of an ask

Inside a herdr pane (~HERDR_PANE_ID~ is set), ~decide ask~ without
~--owner~ uses the label of this pane's tab as the owner, so the owner
matches the tab the user sees. Outside herdr, or when herdr does not
list the pane, ~--owner~ is required.

Every ask from a herdr pane stores that pane as ~notifyPane~, so
[[*Where the owner lives]] can find it. An explicit ~--notify-pane~
still wins and still decides where answers go.

An explicit ~--owner~ that is neither the tab label nor one of this
pane's agentbus names, from ~agentbus whoami~ with a 2s deadline, prints
a warning on stderr and still files the item:

#+begin_example
warning: owner "X" matches neither this tab ("review") nor your agentbus names (ops/inbox); the user finds you by tab
#+end_example

When agentbus is missing or fails, the names are ~none~ and only the tab
label counts.

* Emacs

~devtools/decide/emacs/decide.el~ is a plain Emacs frontend. Load that
file and run ~M-x decide-list~. It calls ~decide list --json~ and
~decide show --json~. ~o~ answers with an option key. ~0~ opens a
normal buffer to reply with free text. ~C-c C-c~ sends that buffer and
~C-c C-k~ closes it without answering. ~l~ opens the item's link with
~browse-url~; with several it asks for one of the numbered links.

~c~ composes a note. The recipient comes from ~decide targets --json~.
~C-c C-c~ runs ~decide send --to~ with the buffer text as one argument.
~C-c C-k~ closes the buffer and does not send. ~s~ shows
~decide status list --json~. A row older than five minutes is dim.
The status buffer refreshes every two seconds while it is visible, and
the timer stops when the buffer is killed.

decide.el runs one ~decide~ command per action, so it works in hub mode
unchanged: with ~hub~ in the config or ~DECIDE_HUB~ set (for example
~(setenv "DECIDE_HUB" "me@hub")~), each call runs on the hub over ssh and
links open in this Emacs. For one hub only in Emacs, set
~decide-program~ to a wrapper script that runs
~exec decide --remote me@hub "$@"~.

* Where an answer came from

Each stored answer has ~via~, shown as ~answer.via~ in
~decide show --json~ and ~decide list --json~, and as a ~via:~ line in
~decide show~.

- ~ui~: the user answered in the inbox TUI, or Emacs answered with
  ~decide answer --via ui~ or, from its composer, ~decide send --id --via ui~.
- ~cli~: ~decide answer~ or ~decide send --id~ on an open question without
  ~--via~. ~--via cli~ is the same. Any other ~--via~ value is an error.

Only the human front ends pass ~--via ui~. Agents never pass it. A tool
that must act only on an answer the user gave interactively checks that
~via~ is ~ui~. An answer stored before ~via~ existed has no ~via~ in its
JSON and does not count as ~ui~. Hub mode forwards ~--via~ unchanged, so
an answer from a hub client keeps its ~via~.

This guards against accidents, not a misbehaving agent: every agent
runs as the same user and could still edit the ledger or drive the TUI.

** Who wrote each message

Each thread message in ~messages~ also records where it came from:

- ~via~: every human message (an answer, a composer send, a new thread
  from ~decide send --to~) has ~ui~ or ~cli~, by the same rules as
  ~answer.via~. Agent messages have none. A message stored before ~via~
  existed has none and does not count as ~ui~.
- ~by~: ~decide reply~ and ~decide send --id~ record who ran them: the
  caller's agentbus name when its pane has one, else its herdr pane
  handle, else nothing. In hub mode the client sends its handle and
  agentbus names to the hub, as for an ask. ~author~ is unchanged: a
  reply's author is still the thread owner. The inbox and Emacs show
  ~owner (via <by>)~ when ~by~ is set and differs from the author.

~decide show --json~ includes ~via~ and ~by~ on each message, next to
~optionKey~.

A reply returns an answered or done thread to the inbox, as intended.
A later human free-text message that answers the reopened thread
replaces ~answer~. A tool that needs an
earlier option pick reads the messages, which keep its ~optionKey~,
~via~ and ~by~, rather than ~answer~.

* Notify

After a relay answer is saved, ~notifyTemplate~ runs as a shell command.
The environment is how a template reads the answer. Nothing is written
into the command string.

- ~DECIDE_ID~ is the item id.
- ~DECIDE_ANSWER~ is the saved answer. An option answer is the option key.
  A multi-line free-text answer is stored unchanged, including quotes.
- ~DECIDE_ANSWER_LABEL~ is the label the chosen option had when it was
  answered. A later follow-up does not change it. It is empty for free text.
- ~DECIDE_OWNER~ is the item owner.
- ~DECIDE_PANE~ is the notify pane. An item pane overrides the config pane.
- ~DECIDE_KIND~ is the item kind, ~relay~ or ~type-in~.
- ~DECIDE_QUESTION~ is the first line of the question, at most 200 characters.
  The next line is not included, and a character is not split.
- ~DECIDE_ANSWERED_AT~ is ~answeredAt~ in RFC3339.
- ~DECIDE_ANSWERED_BY~ is the stored ~answeredBy~, for example ~human~.
- ~DECIDE_THREAD_HEADER~ is one line such as ~[decide D-123 from human]~,
  with the thread id and the author.
- ~DECIDE_REPLY_HINT~ is one line such as
  ~Reply in this thread: decide reply D-123 "..." (add --option key:label for a follow-up question; decide done D-123 "outcome" when finished). Do not answer only in your terminal.~
- ~DECIDE_MACHINE~ is the herdr machine ~DECIDE_PANE~ is on, for an
  item asked in hub mode from another machine. It is empty for a pane on
  this machine. A template that reaches either kind of pane:

  #+begin_src sh
  herdr ${DECIDE_MACHINE:+--machine "$DECIDE_MACHINE"} agent prompt "$DECIDE_PANE" "$DECIDE_THREAD_HEADER $DECIDE_ANSWER"
  #+end_src

An empty ~notifyTemplate~ runs nothing. There is no default notify command.

A parent value of the same name does not win.

~{id}~, ~{answer}~, ~{owner}~, and ~{pane}~ are not substituted. Braces
are not replaced. An old ~notifyTemplate~ that still uses those braces
runs the command and does not insert the answer.

* Hub mode: a second machine

One machine, the hub, holds the ledger. A second machine can run the
same ~decide~ commands against it over ssh. Set the hub in
~$XDG_CONFIG_HOME/decide/config.json~ on the second machine, or set
~DECIDE_HUB~, which wins:

#+begin_src json
{"hub": "me@hub", "hubTimeout": "5s", "machine": "laptop"}
#+end_src

~machine~ is this machine's herdr label on the hub, the same label
agentbus uses; ~DECIDE_MACHINE~ wins over it. An ~ask~ from a herdr
pane needs it: the ask sends this pane as
~DECIDE_AS_HANDLE=herdr:<machine>/<session>/<pane>~. The hub trusts that
handle only when ~SSH_CONNECTION~ is set and the handle names another
machine, as agentbus does. On the hub, the item stores the caller's
pane as ~notifyPane~ when ~--notify-pane~ is not given, and the
caller's machine as ~notifyMachine~ either way, because a bare pane id
names a pane on the machine the command came from. An ~agentbus:~
notify pane gets no machine. An ask on the hub itself stores no
machine, as before.

The client also looks up its tab label and agentbus names, as in
[[*The owner of an ask]], and sends them as ~DECIDE_TAB_LABEL~ and
~DECIDE_BUS_NAMES~ (comma-separated). The hub reads them only with a
trusted ~DECIDE_AS_HANDLE~, so the default owner and the warning work
as they do locally.

The hub then reaches that pane through ~herdr --machine <machine>~: the
built-in compose send (~decide send --id~ and a reply from the inbox)
puts ~--machine <machine>~ after the send template's program, with a
5s deadline, and fails with
~machine <machine> unreachable: host unreachable~ or
~... authentication locked (unlock your SSH/gpg agent)~ as agentbus
does. The notify template reads the machine from ~DECIDE_MACHINE~; see
[[*Notify]].

Then every command except ~help~, ~skill~, ~avatars~, and ~inbox~ runs
as ~ssh -o BatchMode=yes -o ConnectTimeout=<n> <hub> decide <args>~,
with each argument quoted. ~hubTimeout~ is the connect timeout (default 5s).
stdout, stderr, and the exit code come back unchanged, and the local
ledger is never read or created.

~decide --remote <user@host> <command>~ names the hub for one
invocation; it wins over ~DECIDE_HUB~ and the config.

** The inbox in hub mode

~decide inbox~ runs the TUI on this machine against the hub's ledger,
so links open here with the normal opener (~openCommand~, or ~open~ on
macOS and ~xdg-open~ on Linux). No flag is needed. The inbox keeps one
ssh session to the hub, with the same target, options, and deadline as
the CLI, running the hidden ~decide serve --stdio~. That server reads one
JSON request per line, such as ~{"id":3,"op":"answer","item":"D-1","text":"a"}~,
and writes one response per line with the same ~id~. It covers every
call the inbox makes: list, show, mark read, answer (recorded with
~via: ui~), reply, done, archive, withdraw, snooze and unsnooze, the
status board, targets and agentbus names, send, and the owner location.
Ledger writes, notify commands, compose sends, and the status board's
checkout leases all run on the hub with the hub's config, as with the
CLI. The local ledger is never read or created. A hub whose ~decide~
is older than this fails at start and asks to update it.

The inbox lists the hub once a second, off the update loop, so the view
keeps the last good data while a request is in flight. When the hub
stops answering:

- The status line says ~hub unreachable; retrying~ and the view stays.
- The inbox reconnects with a backoff that doubles from one second up
  to 30 seconds. ~hub reconnected~ shows when it is back.
- A write while disconnected fails at once with
  ~hub me@hub unreachable; answer not sent~. Nothing is queued. A write
  cut off by the drop says ~... not confirmed~; look at the item after
  the reconnect.
- A hub that cannot be reached at start fails as the CLI does.

The jump to the owner ([[*Jump to the owner]]) runs herdr here. A pane
the hub stored without a machine is on the hub, so the jump adds
~--machine <hubMachine>~, where ~hubMachine~ in this machine's config is
the hub's label in this machine's herdr:

#+begin_src json
{"hub": "me@hub", "machine": "laptop", "hubMachine": "hub"}
#+end_src

A pane on this machine (~notifyMachine~ equal to ~machine~) needs no
~--machine~, and a pane on a third machine uses that machine's label.
Without ~hubMachine~ the jump says
~owner is on the hub me@hub; set "hubMachine" in the decide config ...~.
When herdr does not know the machine, it says
~owner is on hub; not focusable from here (is hub saved in herdr?)~.

The hub needs an SSH key the agent holds, because ~BatchMode=yes~ never
asks for a passphrase; ~decide~ on its ~PATH~ for a non-interactive ssh
command; and a POSIX login shell (sh, bash, or zsh). The call has a
deadline of twice the connect timeout until the hub's shell starts, so
a locked key cannot hang it. A hub that cannot be reached fails with
~decide: hub me@hub unreachable: host unreachable~ when a one-second
TCP connect to its SSH port fails, or with
~... unreachable: authentication locked (unlock your SSH/gpg agent)~
when the host answers.
