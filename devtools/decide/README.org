#+TITLE: decide

decide is a small inbox for questions that AI coding agents need a human
to answer. An agent runs ~decide ask~ with a question and a few options.
You answer in ~decide inbox~ (a terminal UI) or in Emacs, and decide
notifies the agent's terminal pane with your answer. It also carries
short notes and status between you and your agents, and one inbox can
be shared by two machines.

* Overview

[[https://herdr.dev/][herdr]] is the terminal multiplexer the panes live
in. [[file:../agentbus/README.org][agentbus]] is how a named agent is
reached when the pane is ~agentbus:<name>~. ~decide skill~ prints the
agent rules (~cmd/decide/skill.md~). This file is the human guide.

* Install

#+begin_src sh
go install github.com/jaeyeom/experimental/devtools/decide/cmd/decide@latest
#+end_src

~go install ./devtools/decide/cmd/decide~ is the same from a checkout.
~devtools/setup-dev/ansible/setup-decide.yml~ installs the binary and
the agent skill. ~decide follow~ as a service is manual; see
[[*Getting answers back]].

Config is JSON at ~$XDG_CONFIG_HOME/decide/config.json~, or
=~/.config/decide/config.json= when ~XDG_CONFIG_HOME~ is unset. A
missing file is an empty config.

* Quick start

Inside a [[https://herdr.dev/][herdr]] pane the owner defaults to that
tab's label, and the pane is stored so the answer can be delivered
there. Outside herdr, pass ~--owner~.

#+begin_src sh
decide ask --kind relay --option y:Yes --option n:No --rec y "Merge the release branch?"
#+end_src

The command prints the new id and nothing else. The first item is
~D-001~, then ~D-002~, and so on.

#+begin_src sh
decide inbox
#+end_src

The list is one row per item. The columns are the id, the owner, the
age, the kind, and the latest message:

#+begin_example
>   D-001  review  5m  relay  Merge the release branch?
#+end_example

Enter opens the item. Press ~y~ to pick the Yes option, or answer from
the shell. Answering records the answer and marks the item ~answered~;
it never closes the thread (~done~ stays the owner's step). ~--via ui~
records that a person answered in the inbox or Emacs; a bare ~decide
answer~ records ~cli~.

#+begin_src sh
decide answer --via ui D-001 y
decide show D-001
#+end_src

~decide show~ prints the item. Times are UTC. This sample's owner is
the tab ~review~ and its notify pane is ~w6:pM~:

#+begin_example
id: D-001
question: Merge the release branch?
owner: review
kind: relay
state: answered
freeText: true
unread: false
option: y: Yes recommended
option: n: No
createdAt: 2026-11-15T05:11:55.210872Z
answeredAt: 2026-11-15T05:11:55.511414Z
answer: y: Yes
answeredBy: human
via: ui
notifyPane: w6:pM
message: 2026-11-15T05:11:55.210872Z review Merge the release branch?
message: 2026-11-15T05:11:55.511414Z human y: Yes
#+end_example

~decide show --json D-001~ prints that item as JSON and adds
~ownerLocation~. The answer object is ~value~ ~y~, ~key~ ~y~, ~label~
~Yes~, ~answeredBy~ ~human~, and ~via~ ~ui~. A pane herdr does not list
has ~"state": "closed"~. Unset ~doneAt~ and ~withdrawnAt~ are the zero
time. An empty ~notifyTemplate~ runs nothing. With a template set, the
command's environment has ~DECIDE_ID=D-001~, ~DECIDE_ANSWER=y~,
~DECIDE_ANSWER_LABEL=Yes~, ~DECIDE_OWNER~, and ~DECIDE_PANE~. The full
list is under [[*Getting answers back]].

Close the item when the work is finished:

#+begin_src sh
decide done D-001 "merged"
#+end_src

That prints the item again with ~state: done~ and ~outcome: merged~.

An agent cannot remove an unread item from the user's inbox. When the
item is unread, or an agent message is newer than both ~readAt~
(opening the item in the inbox marks it read) and the user's last
message, ~decide done~ stores
the outcome and the done time, appends ~done: <outcome>~ to the thread,
and sets ~state: done-unread~. The item stays in the inbox, marked
unread, until the user reads and archives it or answers it. The command
prints that on stderr and exits 0. Archiving keeps the agent's outcome.
~decide done --via ui~ is the user's own done from the inbox and Emacs.
It closes the item at once. Agents have no bypass, and ~decide
withdraw~ refuses a done-unread item.

* Concepts

- An *item* is one question or note, id ~D-001~ and up. Its *thread*
  is ~messages~. The ask is the first. ~decide reply~ and ~decide send
  --id~ append. ~decide send --to~ starts a thread.
- The *owner* is who you find the ask by: inside herdr, the pane's tab
  label, unless ~--owner~ is set. A name that matches neither that tab
  nor the pane's agentbus names still files, and asks print a warning
  on stderr.
- *relay* is a choice. It needs at least two ~--option key:label~
  values and ~--rec~ set to one of those keys. Free text is allowed
  unless ~--options-only~ is set or ~optionsOnly~ is true in the config.
  *type-in* is "type this exact text". It needs ~--type-text~ and
  ~--where~.
- *States* are ~open~, ~answered~, ~done~, ~done-unread~, and
  ~withdrawn~. ~done-unread~ is done for the agent but still in the
  user's inbox: ~decide list~ (open) and the inbox show it, and it is
  not counted as the owner's open work. Snoozed is not a state: the
  item keeps its state and is hidden until it wakes.
- The *ledger* is ~ledger.json~ in ~$XDG_STATE_HOME/decide~, or
  =~/.local/state/decide= when ~XDG_STATE_HOME~ is unset. ~status.json~
  in that same directory holds agent and resource rows, separate from
  the ledger.
- The *notify pane* is where the answer is delivered. An ask from a
  herdr pane stores that pane. ~--notify-pane~ wins. A value of
  ~agentbus:<name>~ delivers with ~agentbus send~ instead of a pane
  command.
- A *hub* is a second machine's ssh target. The hub holds the ledger.
  The other machine runs the same commands against it. See
  [[*Using two machines]].
- The *inbox tick* is the reload. A local inbox reloads the ledger every
  250ms. A hub inbox asks the hub once a second and keeps the last good
  view while a request is in flight.

* Asking and answering

~--owner~ names the agent. Inside herdr it defaults to the tab.
~--kind relay~ needs at least two ~--option key:label~ values and
~--rec~. ~--kind type-in~ needs ~--type-text~ and ~--where~.
~--free-text~ allows an answer that is not an option. ~--options-only~
rejects one, and for relay ~--free-text~ wins over that flag and over
~optionsOnly~. ~--deadline~ is RFC3339. ~--link~ repeats. ~--notify-pane~
is a pane id or ~agentbus:<name>~. ~--json~ prints the new item.

~--owner-replies-only~ refuses ~decide reply~ and ~decide send --id~
from anyone but that owner. The sentence is ~item D-123 accepts replies
only from its owner slackwatch; message the owner instead~. A human
reply in the inbox, and any answer, still work. Set it when a tool owns
the thread and parses the answer. Leave it off on an ordinary ask.

~decide list~ prints the id, the deadline or ~-~, the owner, and the
question, tab-separated. ~decide answer~ stores an option key or free
text. ~--via~ is ~ui~ or ~cli~, and the default is ~cli~. ~decide reply~
appends the agent's message and does not deliver it to a pane. On an
open question it keeps the options. ~--option~ replaces them. A plain
reply reopens an answered or done item as a notification you can
archive. A withdrawn item is refused. ~decide send --to~ prints ~sent
to <name> as <id>~. An unknown name exits 2. An empty note sends
nothing. ~decide reassign~ points the item at a new owner or pane when
the owning tab is retired.

Author text stored in the ledger or status board (questions, replies,
option labels, ~done~ outcomes, and status text) must follow inbox shape
rules. The first line is the verdict (at most ~ui.maxFirstLineLength~
characters, 100 by default) and stands alone (followed by a blank line, a
bullet, or the end of the text). No prose paragraph exceeds
~ui.maxParagraphLines~ consecutive non-bullet lines (3 by default), no line
exceeds ~ui.maxLineLength~ characters (160 by default), and the message is
at most ~ui.maxMessageChars~ characters (1200 by default). A line that is
only a URL, a quoted line starting with ~> ~, and a line in a fenced code
block do not count toward line length. Nothing is stored and the exit is 2
when a check fails; the error names each failed check and explains the
expected shape. ~--long-lines~ was removed and no flag skips the checks.
Answers and messages a person gives in the inbox UI are not checked.

For an exact draft or forwarded user text that should be kept as written,
pass ~--verbatim-file <path>~ (or ~--verbatim <text>~) on ~ask~, ~reply~,
or ~send~. It is stored byte for byte in ~verbatim~ without shape checks
and shown in the inbox as a marked quote block ("will be posted as
written"), while the author's own question, reply, or note text around it
is still checked. In ~--json~, verbatim text is in ~messages[].verbatim~
(and the item's ~verbatim~), not in ~text~.

** Item classes

~decide ask~ takes ~--class <name|prefix>~. A single shared counter
numbers every item, and the prefix reflects its class. Every command
accepts any prefix or a bare number (so ~860~, ~D-860~, and ~A-860~
resolve to the same item).

| Prefix | Class      | Meaning                                           | Filing & closing rules                                         |
|--------+------------+---------------------------------------------------+----------------------------------------------------------------|
| ~D~    | ~decision~ | A choice with a reason that guides later choices  | Options + ~--rec~; ~decide done~ requires a 1-2 line outcome   |
| ~A~    | ~approval~ | Yes/no/edit on one exact action or text           | Requires ~--verbatim~ (or ~--verbatim-file~); keys ~yes~/~no~/~edit~; kept forever; optional ~--parent <id>~ |
| ~R~    | ~request~  | The user asks an agent for something              | Tracked to ~done~                                              |
| ~Q~    | ~fact~     | An agent lacks a fact only the user knows         | Answer stored as a plain statement                             |
| ~I~    | ~inbound~  | Someone else wants the user, relayed              | Defaults to ~handle~/~delegate~/~ignore~                       |
| ~T~    | ~task~     | Work only the user can do                         | Tracked to ~done~, with optional ~--deadline~                  |
| ~N~    | ~note~     | FYI, report, or alert                             | No options or answer; closed only with archive                 |

Omitting ~--class~ on ~decide ask~ files a ~decision~ and prints a
deprecation warning on stderr. Setting ~"requireClass": true~ in
config makes a missing ~--class~ an error (exit 2).

~decide retag <id> <class>~ changes an item's class, updates its
display prefix, and records a system event in the thread with the old
and new class.

** Inbox groups, approval cards and backfill

The inbox library arranges open items into four groups, in this order:
approvals (with their parents), other items that need the user
(decisions, facts, tasks; soonest deadline first), requests and inbound,
and notes. An open approval filed with ~--parent~ is nested under that
thread: the parent moves to the approvals group and shows ~approval
waiting~, and the approval has no row of its own. Approvals without a
parent are their own entries. The parent's thread shows the approval
card (the exact text, with yes, no and edit); answering the card answers
the approval, and the parent gets one line, such as ~A-870 approved,
posted 11:40~ or ~A-870 declined~.

Each row has a class badge (the prefix letter) and entries can be
filtered by class (~f~ in the list). ~y~, ~n~ and ~e~ answer an
approval's ~yes~, ~no~ and ~edit~ right from the list, ~E~ archives
open notes in bulk, and notes are not counted as unread.

~decide backfill [--yes]~ is the one-time class backfill. It proposes a
class for every item that is still a decision, by pattern: threads the
user started become requests, "post as written?" items (or items with a
verbatim block) become approvals, and reports with no options and
install reports become notes. Anything uncertain stays a decision. It
prints the batch and applies it only after you answer ~y~ (or pass
~--yes~), retagging each item and recording a retag event on it.

** Decision log

~decide log search <words> [--class decision,fact,...] [--all] [--json]~
looks up what the user already decided. It searches items that have a
user answer or an owner's ~done~ outcome, matching every word against
the question, answer and outcome (case-insensitive). The default classes
are decision and fact; ~--class~ widens or narrows them. Results are
newest first and show id, date, question, answer and outcome. Superseded
items are hidden unless ~--all~ is given. Search never changes anything:
only the user's answers and the owner's ~done~ outcomes make entries.

~decide supersede <old> --by <new>~ marks a newer item as replacing an
older one. Both threads record the link in a system message, and search
shows only the newest item of a chain, with a "supersedes" note.

Agents search the log before filing a decision or fact question, and
cite the id of any precedent they act on.

** Owner and worker

The owner is the agent that filed the item, and it stays the owner
until the item is closed. When another agent takes over the work,
~decide assign <id> <agent>~ records that agent as the item's worker.
The worker is notified at ~agentbus:<agent>~ unless ~--notify-pane~
names another pane. ~decide assign <id> --clear~ removes it. Each change
adds a system message to the thread. A done or withdrawn item is
refused. ~decide show~ prints ~working on it: <agent>~ under the owner,
the inbox header shows ~Working on it~, and ~show --json~ and ~list
--json~ carry ~worker~, ~workerNotifyPane~, and ~workerNotifyMachine~.

A human reply still goes to the owner. On an item whose worker is not
the owner, ~decide send --id~ warns on stderr, for example ~This reply
goes to ada (owner); bea is working on it.~, and notifies the owner as
before. ~--to worker~ notifies only the worker, ~--to both~ notifies
both, and ~--to owner~ notifies the owner without the warning. ~--to
worker~ or ~--to both~ on an item without such a worker is refused.
The inbox shows the same warning when you send a reply there and asks:
~w~ sends to the worker, ~b~ to both, ~o~ to the owner only, and ~Esc~
keeps the draft. An item without a worker behaves as before.

~decide snooze~ takes ~2h30m~, ~HH:MM~ (today, or tomorrow once that
time has passed), ~YYYY-MM-DD HH:MM~, or ~mon 9:00~, in local time. A
clock time may be the next argument, as in ~decide snooze D-001 mon
9:00~. A done or withdrawn item is refused. ~show~ prints ~snoozed
until:~.

An answer's ~via~ is ~ui~ when a person answered in the inbox or Emacs,
and ~cli~ when ~decide answer~ or ~decide send --id~ recorded it. ~by~
on a message is who ran ~decide reply~ or ~decide send --id~: their
agentbus name, else their herdr tab, else their pane. The rules are in
[[file:docs/provenance.org][docs/provenance.org]].

* The inbox

~decide inbox~ is the terminal UI. ~--utc~, or ~"ui": {"utc": true}~ in
this machine's config, shows stamps in UTC. Otherwise times follow the
machine running the inbox, including in hub mode. ~show~ and the ledger
stay UTC. ~--remote user@host~ and ~--snoozed~ are the other flags.

The inbox draws at once and loads the ledger in the background, locally
and from a hub. Until the first list arrives, the list is empty and the
status line says ~Loading…~. Quit, help, compose, and the folder keys
work meanwhile. A failed first list shows its error on the status line
and is retried on the next tick.

The sidebar folders are Inbox, Snoozed, Answered, Done, Withdrawn, then
Status and Contacts. ~g~ waits for a second key. Esc cancels the chord.
Any other second key says ~unknown go-to key~.

The copy menu is ~m~ message, ~q~ question, ~t~ thread, ~i~ id, ~a~
answer, and Esc. The status line says ~copied message (312 chars)~,
with no borders or ANSI codes. ~ui.clipboard~ is ~auto~ (OSC 52, plus
~pbcopy~, ~wl-copy~, or ~xclip~), ~osc52~, ~command~, or ~off~. OSC 52
stops above 100 KB. In the avatar picker, ~h~ ~j~ ~k~ ~l~ or the arrows
move, Enter saves, and Esc cancels. Mouse behavior is under
[[*Customizing]].

The reply box is pinned to the bottom of the item pane outside the
scrolling thread, so scrolling the thread never jumps back to the box.
When unfocused and empty it collapses to one hint line (~reply: ___~);
when focused or holding a draft it grows with the text up to the cap,
shrinking the thread area above it, and keeps the action buttons at the
bottom: ~[Send ^⏎]~, ~[Send and archive M-e]~ (shown on notes,
notifications, and already-answered threads, never on an open question),
and ~[Discard M-d]~. ~Discard~ clears a short draft at once and asks
first when the draft is longer than 3 lines; ~Esc~ leaves the box and
keeps the draft.

** Persistent drafts

Unsent reply, free-text answer, and compose drafts are saved to
=drafts.json= alongside =ledger.json= (in =$XDG_STATE_HOME/decide/= or
=~/.local/state/decide/=). In hub mode, =drafts.json= lives on the hub
and syncs across hub clients through the ~watch~ stream and each
client's local replica, so a draft started on one machine appears on
another.

- *List mark and compose restore*: threads with a saved reply or answer
  draft show a ~draft~ mark in the list, or ~draft!~ when an unresolved
  conflict exists. Opening compose (~c~) when a saved compose draft
  exists shows a ~[r] Restore~ / ~[d] Discard~ prompt; forwarding (~f~)
  does not overwrite that saved draft.
- *Save timing and cleanup*: drafts auto-save 1.5s after typing stops
  (and when changing the compose recipient while text is non-empty),
  flush immediately when leaving a thread or compose view or exiting the
  inbox, and flush before suspending for ~$EDITOR~ (~C-x C-e~ / ~C-g~)
  and save on return. Sending (~Ctrl+Enter~, ~Alt+Enter~, ~C-s~, or
  ~Alt+e~), discarding (~Alt+d~), or clearing text to empty or
  whitespace deletes the draft immediately.
- *GUI emacsclient*: an ~emacsclient~ editor with none of ~-t~, ~-nw~,
  ~-c~ gets no terminal on stdin, so it opens the draft in the running
  Emacs instead of a text frame on the inbox's terminal.
- *Conflicts*: drafts use optimistic concurrency (~baseRev~) so
  concurrent edits from two clients never silently overwrite each other.
  Both versions are preserved, the list shows ~draft!~, and opening the
  draft shows a conflict banner with ~[k] Keep current~, ~[u] Use
  other~, and ~[m] Merge both~ (inserting git-style conflict markers).
- *Limits and lifecycle*: draft text is capped at 64 KiB (oversized
  saves warn on the status line while keeping the in-memory text) and at
  most 10 conflict copies per draft. Reply and answer drafts are deleted
  automatically when the thread is archived, marked done, withdrawn, or
  deleted.

Design details, RPC ops, and replica behavior are in
[[file:docs/drafts.org][docs/drafts.org]].

~ui.answerAction~ controls what picking an option (~1~-~9~ or click)
does: ~stay~ (default) sends the answer and stays in the thread; ~list~
sends and goes back to the list; ~edit~ puts the option's text into the
reply box so you can add text before sending, recording the option key
as the answer and posting the added text as a human message right after
it. Answering never closes a thread.

~ui.openAt~ chooses where a thread opens: ~new~ (default) scrolls so the
first message newer than the item's previous read time is at the top, with
a divider line above it, ~── new since 14:05 ──~ (a stamp like the others).
With nothing new it opens at the last message, and a thread never read
opens at the top. ~last~ and ~top~ always open there. ~Home~ and ~g~ still
go to the top, and ~n~ / ~p~ are unchanged; the current-message marker
starts on the opened message. Messages that are newer but not shown at
open still hold archive. An unknown value is a config error.

Archive waits while a message is unseen or newer than ~ui.archiveGrace~
(default 2s). The status line says ~new message: not archived~. Pending
options still need an answer. ~decide done --via ui~ does not check
that grace.
Snooze offers ~1h~, ~3h~, ~tomorrow 9:00~, ~next Monday 9:00~, or a
custom time. The item stays out of every folder but Snoozed until that
time, or until a message lands, and then it is unread.

~l~ opens the only link, or a numbered picker. A digit opens one of the
first nine; with more links, type the number and press Enter. The
opener is ~openCommand~ (default ~xdg-open~, or ~open~ on macOS). The
URL is the last argument and no shell runs. The limit is 5 seconds.
URLs are OSC 8 hyperlinks unless ~hyperlinks~ is false. Mouse capture
is on by default. ~Ctrl~ click opens a URL. ~M~ gives clicks to the
terminal.

The ~Owner:~ line is the herdr workspace, tab, and pane. ~o~ runs
~herdr workspace focus~ and then ~herdr tab focus~, and does not answer.
Each lookup has a 5s deadline, and the inbox does not wait. ~show
--json~ adds ~ownerLocation~ (~machine~, ~workspace~, ~tab~, ~pane~,
~state~ of ~live~, ~closed~, ~unknown~, or ~unreachable~). Ctrl+Enter
and ~DECIDE_KEYDEBUG~ are in [[file:docs/keys.org][docs/keys.org]].

* Notes and status

~decide send --to <name> "<text>"~ starts a thread. ~decide send --to~ and
~decide send --id~ also accept ~--verbatim <text>~ and ~--verbatim-file
<path>~ (alone, without positional text, ~--text-file~, or stdin, or
alongside short author text). A configured target
uses ~sendTemplate~, which defaults to ~herdr agent prompt {pane}~ with
the note as its own argument. ~{pane}~ is replaced. The note is not
interpolated into a shell. With ~"recipients": {"agentbus": true}~,
~--to~ also accepts a name from ~agentbus list~, and the note goes
through ~agentbus send~. ~--via~ defaults to ~cli~.

The compose dropdown has at most eight rows and filters as you type.
Bus names load in the background, at start and every 30 seconds, so
compose does not wait. ~recipientsTimeout~ bounds a load (default 3s).
Dead names come last. A slow load says ~agentbus: slow (>3s)~. A failure
says ~agentbus: unavailable~ and keeps the last good names.

While the bus cannot deliver, the inbox's top line says ~Bus down:
messages to agents are waiting.~, then the first problem, dimmed and
cut to the screen width. The inbox runs ~agentbus health --json~ in the
background every ~ui.busHealthInterval~ (default 15s), and the line
goes on the first check after the bus recovers. A check that is slow
(over 5s), or an agentbus that is missing or has no ~health~, shows no
line and is logged once at debug level. In hub mode the check runs on
the hub, where agent messages are sent.

While that line is up, sending a reply or a compose note to an agent
on the bus (a bus name, or a pane that starts with ~agentbus:~) first
asks ~The bus is down. This message will wait until it's fixed.~ with
~[Send anyway]~ focused and ~Cancel~. Enter picks the focused choice,
Tab moves the focus, ~y~ sends, and ~n~ or Esc cancels. Cancel keeps the
draft. The prompt uses the last background check and runs none of its
own. A local pane target sends without asking.

~decide status~ uses ~status.json~. ~set --agent~ writes one row. A new
row with no ~--state~ is ~working~, and a later set keeps the state.
~list~ prints name, state, age, and text. A row older than five minutes
is dim. ~set --resource <name> free|busy~ writes a shared flag. ~clear~
removes one row or one flag. ~checkouts~ maps a resource name to a
checkout path and shows that path's agentbus lease (~free~, ~held by
<name> until 14:20~, ~paused by user~, ~needs adopt~, plus ~, <n>
queued~), or the stored row with ~(guess)~. The choice is in
[[file:docs/leases.org][docs/leases.org]].

* Getting answers back

After a relay answer is saved, ~notifyTemplate~ runs as a shell command
for a pane on this machine. Nothing is written into the command string.
An empty template runs nothing. There is no default notify command.
~{id}~, ~{answer}~, ~{owner}~, and ~{pane}~ are not substituted.

The environment is how a template reads the answer:

- ~DECIDE_ID~ is the item id.
- ~DECIDE_ANSWER~ is the saved answer. An option answer is the option key.
- ~DECIDE_ANSWER_LABEL~ is the label that option had when it was picked.
  It is empty for free text.
- ~DECIDE_OWNER~ is the item owner.
- ~DECIDE_WORKER~ is the agent ~decide assign~ recorded, or empty.
- ~DECIDE_PANE~ is the notify pane. The item's pane overrides the config.
- ~DECIDE_KIND~ is ~relay~ or ~type-in~.
- ~DECIDE_QUESTION~ is the first line of the question, at most 200
  characters. A character is not split.
- ~DECIDE_ANSWERED_AT~ is ~answeredAt~ in RFC3339.
- ~DECIDE_ANSWERED_BY~ is the stored ~answeredBy~, for example ~human~.
- ~DECIDE_THREAD_HEADER~ is one line such as ~[decide D-123 from human]~.
- ~DECIDE_REPLY_HINT~ is one line telling the agent to ~decide reply~ in
  the thread and to ~decide done~ when finished.
- ~DECIDE_MACHINE~ is empty. The template runs only for a local pane.
- ~DECIDE_DELIVERY_KEY~ is ~<id>:<answeredAt>~. Retries of the same
  answer reuse it.

A pane on another herdr machine does not run ~notifyTemplate~. Decide
sends the header, the answer, and the reply hint with the compose
command and ~--machine~. An ~agentbus:<name>~ pane uses ~agentbus send
--client-id <key>~ with the same ~DECIDE_DELIVERY_KEY~. ~held~ or
~queued~ is ~waiting~ and is not retried. Any other failure
is stored as ~notifyError~ until a later delivery works. Each attempt is
a ~delivery~ entry (~at~, ~target~, ~outcome~, ~error~). The inbox shows
~not delivered~ when the latest attempt failed.

** Delivery marks

Every message you send to an agent gets a ~delivery~ entry: an answer, a
reply (~decide send --id~ or ~0~ in the inbox), and the first note of a
new thread. The entry names the message (~message~, its time), keeps the
agentbus message id that ~agentbus send~ printed (~busId~), and has one
of three outcomes. The thread view shows it after the message header:

- ~waiting~ means agentbus stored the message and has not delivered it.
  The reason follows when agentbus gives one: ~waiting: bus down~ (the
  transport is unreachable), ~waiting: target composer busy~, or another
  agentbus ~held_reason~. A waiting message is never shown as delivered.
- ~delivered 14:05~ is when the target got it. ~, 7 min late~ follows
  when it waited first. A waiting message that is then delivered also
  adds one system note to the thread when the wait reaches
  ~ui.lateDeliveryAfter~ (five minutes by default), at the delivery time:
  ~delivered late: 7 min~. A shorter wait adds no note. The note stays
  in the thread: it is not sent to the agent and does not mark the item
  unread. A message delivered at once adds no note.
- ~failed: <error>~ is a send that failed, or a wake agentbus is still
  retrying.

After a bus message waits past the threshold, the item gets one
~not delivered yet (N min) to <recipient>~ marker in the list and thread.
It becomes unread and is tagged ~undelivered~; delivery clears the marker.
A failed delivery gets ~not delivered: <reason>~. Search for either
marker in the inbox, or run ~decide list --undelivered~. The marker is
added once, even while the inbox refreshes.

While any message waits, or failed while agentbus retries it, the inbox
checks them every 10s with one ~agentbus status --json <id>...~ call. It
does not check when nothing waits. In hub mode the check runs on the hub
(protocol version 8). A pane reached by the send template is delivered
when the command succeeds and is never waiting. A ~delivered (queued)~
entry written by an older decide reads as ~waiting~; the check asks
agentbus about it by its client id, ~<id>:<answeredAt>~. ~decide show~
prints each entry as ~delivery: <at> <target> <state> <busId>~.

A failure is retried on the ledger machine after 5s, then after 20s,
then it stops. Three attempts is the cap. An answer the owner has not
taken up is followed up once, after ~ui.staleAnswerAfter~ (30 minutes
when unset), unless the owner replied, the item was marked read, or
someone ran ~decide done~. Opening the item marks it read. The check
runs on the ledger machine: an open local inbox, the hub's ~decide
serve --stdio~ once a minute, and ~decide follow~. A hub client does
not run it. A gone pane, or a live pane with no agent, is marked ~owner
gone~ and nothing is re-sent. An agent with ~agent_status~ ~blocked~ is
marked ~owner waiting on a dialog~. Otherwise the same key is sent once
more.

~decide follow~ runs that loop every minute until SIGINT or SIGTERM.
~--every 5m~ changes the interval. ~--once~ is a single pass, for cron.
Run it on the machine that holds the ledger. A parent value of the same
environment name does not win. The systemd unit and the launchd agent
are in [[file:docs/follow.org][docs/follow.org]]. The service needs
~decide~, the notify command, and herdr on ~PATH~.

** Outbox, Answered, delivery marks, and Done

Four distinct stages track a write from your keyboard to the agent:

- *Outbox* (hub mode only): the local queue on the client machine
  (~$XDG_CACHE_HOME/decide/outbox~) that accepts writes immediately so
  the UI never blocks on a slow or disconnected hub. A thread shows
  ~in outbox~ on pending messages, and the *Outbox* folder (~g~ then
  ~o~) lists all pending, held, and failed entries. A pending entry can
  be edited (~e~) or cancelled (~x~). If the item changed on the hub
  before delivery (a new message arrived, or the item was withdrawn,
  marked done, or already answered), the entry is held and offers
  ~[s] send~, ~[e] edit~, or ~[x] cancel~. A permanent error marks the
  entry ~failed: <reason>~ in red and restores its text to the composer.
- *Answered*: the ledger on the hub (or local machine) recorded your
  answer (~state: answered~, ~via: ui~, and for outbox entries both
  ~writtenAt~ and ~receivedAt~). The entry leaves the outbox and the
  inbox begins notifying the agent.
- *Delivery mark*: whether the agent's transport (~agentbus~ or pane
  command) actually received the message (~waiting~, ~delivered HH:MM~,
  or ~failed: <error>~).
- *Done*: the item is closed (~state: done~, or ~done-unread~ if an
  agent closed it while unread), either by the agent (~decide done~) or
  by you (~d~ or archive ~e~ / ~y~). Archive from the outbox still
  checks against the last message time seen when the entry was written.

* Emacs

~devtools/decide/emacs/decide.el~ is a plain Emacs frontend. Load it and

* Using two machines

One machine, the hub, holds the ledger. On the other machine set ~hub~,
or ~DECIDE_HUB~, which wins:

#+begin_src json
{"hub": "me@hub", "hubTimeout": "5s", "machine": "laptop", "hubMachine": "hub"}
#+end_src

~machine~ is this machine's herdr label as the hub knows it.
~DECIDE_MACHINE~ wins. An ask from a herdr pane sends
~DECIDE_AS_HANDLE=herdr:<machine>/<session>/<pane>~. The hub trusts that
handle only when ~SSH_CONNECTION~ is set and the handle names another
machine. It then stores the caller's pane as ~notifyPane~ and the
caller's machine as ~notifyMachine~.

Every command except ~help~, ~skill~, ~avatars~, and ~inbox~ runs over
~ssh -T -o BatchMode=yes~. ~--remote user@host~ wins for one invocation.
The local ledger is never created. Ssh runs in its own session with no
terminal, so it never reads the terminal or gets its signals.

~decide inbox~ draws here and keeps one ssh session to ~decide serve
--stdio~ on the hub. On connect it syncs an on-disk replica under the
user cache directory (~$XDG_CACHE_HOME/decide/replicas~, or the platform
cache directory, one file per hub) from its last sequence number using
the ~watch~ protocol op, and the hub pushes subsequent ledger and status
changes in monotonic sequence order. Any sequence gap or unknown
sequence triggers a full resync. Reads (open, scroll, search, contacts,
and the status page) render from the replica without waiting on the hub,
and ~mark-read~ is sent in the background and retried on failure without
showing an error. Writes (~answer~, ~reply~, ~done~, ~archive~, ~snooze~,
~unsnooze~, ~send~, and settings) append to an on-disk outbox per hub
(~$XDG_CACHE_HOME/decide/outbox~) so the UI returns at once, and a
background sender drains them in order (surviving quit and crash,
holding on conflict, and warning after ~ui.outboxStaleAfter~). The status
line shows freshness
(~synced 12s ago~, or ~hub unreachable; showing copy from 14:05~ while
disconnected) and the inbox backs off from one second to 30. Links
still open here.
~hubMachine~ lets ~o~ focus a pane on the hub. The external editor
(~C-x C-e~ or ~C-g~ in a compose box) returns as soon as it exits, even
while the hub is slow or reconnecting; its temp draft is removed after
an editor error and when the inbox exits with the editor open.

Display keys come from the hub, and a key set locally wins: ~avatars~,
~avatarDefault~, ~avatarMono~, ~recipients~, ~recipientsTimeout~,
~targets~, ~hyperlinks~, ~hiddenContacts~, ~favoriteContacts~,
~contactAliases~, ~ui.orgTree~. ~hub~, ~machine~, ~openCommand~, ~checkouts~, ~ui~ (other than ~ui.orgTree~),
and the templates stay local. ~decide config show --effective~ prints each key, ~local~ or
~hub~, and the value, tab-separated.

The hub needs a ~BatchMode=yes~ key, ~decide~ on ~PATH~, and a POSIX
login shell. Failure starts with ~decide: hub me@hub unreachable~.

* Who may open items

In a multi-agent setup, only a few lead agents report directly to the
user; everyone else should ask its manager instead of opening a new
inbox item. ~owners~ configures who may open items via ~decide ask~ and
~decide send --to~:

#+begin_src json
{
  "owners": {
    "mode": "warn",
    "allowed": ["lead/*"],
    "managers": {
      "team/*": "lead/planner"
    }
  }
}
#+end_src

~allowed~ lists owner names or ~path.Match~ globs (~*~ matches within a
segment, not across ~/~). ~managers~ optionally maps an owner pattern to
the manager named in warning and error messages (most specific pattern
wins). When ~mode~ is ~warn~ or ~enforce~, ~allowed~ must be non-empty.

- ~off~ (the default): every owner may open items.
- ~warn~: non-allowed owners still open the item, get a warning on
  stderr (~decide: owner <name> is not a direct report; ask <manager>
  instead~), and the item is tagged ~off-line~.
- ~enforce~: non-allowed owners get the same message on stderr, nothing
  is opened, and ~decide~ exits with status 3.

Replies on existing items (~decide reply~, ~decide send --id~) and items
opened from the UI (~--via ui~, such as the inbox or Emacs) are always
allowed.

Run ~decide list --off-line~ (with optional ~--json~) for health checks
to find items tagged ~off-line~ under ~warn~ mode. For hub-mode clients,
the hub's ~owners~ config decides (and overrides any local ~owners~
setting).

Non-goals: ~owners~ does not change tool-approval flows or touch Claude
settings.

* Customizing

Avatars are optional 10x6 figures beside an item header and beside the
compose recipient. An exact ~match~ wins, then the first glob. ~file~
may start with =~/=. A PNG or WEBP is drawn as characters. Any other
file is text. ~builtin~ names a shipped figure. Both in one rule is an
error. ~"hide": true~ shows nothing.

#+begin_src json
{"avatars": [{"match": "pm-*", "builtin": "owl"}], "avatarDefault": true}
#+end_src

~avatarDefault~ is off until you set it. The same name always gets the
same figure. ~decide avatars list~ previews them. ~--name~ shows one
name's figure, and ~--ids~ prints the ids. ~decide avatars set ops/x
owl~ saves a name. ~default~ drops that exact rule. ~none~ hides it.
~--local~ writes this machine even in hub mode. Otherwise a hub-mode
set saves on the hub. ~A~ opens the picker. With mouse capture on, a
click on a cell saves it, a click outside the picker or on its border
cancels, and the wheel moves one row. The id list, the hash, and the
config write are in [[file:docs/avatars.org][docs/avatars.org]].

Contacts (~g~ then ~c~) lists ~agentbus list~ names plus every owner
and sender. ~human~ and ~system~ are not contacts. ~active~ is alive,
~unresponsive~ is registered but not answering, and ~dead~ is gone or
known only from the ledger. ~x~ hides a row until it is active again.
~H~ shows hidden rows for this session. ~X~ hides every dead contact
after a confirm. ~R~ runs ~agentbus release~ for a name the bus lists
as dead. ~a~ stores a ~contactAliases~ entry. ~*~ stars a contact, here or in
the compose recipient list: starred names come first in that list,
marked ~★~, in the order they were starred, and are not repeated
below. A starred name that is not live still shows there, marked dead.
Hidden and starred do not conflict: the name stays hidden in Contacts
and is still listed first when composing. ~decide contacts prune
--dead~ prints names and writes nothing unless ~--yes~. ~--release~
also releases those bus names.

The list starts with the name. A panel shows the contact under the
cursor in full: its avatar as the thread shows it, its state, its
liveness and when agentbus last saw it, its whole ~when~ text, its
open, answered, done, and withdrawn item counts, its last activity, and
how many messages to it are still waiting or failed to deliver. On a
wide screen the panel is to the right of the list. Below 80 columns it
is hidden; ~i~ shows it below the list and hides it again, and the
footer names the key.

With ~ui.orgTree~ on, ~t~ switches Contacts between the list and the
org tree from ~orgctl tree --json~ on ~ui.orgSpec~: you, then direct
reports, then their reports, with each pool under the role that starts
it. Roles with no contact and pools are dimmed and cannot be selected.
Contacts the spec does not name are in an ~other~ group at the bottom.
If ~orgctl~ is missing or fails, the list stays flat with one line
saying why. With ~ui.orgTree~ off, decide never runs ~orgctl~. On a hub
client, ~orgctl~ and ~ui.orgSpec~ stay on the hub: the hub's ~ui.orgTree~
becomes the default (a local ~ui.orgTree: false~ still turns it off),
and the client caches the tree in its local replica, refreshing on
connect and when the hub's spec mtime changes. An older hub without

* Troubleshooting

~DECIDE_KEYDEBUG=/tmp/decide-keys.log decide inbox~ logs each key.
~1~ uses ~decide-keys.log~ in the temp directory. Ctrl+Enter is
recognized only as the two sequences in
[[file:docs/keys.org][docs/keys.org]]. A terminal that sends it as Enter
gets Enter. A config that does not parse is left unchanged. Avatar and
contact writes touch only their own key, and the first write in a
process copies the file to ~config.json.bak~.
