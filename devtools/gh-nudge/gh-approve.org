This page is the rules, the dry run, and the audit log.

* gh-approve

~gh-approve~ approves pull requests that match rules you write in config, or
hands them off to a colleague (see [[*Hand-off rules][Hand-off rules]]). It
acts as the logged-in ~gh~ user, through the ~gh~ CLI. It leaves every other
pull request for a human. It runs no LLM review itself, but a rule can
run a command of yours as a last check. See [[*Agent command][Agent command]].

It looks only at open pull requests that request you *as an individual*. It
finds them with the search ~user-review-requested:@me~. It ignores a pull
request that requests only a team you belong to, unless a rule sets
~requested_via_team~. See [[*Approve for your own files][Approve for your own files]].

#+begin_src shell
  # Dry run (the default): print what would be approved. Nothing is approved.
  gh-approve

  # Approve for real
  gh-approve --apply

  # Evaluate one pull request and print every condition with the value it saw
  gh-approve --pr acme/widgets#12 --explain
  gh-approve --pr https://github.com/acme/widgets/pull/12

  # Keep colors when relaying the output to a terminal
  gh-approve --color=always

  # Run without the per-commit PR facts cache
  gh-approve --no-cache

  # Bound concurrent uncached PR loads (default 4)
  gh-approve --load-concurrency 4

  # Run agent commands without the decision cache
  gh-approve --no-agent-cache

  # Stop starting pull requests after five minutes; the current one finishes
  gh-approve --max-duration 5m

  # Recent decisions. --action defaults to approved. --days defaults to 7.
  gh-approve history
  gh-approve history --days 30 --action all --rule dashboard --json
  gh-approve history --no-state --no-links

  # Open a pull request in the browser (or print its URL with --print)
  gh-approve open 12
  gh-approve open acme/widgets#12
  gh-approve open --print https://github.com/acme/widgets/pull/12/files
#+end_src

One starter rule, in the ~approve~ section of ~config.pkl~. ~gh-approve~
prints the plan and changes nothing until ~--apply~.

#+begin_src pkl
approve {
  rules {
    new {
      name = "docs"
      paths_all_match { "docs/**" }
      checks = "green"
    }
  }
}
#+end_src


The output is a table with the status, the pull request, the action, the
matched rule, and the title. When no rule matches, the rule column shows
~manual~. Then, for each rule, it shows the first condition that failed.

The status is a marker and a word for the outcome group: ✅ approved, 🤝
handed off, 👀 left for you (~manual~, ~mark_viewed~), ⏭️ skipped, or ❌
error. A dry-run action adds ~(dry run)~. Rows print as each pull request is
evaluated. At the end, a summary lists the pull requests in each non-empty
group with a count: left for you, approved, handed off, errors, then skipped.
Each line has the title and the first reason from its row.

#+begin_example
STATUS                    PR                               ACTION             RULE                 TITLE
✅ approved (dry run)     acme/widgets#1                   would_approve      dashboard            Tidy dashboard
👀 left for you           acme/widgets#2                   manual             manual               Bump infra
    dashboard: paths_all_match failed (outside globs: infra/main.tf)

👀 Left for you (1)
  acme/widgets#2  Bump infra - dashboard: paths_all_match failed (outside globs: infra/main.tf)

✅ Approved (1)
  acme/widgets#1  Tidy dashboard (dry run)
#+end_example

The marker and word are colored: green approved, cyan handed off, yellow left
for you, dim skipped, red error. ~--color=auto~, the default, colors only
when stdout is a terminal. ~--color=never~ turns color off, and so does a
non-empty ~NO_COLOR~. ~--color=always~ colors even through a pipe, for a
caller that relays the output to a terminal. The audit log never has colors
or markers.

The search includes labels, draft state, author, changed-file count, additions,
and deletions. When every rule that can match a team request requires labels,
gh-approve adds those labels to the GitHub search query. Different required
label sets use separate queries, and duplicate pull requests are merged.
Rules that do not require labels keep the unfiltered team search. Before it
loads a pull request's full metadata, gh-approve checks labels, draft state,
author, and size limits from the search result. Candidates that fail every
rule are skipped, with the failed conditions still shown by ~--explain~.

The pass summary reports candidate, cheaply skipped, and fully loaded counts
with elapsed time. ~--max-duration~ stops new pull requests from starting;
the pull request already in progress finishes, then the usual summary reports
how many candidates were left unevaluated. Set ~approve.max_duration~ in
config to apply the limit without a command-line flag. The default is no limit.

** Rules

Add rules to the ~approve~ section of ~config.pkl~. The conditions in one rule
are ANDed. Rules are ORed, and the first rule that matches is used. Every
condition is optional. An empty list or an unset limit adds no condition.

| Condition                | Meaning                                                                           |
|--------------------------+-----------------------------------------------------------------------------------|
| ~repos~                  | Repositories as ~owner/name~ or globs, such as ~acme/*~                           |
| ~paths_all_match~        | Globs. Every changed file must match one of them                                  |
| ~paths_none_match~       | Globs. No changed file may match any of them, such as CI config, infra, lockfiles |
| ~paths_any_match~        | Globs. At least one changed file must match one of them                           |
| ~codeowners_covered~     | Default ~false~. Every changed file must pass the CODEOWNERS coverage check       |
| ~codeowners_none_mine~   | Default ~false~. No changed file may be owned by you or any team you belong to    |
| ~max_changed_lines~      | Maximum added plus deleted lines                                                  |
| ~max_added_lines~        | Maximum added lines                                                               |
| ~max_files~              | Maximum changed files                                                             |
| ~pure_deletion~          | The pull request adds no lines                                                    |
| ~deletions_and_comments_only~ | Default ~false~. At least one line is deleted, and every added line is blank or a comment |
| ~authors_allow~          | The author must be one of these logins                                            |
| ~authors_deny~           | The author must not be one of these logins                                        |
| ~labels_required~        | Every one of these labels must be present                                         |
| ~labels_forbidden~       | None of these labels may be present                                               |
| ~required_approvals_by~  | Each login's latest review on the current head SHA must be ~APPROVED~             |
| ~checks~                 | ~"green"~ or ~"allow_pending"~. See below                                         |
| ~not_draft~              | Default ~true~. A draft does not match                                            |
| ~max_unresolved_threads~ | Default ~0~                                                                       |
| ~agent_command~          | A command, as argv, that must print ~approve~. Runs last. See below               |
| ~agent_timeout~          | Default ~120.s~. How long ~agent_command~ may run                                 |
| ~agent_cache~            | Default ~true~. ~false~ runs ~agent_command~ every time, without the cache        |
| ~requested_via_team~     | Default ~false~. Also run when you are requested only through a team of yours     |
| ~mine_comments_only~     | Default ~false~. Your CODEOWNERS files change only comments or blank lines        |
| ~body~                   | Approval body for this rule, overriding the global ~body~. See below              |
| ~file_checks~            | Map from glob pattern to built-in check or script. See below                      |
| ~file_checks_timeout~    | Default ~30.s~. How long a ~file_checks~ script may run                           |
| ~mark_viewed_on_pass~    | Default ~true~. Mark files whose ~file_checks~ check returns ~approve~ as viewed  |

Globs use ~**~ for any number of directories. Logins match without regard to
case. Labels match exactly, including case. For ~required_approvals_by~, a
~COMMENTED~ review does not replace an earlier approval on the same head.

~checks = "green"~ requires that no check failed and every required check
passed. When the head has no required check, every check counts as required.
~checks = "allow_pending"~ requires only that no check failed. A failed check
always fails.

Comment markers for ~deletions_and_comments_only~ are under
[[*Comment markers][Comment markers]].

Global settings:

- ~body~ is the approval body. Default ~LGTM~. The matching rule name is
  appended as ~<!-- gh-approve: <rule> -->~. A rule's own ~body~ overrides it.
- ~skip_already_approved~ skips a pull request you already approved at the
  current head. Default ~true~.
- ~skip_open_change_requests~ skips any pull request with an open
  ~CHANGES_REQUESTED~ review from any reviewer — including your own earlier
  change request — even when posted on an older commit. A dismissed change
  request or one followed by a later ~APPROVED~ review from the same reviewer
  does not block; ~COMMENTED~ and ~PENDING~ reviews do not clear or count as a
  change request. When enabled, this check applies to every rule (including
  comment-only and deletion rules). Default ~false~ (off by default); set
  ~skip_open_change_requests = true~ in ~approve~ to turn it on.
- ~agent_cache_ttl~ is how long a cached ~agent_command~ decision is reused.
  Default ~7.d~.
- ~agent_cache_max_mb~ bounds the ~agent_command~ decision cache. Default ~50~.
  See [[*Agent decision cache][Agent decision cache]].
- ~load_concurrency~ bounds concurrent uncached PR loads. Default ~4~.
- ~pr_cache_ttl~ is how long per-commit PR facts are kept after a PR leaves
  the candidate list. Default ~7.d~.
- gh-approve never approves a pull request you authored. This is always on and
  cannot be configured.

Starter rule shapes. These are examples. Nothing is hard-coded.

#+begin_src pkl
  approve {
    rules {
      // Only files under one internal dashboard directory.
      new {
        name = "internal-dashboard"
        paths_all_match { "tools/internal-dashboard/**" }
        checks = "green"
      }
      // Pure deletions.
      new {
        name = "pure-deletion"
        pure_deletion = true
        checks = "green"
      }
      // Deletions whose added lines are only comments or blank.
      new {
        name = "comment-cleanup"
        deletions_and_comments_only = true
        checks = "green"
      }
      // At most 50 changed lines outside CI and infra paths.
      new {
        name = "small-outside-infra"
        max_changed_lines = 50
        paths_none_match { ".github/**"; "infra/**"; "**/*.lock"; "**/go.sum" }
        checks = "green"
      }
      // Small pull requests, up to 200 lines, that carry an "internal-only" label.
      new {
        name = "internal-only"
        max_changed_lines = 200
        labels_required { "internal-only" }
        checks = "allow_pending"
      }
    }
  }
#+end_src

The ~approve~ section is supported only in Pkl config. A YAML config that has
an ~approve~ key fails to load.

** Hand-off rules

Sometimes you are asked to review a pull request only because it touches a
directory that a colleague also owns. A hand-off rule passes such a pull
request to the colleague: it requests the colleague's review, then removes you
as an individual requested reviewer. A hand-off *never approves anything*. The
scope is the same as for approve rules: only pull requests that request you as
an individual, and never your own.

#+begin_src pkl
  new {
    name = "dashboard-handoff"
    action = "handoff"
    reviewers { "colleague" }
    paths_any_match { "tools/dashboard/**" }
    authors_deny { "colleague" }
    codeowners_covered = true
  }
#+end_src

- ~action~ is ~"approve"~ (the default) or ~"handoff"~.
- ~reviewers~ are the logins to request. It is required on a hand-off rule and
  not allowed on an approve rule.
- Every other condition works as for approve rules and is ANDed.

*Coverage check.* With ~codeowners_covered = true~, every changed file must
meet one of these:

1. It matches the rule's ~paths_any_match~, the area the colleague takes over.
2. Its owners include neither you nor a team you belong to.
3. Every owning team that includes you also has other members *and* is a
   requested reviewer on the pull request. You are not an owner by name.

Owners come from the base branch's CODEOWNERS (=.github/=, the root, or
=docs/=, the first found), parsed with the same code as ~gh-codeowners~. If
CODEOWNERS or a team's members cannot be read, the check fails; it never
assumes a pass. Reading team members needs the ~read:org~ scope. An email
owner fails the check, since gh-approve cannot tell whether it is you.
~--explain~ prints the verdict for each file and the owner that blocked it.

*Strict no-ownership check.* With ~codeowners_none_mine = true~, every changed
file's CODEOWNERS owners must include neither you nor any team you belong to:

- There is no exception for teams with other members or for requested
  reviewers, and no ~paths_any_match~ escape.
- Owners use the same base-branch CODEOWNERS lookup order and fail closed when
  CODEOWNERS or team membership cannot be read, or when an email owner is
  present.
- Setting ~codeowners_none_mine = true~ together with ~codeowners_covered = true~
  is allowed; both are ANDed, so the stricter check decides.
- ~--explain~ names the file and the owner that blocked it.

*Actions with ~--apply~.* gh-approve re-reads the head and skips the pull
request if it moved. Then it requests the reviewers through the REST
~requested_reviewers~ endpoint. Only after that succeeds does it remove you as
an individual requested reviewer. It never removes a team request and never
dismisses or changes a review. If the request succeeds and the removal fails,
the pull request is reported as an error with both steps; the colleague stays
requested, which is harmless. Writes are never retried.

It skips the pull request when a target reviewer already reviewed it or is
already requested, or when you already reviewed it.

*Loop guard.* The author may add you back after a hand-off, and then the pull
request stays with you. gh-approve reads the pull request's
~review_requested~ and ~review_request_removed~ timeline events for you. If
your own account ever removed you from the pull request, it never hands it off
again and reports ~manual~ with ~re-requested after hand-off~. The timeline is
the source of truth, so this works without local state and across machines.

** Approve for your own files

You may be requested, as an individual or through a team, on a large pull
request where the only files you own change nothing but comments, and other
code owners cover the rest. These three rule fields approve for your files
only. Each is off by default.

#+begin_src pkl
  new {
    name = "my-comments"
    requested_via_team = true
    mine_comments_only = true
    body = "Comment-only change in {my_files} ({my_teams}); approving for those files only. Other files not reviewed by me."
    checks = "green"
  }
#+end_src

- ~requested_via_team~ also runs the rule when you are requested only through
  a team you belong to. gh-approve then searches with ~review-requested:@me~,
  which includes team requests. Rules that do not set it still skip such a
  pull request, and it is reported as ~skipped~ (shown with ~--pr~ or
  ~--explain~) when no opted-in rule matches. Not allowed on a hand-off rule.
- ~mine_comments_only~ looks at "my files": the changed files whose owners
  include you or a team of yours, from the base branch's CODEOWNERS (the last
  matching line). There must be at least one, and every one must change only
  comment or blank lines, by the same line classifier as
  ~deletions_and_comments_only~ (see [[*Comment markers][Comment markers]]).
  Deleted lines are classified too: deleting a comment is fine, deleting code
  is not. A file your team owns jointly with others is still yours, so the
  approval never counts as code-owner review of code you did not read. If
  CODEOWNERS, a team's members, or a patch cannot be read, the condition
  fails. ~--explain~ lists each of your files with its CODEOWNERS line and why
  it passed or failed.
- ~body~ overrides the global ~body~ for the rule. It may use ~{my_files}~
  (comma-separated paths of your files), ~{my_teams}~ (your teams that own
  them, or your login), and ~{rule}~ (the rule name). ~{my_files}~ and
  ~{my_teams}~ need ~mine_comments_only~. An unknown placeholder is a config
  error. A body with placeholders is used as written. A plain body gets the
  rule name appended, as the global body does. Not allowed on a hand-off rule.

** Per-file checks (~file_checks~)

A rule may set ~file_checks~, mapping a glob pattern to a check:

#+begin_src pkl
  new {
    name = "reviewer-code-plus-shrink-baseline"
    codeowners_covered = true
    checks = "green"
    file_checks {
      ["**/baseline.txt"] = "only-deletions"
      ["checkers/size/baseline.txt"] = "./check-shrink"
    }
  }
#+end_src

For example, a rule can allow code changes owned by the reviewer, plus
~checkers/size/baseline.txt~ where ~./check-shrink~ approves only removed lines
or lowered numbers. A pull request that lowers one entry and fixes the code
approves; one that raises a number defers.

Each changed file is matched against the patterns, and the most specific
pattern wins: an exact path beats any glob, then the pattern with more literal
path segments, then the longer literal text. Two globs with tied
specificity are a config error at load time; distinct exact paths never tie. A file that a pattern covers is judged only by its check;
an uncovered file fails ~file_checks~ (~<path>: not covered by file_checks~),
unless the rule also sets ~paths_all_match~, ~codeowners_covered~,
~codeowners_none_mine~ or ~mine_comments_only~. Those conditions then judge the
uncovered files, and ~--explain~ shows ~not covered (left to <condition>)~ for
each, with ~which passed~ or ~which failed~ when the condition was evaluated. A
pull request with no covered file never passes ~file_checks~. A rule whose files
are all covered and all approved needs no other file condition. Loading a
config that sets ~file_checks~ without one of those conditions logs a warning,
because uncovered files fail the rule. Pull-request-level conditions (~checks~, ~authors_allow~, ~labels_required~,
and so on) still apply.

A check is either:

- A *built-in* name:
  - ~only-deletions~: the file's diff removes lines and adds none.
  - ~deletions-and-comments-only~: reuses the comment classifier under
    [[*Comment markers][Comment markers]].
- A *script*: a path (relative to the config file, ~~~ expanded) or an argv
  list, run directly without a shell:
  - *Stdin*: that one file's unified diff.
  - *Env*: ~GH_APPROVE_REPO~, ~GH_APPROVE_PR~, ~GH_APPROVE_PATH~,
    ~GH_APPROVE_HEAD_SHA~, ~GH_APPROVE_BASE_REF~.
  - *Stdout*: the first word must be ~approve~ or ~defer~. Anything else, a
    non-zero exit, or a timeout (~file_checks_timeout~, default ~30.s~) means
    ~defer~. Output is capped, and stderr goes to ~--explain~.
  - *Cache*: each script decision is cached per ~(script, file diff hash)~ in
    the agent cache.

~--explain~ lists each changed file with its pattern, its check and the result
(~approve~, ~defer~ and why), or ~not covered~.

When ~mark_viewed_on_pass~ is ~true~ (the default), any file whose check returns
~approve~ is marked Viewed on the pull request via ~markFileAsViewed~ (even if
the pull request as a whole is left for a human). ~DISMISSED~ files (changed
since last viewed) are re-marked when they pass on the new diff, and logged
with ~re-mark after change~. ~VIEWED~ files are skipped, ~viewed.never_mark~
still wins, marking happens only with ~--apply~ (dry run reports
~would_mark_viewed~), it shares ~viewed.max_marks_per_run~, and each mark is
logged as ~mark_viewed~ with the passing ~file_checks~ pattern.

** Agent command

A rule may set ~agent_command~, such as a script that asks an LLM to review
the diff. It is a list of arguments, run directly, not through a shell. It
runs only when every other condition of the rule passed and no earlier rule
matched, and never for a pull request that is skipped anyway, such as your own.
It runs in dry run too.

#+begin_src pkl
  new {
    name = "docs-reviewed-by-agent"
    paths_all_match { "docs/**" }
    checks = "green"
    agent_command { "/home/me/bin/review-agent"; "--strict" }
    agent_timeout = 60.s
  }
#+end_src

Its stdin is one JSON object:

#+begin_src json
  {
    "rule": "docs-reviewed-by-agent",
    "pr": {"repo": "acme/widgets", "number": 12, "url": "...", "title": "...",
           "author": "alice", "headSha": "...", "draft": false, "additions": 3,
           "deletions": 1, "changedFiles": 1, "labels": ["docs"]},
    "files": [{"path": "docs/a.md", "additions": 3, "deletions": 1}],
    "diff": "diff --git a/docs/a.md b/docs/a.md\n..."
  }
#+end_src

~filesError~ is added when the file list could not be read completely. The
command must print one JSON object, ~{"decision": "approve" | "defer",
"reason": "..."}~. ~approve~ lets the rule match. ~defer~ leaves the pull
request for a human, and the reason is shown in the table. A non-zero exit, a
timeout, output that is not one JSON object, or an unknown decision all count
as ~defer~, with the error as the reason. A diff that cannot be read defers
without running the command. On timeout, the command's whole process group is
killed.

** Comment markers

~deletions_and_comments_only~ passes when the pull request deletes at least
one line and every added line is blank or a comment. A comment line is
optional whitespace, then the marker, then anything. Code before the marker
on the same line fails. ~/* */~ and ~<!-- -->~ blocks pass when they open and
close on added lines. A block opened in a context line, a deleted line, or
outside the hunk does not cover an added line. A ~#~ line in C or C++ is a
preprocessor line, so it fails. Python docstrings fail. An added line in a
file that is not listed fails. Patches come from ~pulls/{n}/files~ only when
a rule sets the condition. A missing patch, a binary file, or a truncated
file list fails with ~patch unavailable for <file>~. A rename with no content
change passes. On success the condition reports ~N deletions, M comment/blank
additions~.

| ~.cfg~ ~.ini~ | ~#~ or ~;~ |
| ~.go~ ~.c~ ~.cc~ ~.cpp~ ~.cxx~ ~.h~ ~.hh~ ~.hpp~ ~.rs~ ~.ts~ ~.tsx~ ~.js~ ~.jsx~ ~.java~ ~.kt~ ~.swift~ ~.proto~ ~.scala~ ~.cs~ | ~//~ and ~/* */~ |

** Lazy loading and caches

Some conditions need data that costs extra calls: CODEOWNERS and the viewer's
teams (~codeowners_covered~, ~codeowners_none_mine~, ~mine_comments_only~, and the
~codeowners_not_mine~ mark-viewed selector), and file patches
(~deletions_and_comments_only~, ~mine_comments_only~, and ~file_checks~ checks
that read a diff).
gh-approve loads them only when a rule reaches such a condition, after every
cheaper condition of that rule passed, and at most once per pull request. A
pull request that a cheap condition rejects, such as ~repos~, ~authors_allow~,
~labels_required~, ~max_files~, ~not_draft~ or ~checks~, makes no CODEOWNERS,
team or patch call. A condition not reached because a cheaper one failed is
reported as ~skip~ in ~--explain~ and as ~not evaluated: <condition> failed~.

- *CODEOWNERS* is read and parsed once per repository and base branch in a
  run.
- *Teams.* gh-approve reads your own teams once per organization in a run,
  with one paged query, and decides from that set whether you are in a team.
  The query also reads the parents of each of your teams, so a parent team
  counts when you are in one of its child teams. A team still counts only when it has other members and is a requested
  reviewer. For that it reads the member count of a team of yours, never the
  member list. When your teams cannot be read, it falls back to listing the
  team's members. Counts and lists are cached for the run too.
- *Patches* are not fetched for a pull request with more than
  ~patch_max_files~ changed files (default ~300~) or more than
  ~patch_max_added_lines~ added lines (default ~5000~), both set in the
  ~approve~ block. A condition that needs them then fails with ~too large to
  check~, and the pull request is left for a human.

~--explain~ prints one line per pull request, such as:

#+begin_example
  timing: total 1.2s; pull request 310ms; CODEOWNERS 420ms; teams 95ms; patches 760ms; agent command skipped; cache: hit
#+end_example

It gives the total time and the time of each load: the pull request, CODEOWNERS,
teams, patches and the agent command. A load reads ~skipped~ when no rule needed
it (or, for patches, ~skipped (too large)~), and ~cache hit~ when the run
already had it, or, for the agent command, when its decision cache answered.
When the per-commit PR facts cache is enabled, it ends with ~cache: hit~ or
~cache: miss (<reason>)~.

*** Per-commit PR facts cache and parallel loading

gh-approve caches expensive per-commit facts across passes under
=$XDG_CACHE_HOME/gh-approve/facts/= (default =~/.cache/gh-approve/facts/=),
next to the agent decision cache:

- Changed file list and per-file stats;
- REST file patches;
- CODEOWNERS ownership for those files and the viewer's team membership used
  for ownership.

Each entry is keyed by ~owner/repo~, pull request number, head SHA, and a
schema version. Mutable state (labels, draft state, author, review requests,
reviews, checks, and unresolved threads) is never cached and is always read
and evaluated live on each pass.

An entry is invalidated and reloaded when any of these change:

- the head SHA;
- the CODEOWNERS blob SHA on the base branch;
- the hash of the viewer's team list;
- the cache schema version.

Corrupt or unreadable entries count as a miss and are removed. Entries for pull
requests that are no longer candidates are pruned after ~approve.pr_cache_ttl~
(default ~7.d~). Pass ~--no-cache~ to bypass the cache.

Uncached candidates are loaded with a bounded worker pool (~approve.load_concurrency~,
default ~4~, overridable with ~--load-concurrency~). Output order always matches
candidate order, and approvals, hand-offs, and file marks still run
sequentially. On a GitHub secondary rate-limit response, gh-approve backs off,
reduces worker concurrency, and retries without failing the pass.

** Agent decision cache

An agent command can be expensive, such as an LLM review, so gh-approve caches
its decision. The key is the sha256 of the exact stdin bytes, the argv, and the
rule name. Stdin is built deterministically: files and labels are sorted, and
it carries the head SHA, so a new push or a changed diff runs the command
again.

- One file per key under =$XDG_CACHE_HOME/gh-approve/agent/= (default
  =~/.cache/gh-approve/agent/=), mode 0600, written atomically. It holds the
  decision, the reason, the time, and the duration of the original run.
- Only an ~approve~ or ~defer~ the command printed is cached. An error, a
  timeout, a non-zero exit, invalid output, or an unknown decision is never
  cached, so the next pass runs the command again.
- An entry older than ~agent_cache_ttl~ (default ~7.d~) is ignored and removed.
  When the cache is larger than ~agent_cache_max_mb~ (default ~50~), the
  oldest entries are evicted first.
- ~--no-agent-cache~ neither reads nor writes the cache. A rule with
  ~agent_cache = false~ always runs its command.
- Only the agent step is cached. Every other condition is still evaluated
  live, and ~--apply~ still re-reads the head before it approves.

The table shows where a decision came from, such as ~agent: approve (cached 2d
ago)~, ~agent: defer (cached)~, or ~agent: approve (fresh)~. ~--explain~ adds
~agent_cache: hit|miss|bypass~ and the key's short hash, and the audit log's
~agent~ object has ~agent_cache~ and ~agent_cache_key~.

** Safety

- *Dry run by default.* Only ~--apply~ approves, hands off, or marks files
  viewed. A dry run makes no writes.
- *Head pinning.* gh-approve evaluates one head SHA. With ~--apply~, it reads
  the head again just before it approves. If the head moved, it skips the pull
  request and says so. The approval is posted with ~gh api~ to the pull
  request reviews endpoint, with ~event=APPROVE~ and ~commit_id~ set to the
  evaluated head SHA.
- *Fail loud.*
  - A ~gh~ error stops that pull request with a clear error. The other pull
    requests still run, and gh-approve exits non-zero.
  - An unknown config key is a load error.
  - Data that cannot be read, such as missing review thread or check data or a
    truncated file list (for example, more than 100 changed files), never counts
    as a met condition and is never auto-approved. An unevaluated pull request
    is reported as ~unevaluated: <reason>~ (with ~manual~ for non-transient
    incomplete data or ~error~ for load API errors), counted in ~Left for you~,
    and listed separately under it with a rerun suggestion only for transient
    failures.
- *Audit log.* Each decision is appended as one JSON line to
  =~/.config/gh-nudge/approve-log.jsonl=. A line has ~time~, ~pr~, ~url~,
  ~title~, ~author~ (the pull request author's login; lines written before
  this field still read), ~headSha~, ~rule~ (~null~ when none matched), ~rules~ (each rule's
  per-condition ~pass~ and ~saw~, and ~agent~ with ~decision~, ~reason~ and
  ~durationMs~ when the rule's agent command ran), ~action~, ~reason~, and
  optional ~unevaluated~ / ~transient~ flags when unevaluated.
  ~--explain~ shows the same agent decision, reason and duration. The action is
  ~approved~, ~would_approve~, ~handoff~, ~would_handoff~, ~mark_viewed~,
  ~would_mark_viewed~, ~skipped~, ~manual~, or ~error~. A hand-off line also
  has ~reviewers~, ~timeline~ (your review request events, the loop guard's
  evidence), ~loopGuard~, and ~steps~ (each write and its result). A mark
  line also has ~paths~, the files that were marked, or that a dry run would
  mark.

** History

~gh-approve history~ lists those decisions. ~--days~ defaults to 7. ~--action~
is ~approved~ (the default), ~handoff~, ~mark_viewed~, or ~all~. A ~would_*~
dry-run action is included only with ~--action all~. ~--rule NAME~ keeps one
rule. ~--json~ prints one JSON array.

The table columns are time (UTC), ~owner/repo#n~, author, current state
(~OPEN~, ~CLOSED~, or ~MERGED~), action, rule, and title. The author comes
from the log line. It is looked up only for an older line that has no
~author~. When stdout is a terminal, the PR column is rendered as a clickable
OSC 8 hyperlink to the pull request URL without changing column alignment;
non-TTY stdout, ~NO_COLOR~, ~TERM=dumb~, and ~--no-links~ disable links.
~--json~ includes a ~url~ field and never emits escape sequences.

~gh-approve open <ref>~ opens a pull request in the browser using
~gh browse <N> -R owner/repo~ (falling back to ~open~ on macOS or ~xdg-open~
elsewhere when ~gh~ is unavailable). ~<ref>~ may be a bare number (resolved
against the single configured repository in ~github.repos~; an error listing
configured repositories if several exist), ~owner/repo#N~, or a GitHub pull
request URL (ignoring trailing paths or queries). ~--print~ prints the URL
instead of opening it.

~MERGED~ is final. History caches it, with the author and title, in
~$XDG_CACHE_HOME/gh-nudge/pr-state.json~ (or =~/.cache/gh-nudge/pr-state.json=)
and does not fetch that pull request again. ~OPEN~ and ~CLOSED~ are fetched
on every run and are not cached. Every lookup in one run is one GraphQL
request of aliased ~repository~ / ~pullRequest~ fields, through ~GH_BIN~,
split into chunks of at most 50. A run whose pull requests are all cached
as ~MERGED~ makes no call. ~--no-state~ drops the state column and makes no
call; author and title then come from the log or the cache, and are blank
when neither has them.

A GraphQL error stops the command. A pull request that cannot be read shows
~?~ in the cells that are still unknown, and a warning on stderr. The row
stays.

** Mark viewed

A pull request that no approve or hand-off rule took stays with you. ~viewed~
rules can tick your GitHub *Viewed* checkbox on files you have decided never
to read, so the Files tab shows what is left. This never approves anything
and never changes anyone else's viewed state. It is off unless ~enabled~.

#+begin_src pkl
viewed {
  enabled = true
  never_mark { "**/*.go"; "**/*.py"; "**/*.proto" }
  rules {
    new { name = "locks"; paths_match { "**/*.lock"; "**/go.sum"; "**/pnpm-lock.yaml" } }
    new { name = "not-mine"; codeowners_not_mine = true; paths_none_match { "docs/**" } }
  }
}
#+end_src

- ~enabled~ defaults to ~false~. ~max_marks_per_run~ defaults to 200. One run
  stops cleanly at that many files.
- A rule has a ~name~, an optional ~repos~ filter (~owner/name~ or a glob),
  and one or more selectors. A changed file is selected when the repository
  matches and any selector matches: a ~paths_match~ glob, or
  ~codeowners_not_mine~ when the file's CODEOWNERS owners include neither you
  nor a team you belong to.
- ~paths_none_match~ (alias ~except_paths~) is a glob list on one rule, with
  the same syntax as ~paths_match~. A file matching any of them is not marked
  by that rule, even when a selector matches. Another rule can still mark it.
  Setting both names on one rule is a config error.
- ~never_mark~ is a glob list on ~viewed~. A file matching any of them is
  never marked by any rule. It wins over every rule's selectors.
- ~@generated~ works in ~paths_match~, ~paths_none_match~, and ~except_paths~
  the same way as in approve rules.

** Generated file lists (~@generated~)

Instead of copying generated-file globs into ~config.pkl~ by hand, you can point
~generated_lists~ at a YAML file checked into the reviewed repository:

#+begin_src pkl
generated_lists {
  ["example-org/example-repo"] = "tools/generated_files.yaml"
}
#+end_src

The list file in the repository is a YAML sequence of entries, one per glob,
in the format of [[file:../genfiles/README.org][genfiles]]:

#+begin_src yaml
- pattern: "**/*.pb.go"
  comment: Protobuf Go code.
  run:
    - [make, proto]
#+end_src

Only ~pattern~ is read by ~gh-approve~; other keys are ignored, so lists in an
older shape (a ~regenerate~ string, ~bazel_generated~, ~source~) keep working.
An empty or comment-only file is a list with no patterns. An entry without a
valid ~pattern~ is a parse error; that includes doublestar-only syntax such as
brace alternatives (~{a,b}~) and bracket classes, which ~.gitattributes~ does
not support, so write one entry per pattern. ~genfiles check~ is the
strict checker for the rest of the format. ~gh-approve~ reads the file from
the pull request's base SHA through the GitHub API and caches it per
repository and base SHA for the run.

List patterns match with ~.gitattributes~ rules, the same as ~genfiles~ and
GitHub: a pattern with no ~/~ matches the file name at any depth, so
~Cargo.lock~ from the list matches ~sub/Cargo.lock~. Inline rule globs keep
their own doublestar rules, where ~Cargo.lock~ matches only at the root. In
~paths_all_match { "@generated"; "Cargo.lock" }~ the two ~Cargo.lock~ globs
therefore match differently.

Any rule glob list (~paths_all_match~, ~paths_any_match~, ~paths_none_match~,
~file_checks~ keys, and ~viewed~'s ~paths_match~, ~paths_none_match~, and
~except_paths~) can include ~"@generated"~, combined as a union with inline
globs:

#+begin_src pkl
paths_all_match { "@generated"; "**/*.lock" }
#+end_src

Referencing ~@generated~ for a repository without a ~generated_lists~ entry is
a config error at load time. At runtime, ~gh-approve~ fails closed: if the list
file is missing on the base branch, cannot be fetched, or fails to parse, every
condition referencing ~@generated~ fails with the reason (such as
~generated list tools/generated_files.yaml: not found at <sha>~) and a ~viewed~
rule marks nothing. With ~--explain~, each file matched through the list prints
~<path>: @generated "<pattern>"~.
- With ~--explain~, a file a selector would have marked and an exclusion kept
  visible is named with ~excluded by rule <name> paths_none_match <glob>~ or
  ~excluded by viewed.never_mark <glob>~. The audit log does not record that
  file as marked.
- ~UNVIEWED~ and ~DISMISSED~ files matched by a rule are marked by default
  (~DISMISSED~ means the file changed since you viewed it; re-marked files are
  logged as ~re-mark after change~). ~VIEWED~ files are left alone. Set
  ~viewed.remark_dismissed = false~ to leave ~DISMISSED~ files unmarked.
  Nothing is ever unmarked. (Note: ~viewed.remark_dismissed~ previously
  defaulted to ~false~; existing configs that omit it now re-mark ~DISMISSED~
  files automatically.)
- The same pull requests as approve rules: you are requested as an individual,
  it is open, and it is not a draft. Never your own. A pull request an approve
  or hand-off rule took is not marked.
- CODEOWNERS and team members are read the same way as a hand-off coverage
  check. If either cannot be read, that pull request is not marked.
- With ~--apply~, gh-approve re-reads the head and skips the pull request if
  it moved, then runs one ~markFileAsViewed~ mutation per file through ~gh~.
  A dry run prints ~would_mark_viewed: N files~ and, with ~--explain~, the
  paths. The audit action is ~mark_viewed~ or ~would_mark_viewed~.
