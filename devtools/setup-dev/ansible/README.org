#+TITLE: Ansible playbooks
#+DATE: 2026-11-15

This directory is the playbooks behind
[[file:../README.org][setup-dev]]. A rule is a playbook name: the file
name with ~.yml~ removed. ~./ensure.sh rg~ runs ~rg.yml~. Most
playbooks are generated from ~packages_data.go~. A file whose first
lines do not say ~AUTO-GENERATED~ is hand-written. The fresh-machine
steps are in the setup-dev README, not here.

* Running playbooks

** One tool, a profile, or everything

#+BEGIN_SRC bash
./ensure.sh rg
./ensure.sh profile-minimal
./ensure.sh all
#+END_SRC

~rg~ installs ripgrep. ~profile-minimal~ is the light set. ~all~
imports the groups listed in ~all.yml~. System packages may ask for a
sudo password. The log path is in the setup-dev README.

** Passing Ansible flags

Arguments that start with ~-~ go to ~ansible-playbook~. The others are
playbook names. These flags read the next argument as their value:
~-e~ / ~--extra-vars~ (may repeat), ~-t~ / ~--tags~, ~--skip-tags~,
~-l~ / ~--limit~, and ~-i~ / ~--inventory~. Each value is one
argument, so spaces, JSON, and ~@file~ work:

#+BEGIN_SRC bash
./ensure.sh -e foo=bar -e 'msg="hello world"' --tags setup profile-cloudflare-dev
#+END_SRC

For any other flag that takes a value, use the joined form
~--flag=value~, or the value is treated as a playbook name. Arguments
after ~--~ are always playbook names.

** Resuming a failed run

When a nested ~import_playbook~ fails, Ansible stops and ~ensure.sh~
prints the leaf file and task, plus a resume command. ~--from~ starts
at the beginning of that leaf playbook. The include guard must be the
first play in that file, so the file's ~import_playbook~ lines still
run. Re-running the rest of that leaf file is expected:

#+BEGIN_SRC bash
./ensure.sh --from setup-git -- all
#+END_SRC

~--from~ reads the include-guard task name from the playbook. An
include guard is the task that stops the file when it was already
imported. If the file has no include guard, ~ensure.sh~ exits with an
error instead of guessing ~--start-at-task~.

** Daily refresh

~ensure.sh~ refreshes system package managers (~nala~ on
Debian/Ubuntu, ~brew~ on macOS, ~pkg~ on Termux) and a few toolchains
(~rustup~, Termux ~pip~, ~ansible-galaxy~) at most once every 24
hours. Stamp files live in =$HOME/.cache/last_upgrade/=. Delete one
to force that refresh on the next run.

* Profiles (Qubes OS / Subset Installs)

A profile is a curated subset of tools in a ~profile-*.yml~ file. It
uses the same ~import_playbook~ form as ~all.yml~, with fewer
playbooks.

*** Available Profiles

- ~profile-minimal.yml~ -- core CLI tools for a light setup
- ~profile-emacs-daily.yml~ -- Emacs with shell tools for daily use
- ~profile-antigravity.yml~ -- the agy CLI and the desktop IDE
- ~profile-cloudflare-dev.yml~ -- Node.js, TypeScript, and Cloudflare

To add a profile, create ~profile-{name}.yml~ and run ~make~.

*** Qubes OS Workflow

A TemplateVM and an AppVM do different jobs:

1. TemplateVM: run the generated ~qubes-templatevm-{profile}.sh~ to
   add apt sources and install system packages.
2. AppVM: run ~./ensure.sh profile-{profile}~ to install
   home-directory tools (Go, Cargo, npm, configs).

The hand-written trim and default scripts live in ~../qubes/~, not in
these generated files. The setup-dev README says which is which.

* Per-machine settings

~inventory.ini~ is tracked and shared, so per-machine settings do not
go there. Put them in =~/.config/setup-dev/vars.yml=, or under
~XDG_CONFIG_HOME~ when that variable is set. The file is outside the
repository and is optional. A playbook loads it with
~vars_files~ when it reads such a setting, and ~-e~ still overrides it
for one run.

| Variable                  | Playbook                 | Effect                                  |
|---------------------------+--------------------------+-----------------------------------------|
| ~fork_keeper_cron_enabled~ | ~setup-fork-keeper.yml~ | ~true~ keeps the daily fork-keeper job  |
| ~hub_ssh_target~          | ~setup-hub-client.yml~   | required ssh target; see the hub doc    |

For example, on the machine that runs fork-keeper:

#+BEGIN_SRC yaml
fork_keeper_cron_enabled: true
#+END_SRC

* Adding a tool

Edit ~packages_data.go~. From the repository root, regenerate:

#+BEGIN_SRC bash
make generate-ansible
#+END_SRC

From this directory, ~make~ does the same thing.

A tool whose installer downloads a shell script must go through
~verified-run~. That helper checks the script's SHA-256 and refuses
to run it after the upstream file changes. In ~packages_data.go~ the
command looks like
~{{ playbook_dir }}/verified-run exec https://example.com/install.sh~.
Do not add a new ~curl ... | bash~ installer.

Then check syntax:

#+BEGIN_SRC bash
bazel test //devtools/setup-dev/ansible:ansible_syntax_tests
#+END_SRC

* Platform-Specific Installation Strategy

The generator picks an installer per platform.

** Termux

Prefer ~pkg~ when the package exists. Termux's layout usually needs
its own packages, and ~pkg~ handles those dependencies.

** Debian/Ubuntu

Prefer apt only when an old package is acceptable, or when a
maintained PPA is current. The Emacs PPA
(~ppa:ubuntuhandbook1/emacs~) is one of those. The Go toolchain itself
is not the Ubuntu ~golang~ package. ~go.yml~ installs the latest
stable upstream release under =/usr/local/go=, checks its SHA-256
against https://go.dev/dl/?mode=json, and replaces it when a newer
stable release is published.

** Python

Prefer ~uv~. It is faster than pip and does not depend on the system
~distutils~ package.

** Go

~go install~ is the usual method for Go programs. The generator checks
the installed version and upgrades it.

** Rust

On macOS and Debian, ~rustup~ is the toolchain (~rustc~, ~cargo~,
~rustfmt~, ~clippy~). Extra pieces such as ~rust-analyzer~ are
~rustup~ components. On Termux, ~pkg install rust~ provides the
bundled tools, and ~rust-analyzer~ is its own package.

** macOS

Prefer Homebrew for system packages. ~rustup~ itself comes from
Homebrew and then manages the Rust components.

* Troubleshooting

** sudo / privilege escalation

Playbooks use ~become: yes~ for apt. Ansible's sudo plugin defaults to
~sudo -H -S -n~ and does not reuse a terminal sudo ticket. ~sudo true~
succeeding in your shell is not enough. sudo timestamps are
TTY-specific, and Ansible invokes sudo on a different TTY.

On Linux, ~ensure.sh~ probes passwordless sudo in a new session. If
that fails, it passes ~-K~ and Ansible prompts for the become password
once. Passwordless sudo skips the prompt. A non-interactive run
without passwordless sudo fails immediately. Re-run from a terminal,
pass ~-K~, or configure ~NOPASSWD~.

Ubuntu 25.10 and later point =/usr/bin/sudo= at sudo-rs. sudo-rs
prints the ~-p~ prompt in a form Ansible does not recognize, so the
task times out. When ~sudo.ws~ is on ~PATH~, ~ensure.sh~ sets
~ANSIBLE_BECOME_EXE~ to that classic sudo. A value you already
exported is left unchanged.

** Ansible version requirement

Playbooks use ~ansible.builtin.deb822_repository~ (ansible-core 2.15
or newer). Ubuntu LTS apt packages are often older. ~ensure.sh~
detects that and upgrades Ansible with ~pip --user~. Ansible resolves
modules at parse time, so a too-old Ansible fails even on tasks that
only target Debian.

On Debian/Ubuntu, ~ensure.sh~ also installs ~python3-debian~, which
~deb822_repository~ imports.

~ensure.sh~ installs ~community.general~ so a Galaxy copy cannot
shadow a compatible bundled collection:

- On Debian/Ubuntu it prefers the collection shipped with the active
  Ansible. If that bundled collection is missing, it installs a Galaxy
  version pinned to the installed ansible-core (2.15 through 2.18).
- After a pip ~--user~ ansible-core upgrade it ignores leftover apt
  collections and force-installs a pin for the new core.
- On macOS and Termux it installs the latest collection from Galaxy.
- A failed ~ansible-galaxy~ install aborts the run and does not
  refresh the daily cache.

* Two-machine agent hub

Optional. One Linux machine runs the agent bus daemon and the decide
ledger. Clients reach it over ssh. The playbooks, the variables, and
what they change are in [[file:docs/hub-setup.org][the hub setup]].

* Playbook notes

** Homebrew on non-interactive zsh

~setup-homebrew-env.yml~ still puts ~brew shellenv~ in the interactive
rc (=~/.zshrc= on zsh). ~ssh host command~ reads =~/.zshenv= only, so
on macOS the same playbook prepends the Homebrew bin and sbin
directories there when ~brew~ is installed. A second run does not
duplicate them. Linux and Termux are left alone.

** Claude Code sandbox network

~setup-claude-sandbox.yml~ writes ~sandbox.network.allowedDomains~,
~sandbox.network.allowUnixSockets~, and ~sandbox.filesystem.allowWrite~
in =~/.claude/settings.json=. A rerun unions each list with what is
already there. Domains also take ~allowedHosts~, then that key is
dropped. Entries added by hand stay, in front. ~allowUnixSockets~ also
gains the docker socket and the herdr, agentbus daemon, and agentbus
tunnel sockets from ~agentbus doctor --sandbox~. On macOS,
~allowWrite~ also gains =~/Library/Caches/agentbus/state= and
=~/Library/Caches/agentbus/run=. Other settings keys are left as they
are.

* Hand-written playbooks

A ~.yml~ file without the ~AUTO-GENERATED~ header is maintained by
