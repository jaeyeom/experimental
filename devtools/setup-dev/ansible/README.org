This directory includes Ansible playbooks and a generator of it.

* Bootstrap (Fresh Machine)

On a fresh machine without the repository cloned, run:

#+begin_src sh
curl -fsSL https://raw.githubusercontent.com/jaeyeom/experimental/main/devtools/setup-dev/ansible/bootstrap.sh | sh
#+end_src

This installs git (if needed), clones the repository, and guides you through
running =ensure.sh=.

* How to Use

Run the =ensure.sh= script with the proper rule name. Rule names are playbook
filenames.

#+begin_src sh
  ./ensure.sh [rule]...
#+end_src

Arguments starting with =-= go to =ansible-playbook=; the others are
playbook names. These flags read the next argument as their value:
=-e=/=--extra-vars= (may repeat), =-t=/=--tags=, =--skip-tags=,
=-l=/=--limit=, and =-i=/=--inventory=. Each value is passed as one
argument, so spaces, JSON, and =@file= work:

#+begin_src sh
  ./ensure.sh -e foo=bar -e 'msg="hello world"' --tags setup profile-cloudflare-dev
#+end_src

For any other flag that takes a value, use the joined form
(~--flag=value~), or the value is treated as a playbook name. Arguments
after =--= are always playbook names.

When a nested =import_playbook= fails, Ansible stops and =ensure.sh= prints
the leaf file and task (not only the top-level argument), plus a resume
command. =--from= starts at the beginning of that leaf playbook file (its
include-guard, which must be the first play so that file's
=import_playbook= lines still run) and continues the rest of the original
run. Re-running the rest of that leaf file is expected:

#+begin_src sh
  ./ensure.sh --from setup-git -- all
#+end_src

=--from= reads the include-guard task name from the playbook file. If the
file has no include guard, it exits with an error instead of guessing
=--start-at-task=.

=ensure.sh= refreshes system package managers (=nala= on Debian/Ubuntu,
=brew= on macOS, =pkg= on Termux) and a few toolchains (=rustup=, Termux
=pip=, =ansible-galaxy=) at most once every 24 hours. Stamp files live in
=$HOME/.cache/last_upgrade/=; delete one to force that refresh on the
next run.

** sudo / privilege escalation

Playbooks use =become: yes= for apt operations. Ansible's sudo plugin
defaults to =sudo -H -S -n= and does *not* reuse a terminal sudo ticket:
=sudo true= succeeding without a password in your shell is not enough.
sudo timestamps are TTY-specific, and Ansible invokes sudo on a different
TTY (or none).

On Linux, =ensure.sh= probes passwordless sudo in a new session (so a
TTY ticket cannot hide a missing =NOPASSWD= rule). If that fails, it
passes =-K= and Ansible prompts for the become password once at the start
of the run. Passwordless sudo skips the prompt. Non-interactive runs
without passwordless sudo fail immediately; re-run from a terminal, pass
=-K=, or configure =NOPASSWD=.

Ubuntu 25.10 and later point =/usr/bin/sudo= at sudo-rs. sudo-rs prints
=-p PROMPT= as =[sudo: PROMPT] Password:=, which Ansible's become plugin
does not recognize, so the task times out on the prompt. When =sudo.ws=
is on =PATH=, =ensure.sh= sets =ANSIBLE_BECOME_EXE= to that classic sudo.
A value you already exported is left unchanged.

** Ansible version requirement

Playbooks use =ansible.builtin.deb822_repository= (ansible-core >= 2.15).
Ubuntu LTS apt packages are often older than that; =ensure.sh= detects this and
upgrades Ansible via =pip --user= so module resolution succeeds. Ansible
resolves modules at parse time, so even Debian-only tasks fail on Ubuntu when
the installed Ansible is too old.

On Debian/Ubuntu, =ensure.sh= also installs =python3-debian= (the runtime
library =deb822_repository= imports).

=ensure.sh= installs =community.general= so a Galaxy copy cannot shadow a
compatible bundled collection:

- On Debian/Ubuntu it prefers the collection shipped with the *active*
  ansible (the python module tree, not a leftover apt path). If that
  bundled collection is missing, it installs a Galaxy version pinned to
  the installed ansible-core (2.15–2.18).
- After a pip =--user= ansible-core upgrade it ignores leftover apt
  collections and force-installs a pin for the new core.
- On macOS and Termux it installs the latest collection from Galaxy
  (=--force= after an upgrade).
- A failed =ansible-galaxy= install aborts the run and does not refresh
  the daily cache.

** Per-machine settings

=inventory.ini= is tracked and shared by every machine, so per-machine
settings do not go there. Put them in
=${XDG_CONFIG_HOME:-~/.config}/setup-dev/vars.yml=, outside the repository,
so every checkout and worktree on the machine uses them. The file is
optional. A playbook loads it with =vars_files= when it reads such a
setting, and =-e= still overrides it for one run.

| Variable                   | Playbook                | Effect                               |
|----------------------------+-------------------------+--------------------------------------|
| =fork_keeper_cron_enabled= | =setup-fork-keeper.yml= | =true= keeps the daily fork-keeper job |
| =hub_ssh_target= and others | =setup-hub-client.yml= | See [[*Two-machine hub setup]]     |

For example, on the machine that runs fork-keeper:

#+begin_src yaml
  fork_keeper_cron_enabled: true
#+end_src

** Two-machine hub setup

One machine, the hub (Linux), runs =agentbusd= and the decide ledger. A
client (for example macOS) runs =agentbus= and =decide= in hub mode, and
they reach the hub with =ssh -o BatchMode=yes <hub> <cmd>=. Two manual
playbooks set this up. =all.yml= imports neither, so nothing changes on a
machine until you run one there.

| Variable               | Default     | Meaning                                                  |
|------------------------+-------------+----------------------------------------------------------|
| =hub_ssh_target=       | required    | ssh target of the hub, such as =me@hub.example=          |
| =client_machine_label= | required    | this client's herdr saved-machine label on the hub       |
| =hub_tools_version=    | =latest=    | =go install= version of agentbus and decide: a tag or commit |
| =hub_connect_timeout=  | =5s=        | ssh connect timeout (=hubTimeout=, =remote_timeout=)     |
| =hub_host_shell=       | login shell | =bash= or =zsh=, for =setup-hub-host.yml=                |

Set them in the client's per-machine vars file (see [[*Per-machine
settings]]), in a private inventory or group vars, or with =-e=; not in
the shared =inventory.ini=. Without =hub_ssh_target= and
=client_machine_label=, =setup-hub-client.yml= stops before it changes
anything.

On the hub, =setup-hub-host.yml= puts =~/go/bin= and =~/.local/bin= on
=PATH= for =ssh hub cmd=. Many =~/.bashrc= files return early for a
non-interactive shell, so for bash it writes a marked block at the top
of =~/.bashrc=, above that guard; for zsh it writes the block to
=~/.zshenv=. Another run leaves the file as it is, and the block does
not add a directory that is already on =PATH=. Then it checks, from a
non-interactive shell, that =decide=, =agentbus=, and =herdr= are found,
and fails naming any that are not. It does not install them.

On the client, =setup-hub-client.yml= installs =agentbus= and =decide=
with =go install ...@<hub_tools_version>=. =agentbusd= refuses to start
in hub mode, so it is not installed. Then it:

- merges =hub=, =hubTimeout=, and =machine= into
  =~/.config/decide/config.json= and keeps every other key;
- sets the top-level =hub=, =machine=, and =remote_timeout= in
  =~/.config/agentbus/config.toml=, above its first =[section]=, and
  keeps the other keys and sections.

Both files are backed up before a change. It does not run
=agentbus install=, start a service or tunnel, or touch tokens.

Run each playbook on its own machine:

#+begin_src sh
  # on the hub
  ansible-playbook -i inventory.ini setup-hub-host.yml
  # on the client
  ansible-playbook -i inventory.ini setup-hub-client.yml \
    -e hub_ssh_target=me@hub.example -e client_machine_label=laptop
#+end_src

=./ensure.sh setup-hub-host= and =./ensure.sh setup-hub-client= work too.
To run both from one controller, use a private inventory that names the
two machines and limit each run, for example
=ansible-playbook -i ~/hosts.ini setup-hub-host.yml -l hub=.

*** Check

The last task of =setup-hub-client.yml= runs =decide status list= and
=agentbus list= through the hub, with =DECIDE_HUB= and =AGENTBUS_HUB= set
to =hub_ssh_target=. It fails with the command's stderr when the hub is
unreachable or a binary is missing on either side. To run only the check:

#+begin_src sh
  ansible-playbook -i inventory.ini setup-hub-client.yml --tags hub-check \
    -e hub_ssh_target=me@hub.example -e client_machine_label=laptop
#+end_src

The hub must accept the client's ssh key without a prompt, and the
client must be saved in the hub's herdr as =client_machine_label=.

*** Next manual step

For the faster forwarded-socket path, add =hub_socket= to the client's
=~/.config/agentbus/config.toml= and run =agentbus install= there; see
"Talk to the hub daemon over a forwarded socket" in
[[file:../../agentbus/README.org][agentbus/README.org]]. Without it,
every agentbus command goes over ssh.

*** Undo

Each change leaves a backup next to the file, named
=<file>.<pid>.<date>@<time>~=. The agentbus config gets one backup per
key that changed, so the oldest backup from a run is the file before
that run:

#+begin_src sh
  ls -tr ~/.config/decide/config.json.*~ ~/.config/agentbus/config.toml.*~
  cp ~/.config/decide/config.json.12345.2026-01-02@03:04:05~ ~/.config/decide/config.json
#+end_src

A file that did not exist before has no backup; delete it. On the hub,
delete the lines from =# BEGIN setup-dev hub PATH= through
=# END setup-dev hub PATH= in =~/.bashrc= or =~/.zshenv=.

* Design
The purpose of this Ansible Setup Dev is to set up my development environment
mostly identical in any environment. I made Ansible Playbooks import other
Playbooks to handle dependencies. To prevent multiple inclusion, I added include
guards for each playbook file. Generating it is very cumbersome, so I made a Go
program to generate repetitive text in playbook.

** Platform-Specific Installation Strategy
The generator follows a platform-specific installation strategy to ensure optimal
package management across different environments:

*** Termux
Package manager =pkg= should be strongly preferred on Termux if the package is
available, because Termux has an unconventional setup that usually needs
patching. The =pkg= package manager is also nearly up-to-date and handles
dependencies properly within the Termux environment.

*** Debian/Ubuntu
Debian/Ubuntu's package manager =apt= is often not up-to-date, so it's not
preferred for packages that are actively being developed. Only use =apt= when
old versions are totally acceptable for the use case.

If there's a well-maintained PPA that provides up-to-date packages, it's good to
use it with =apt=. One example is the Emacs PPA (=ppa:ubuntuhandbook1/emacs=)
which provides recent Emacs versions.

*** Python Packages
For Python packages, =uv= is the most preferred installation method. It's
significantly faster than =pip=, has better dependency resolution, and doesn't
suffer from issues like the Python 3.12+ =distutils= removal that affects
system =pip= installations.

*** Go Packages
Go installer (=go install=) is quite cross-platform and handles versioning well,
so it's usually a good idea to use it for Go projects. The generator includes
automatic version checking and upgrade logic for Go packages.

The Go toolchain itself is not installed from apt on Debian and Ubuntu.
Ubuntu's =golang= package lags upstream (noble still ships Go 1.22), and the
old playbook also left an existing =go= binary untouched, so =go install=
kept running that older toolchain. =go install pkg@version= does not download
a newer toolchain when only a dependency requires one. =go.yml= therefore
installs the latest stable upstream release under =/usr/local/go=, checks its
SHA-256 against https://go.dev/dl/?mode=json, and replaces it when a newer
stable release is published. macOS still uses Homebrew, and Termux still uses
=pkg=, because the official Linux tarballs do not run there.

*** Rust Packages
On macOS and Debian, =rustup= is the sole Rust toolchain provider. It is
installed via Homebrew (macOS) or apt (Debian), and =rustup default stable=
provides =rustc=, =cargo=, =rustfmt=, and =clippy=. Additional components like
=rust-analyzer= are added via =rustup component add=.

On Termux, the system =rust= package (=pkg install rust=) provides the bundled
tools (rustc, cargo, rustfmt, clippy), and =rust-analyzer= is available as a
separate Termux package.

*** macOS
Homebrew is generally the preferred installation method on macOS because it
provides system-level packages. For the Rust toolchain itself, =rustup= is
installed via Homebrew and manages all Rust components including =rust-analyzer=.

Homebrew also supports taps and installation options when needed for specialized
packages.

To regenerate the playbooks, simply run:
#+begin_src sh
  make generate-ansible
#+end_src

The playbook =all.yml= just imports variuos other playbooks that I think are
essential.

** Profiles (Qubes OS / Subset Installs)
Profiles are curated subsets of tools defined in =profile-*.yml= files. Each
profile follows the same =import_playbook= format as =all.yml= but includes
only the playbooks needed for a specific use case.

For each profile, the generator produces =qubes-templatevm-{profile}.sh=, a
self-contained TemplateVM bootstrap script that adds PPAs, backports, custom apt
repos, and installs all packages.

*** Qubes OS Workflow
In Qubes OS, TemplateVMs and AppVMs serve different roles:
1. *TemplateVM*: Run the generated =qubes-templatevm-{profile}.sh= to install
   system-level apt packages and their sources.
2. *AppVM*: Run =./ensure.sh profile-{profile}= to install home-directory tools
   (Go, Cargo, npm, configs, etc.) that are not part of the system packages.

*** Available Profiles
- =profile-minimal.yml= -- Core CLI tools for any lightweight setup
- =profile-emacs-daily.yml= -- Emacs with shell tools for daily use

To create a new profile, add a =profile-{name}.yml= file and run =make= to
regenerate outputs.
