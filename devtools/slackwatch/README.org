#+TITLE: slackwatch
#+DATE: 2026-11-09

* Overview

~slackwatch~ tracks Slack posts made on a user's behalf and pushes
replies to whoever owns each post. One binary is both the server
(~slackwatch serve~) and the CLI. It posts only drafts the user
approved in ~decide~ (see [[*Posting][Posting]]), and never reacts or edits.

~serve~ connects through Slack Socket Mode and handles live events. It
catches up on missed traffic and closes quiet watches in a periodic sweep.

What it does not do:

- It never reacts, edits, or deletes. The Slack token in ~tokenFile~ is
  read only. Posting is off unless ~post.mode~ is set; handoff mode
  leaves the posting to an agent's own Slack tool, and direct mode uses
  a separate write token.
- It never writes or changes post text and never interprets a free-text
  answer.
- It knows nothing about terminals, agent runtimes, or workspaces. Every
  integration is a config value: a notify template and its targets.

* Slack app setup

Create a Slack app for your workspace and install it for yourself.

1. Under *OAuth & Permissions*, add these *user token* scopes, all read
   only: ~channels:history~, ~groups:history~, ~im:history~,
   ~mpim:history~, ~users:read~, ~channels:read~, ~groups:read~,
   ~im:read~, ~mpim:read~, ~search:read~, ~reactions:read~. Do not add
   ~chat:write~.
2. Under *Socket Mode*, turn Socket Mode on.
3. Under *Basic Information*, create an app-level token with the
   ~connections:write~ scope. It starts with ~xapp-~.
4. Under *Event Subscriptions*, turn events on and subscribe to these
   events *on behalf of users*: ~message.channels~, ~message.groups~,
   ~message.im~, ~message.mpim~, ~reaction_added~.
5. Install the app and copy the user OAuth token. It starts with ~xoxp-~.
6. Put both tokens in the token file (see [[*Config][Config]]) and run
   ~chmod 600~ on it.

Direct posting (see [[*Posting][Posting]]) needs a user token with ~chat:write~.
Keep it out of the read-only app: put it alone in the file named by
~post.writeTokenFile~, ~chmod 600~ it, and run ~slackwatch pin~.

* Events

~serve~ learns the token owner's user id and the workspace URL from
~auth.test~ at startup. ~add~ does the same when it catches up. The
workspace URL is stored for permalinks.
Each new message is handled by the first rule that matches.

1. A reply in a watched thread that is not closed, newer than the watch's
   ~since_ts~, is stored. A reply by someone else notifies the owner
   (~reply~, or ~unowned~ to ~fallbackTarget~ when there is no owner).
   The token owner's own reply is stored without a notification unless
   ~notifySelf~ is set. Either kind updates ~last_activity~.
2. A top-level message by someone else in an IM or MPIM with an active
   ~dm~ watch counts as a reply to the latest such watch. It is not
   recorded as inbound.
3. A reply in a closed watch's thread within ~reopenWindow~ of closing
   reopens the watch and notifies ~reopened~.
4. A post by the token owner that matches ~footerPattern~ and has no watch
   is registered like ~add~, as ~unowned~ with source ~footer~. If it is
   still ~unowned~ after ~unownedGrace~, ~fallbackTarget~ gets an
   ~unowned~ notification. An ~add --owner~ within that time, such as from
   a hook, opens the watch and suppresses the notification. A server stop
   within that time drops the notification.
5. A DM to the token owner, or a message that mentions them, is stored in
   ~inbound~. Without an ~inbound~ block, nothing is notified. With the
   block, a newly stored message notifies ~inbound.target~ as ~inbound~
   when ~kinds~ includes it and the author is not in ~ignoreAuthors~. A
   message already delivered as a watch reply or a subscription event is
   not notified again. Each message is notified at most once, including
   after a restart or catch-up. The token owner's own messages are not
   inbound.
6. Anything else is dropped.

A channel in ~ignoreChannels~ is dropped before these rules. The message
is not stored, not notified, and its text is not logged. slackwatch logs
a drop count only.

Separately from these rules, a top-level message or thread reply in a
subscribed channel is stored and notifies each subscriber as ~channel~.
The token owner's own messages are skipped unless the subscription has
~--include-self~. A subscriber whose target already got the message as a
watch notification under rules 1 to 3 is not notified again. A
mention in a subscribed channel is still stored in ~inbound~, and is
not also notified as ~inbound~. An ~ignoreChannels~ channel is not
caught by a subscription either.

Messages are deduplicated on channel and ts. Edits update the stored
text, deletes mark a reply deleted, and reactions on watched posts and
replies are stored for ~show~. None of these notify.

* Catch-up and expiry

~serve~ sweeps after every Socket Mode connect (so on start and on each
reconnect) and every ~sweepInterval~. ~add~ also catches up its one
watch when a token is available. A sweep:

1. Catches up every watch that is not closed, or was closed within
   ~reopenWindow~: ~conversations.replies~ for a thread watch and
   ~conversations.history~ for a ~dm~ watch, after the watch's cursor
   (initially its ~since_ts~).
2. Runs ~search.messages~ for the token owner's own posts (~from:me~),
   messages to them (~to:me~), and mentions of them, after the search
   cursor (initially one day back). This finds footer posts and inbound
   messages missed while ~serve~ was down.
3. Catches up every subscription whose ~until~ has not passed, after its
   cursor (initially the time of ~sub~): ~conversations.history~ for
   top-level messages, plus ~conversations.replies~ for threads whose
   ~latest_reply~ is after the cursor. Thread parents are looked for up
   to 7 days before the cursor.
4. Closes watches past their deadline, without notifying.

Fetched messages go through the same rules as live events and are
deduplicated on channel and ts, so overlap with events is harmless.
Reactions on fetched watched posts and replies are stored. A cursor
advances only after its batch is stored. A ~429~ waits out ~Retry-After~
and retries. One failing watch or subscription is logged and does not stop the others.

A watch's deadline is ~until~ when set. Otherwise it is ~quietExpiry~
after the later of its creation and its latest reply by someone other
than the token owner. The token owner's own replies update
~last_activity~ but do not keep a watch open.

* Watch commands

The CLI writes the database directly, so the server does not have to be
running.

| Command | Does |
|---------+------|
| ~add <post> [--owner T] [--purpose S] [--ref R ...] [--until DATE] [--source SRC]~ | Watch a post. ~SRC~ is ~outbox~, ~hook~, or ~manual~ (default). |
| ~claim <post> --owner T [--purpose S] [--ref R ...]~ | Take an ~unowned~ or ~orphaned~ watch and open it. |
| ~done <post> [--reason S]~ | Close a watch. |
| ~snooze <post> --until DATE~ | Keep a watch open until ~DATE~. |
| ~ack <post>~ | Mark every stored reply acknowledged. |
| ~ls [--owner T] [--state S] [--unacked] [--json]~ | One row per watch. |
| ~show <post> [--json]~ | A watch with its posts, replies, and reactions. |

~<post>~ is a Slack permalink, a channel and ts (~C0123 1700000000.000100~),
or a watch id. ~DATE~ is ~YYYY-MM-DD~ (through the end of that local day),
RFC 3339, or a duration such as ~72h~.

- A thread reply is watched on its parent thread, and several posts in one
  thread share one watch. A reply permalink carries ~?thread_ts=~. A
  channel and ts pair is taken as a top-level post unless that ts is
  already registered as a reply.
- A post in an IM channel (id starting with ~D~) makes a ~dm~ watch.
- ~since_ts~ is the earliest registered post. Older thread traffic is
  never notified.
- ~add~ again for a watched post updates only the flags given. A new watch
  is ~open~ with ~--owner~ and ~unowned~ without it. ~--owner~ on an
  ~unowned~ watch claims it, as ~claim~ does, and opens it.
- After registering, ~add~ catches up on the watch when a token is
  available. Without a token it skips catch-up quietly.
- ~ls~ counts unacknowledged replies by others and flags a watch that has an
  undelivered notification.
- ~show~ prints a ~link:~ line with the watched post's permalink and a
  permalink on each reply line. ~show --json~ has ~permalink~ on the watch
  and on each reply, and ~ls --json~ has it on each watch. Plain ~ls~ shows
  no links. A watch added from a permalink keeps that link. Otherwise the
  link is built from the stored workspace URL, such as
  ~https://acme.slack.com/archives/C0123/p1700000005000200?thread_ts=1700000000.000100&cid=C0123~
  for a thread reply. Until ~serve~ or a catch-up has run ~auth.test~, the
  workspace URL is unknown and links are left out.

* Channel subscriptions

| Command | Does |
|---------+------|
| ~sub <channel> --owner T [--purpose S] [--until DATE] [--include-self] [--owner-unchecked]~ | Notify ~T~ of every new message in a channel. |
| ~unsub <channel> [--owner T]~ | Remove the channel's subscriptions, or only ~T~'s. |
| ~subs [--json]~ | List subscriptions. |

~<channel>~ is a channel id or ~#name~. A name is resolved with
~conversations.list~, which needs ~tokenFile~, and the id is stored in
the ~channels~ table. A cached id is trusted for ~channelCacheTtl~
(default 168h) and makes no API call. The service refreshes that row
when it sees the channel on an event, a watch, a search match, or
~conversations.info~. A Slack rate limit waits ~Retry-After~, prints
~rate limited, waiting Ns…~ on stderr, and keeps the pagination cursor.
The total wait is at most ~channelLookupWait~ (default 60s). If the name
still cannot be resolved, the error is ~could not resolve #name
(<reason>); pass the channel id (C…) to --to~, before any outbox record
is stored. A later post or read that gets ~channel_not_found~ for a
cached id drops that entry and resolves the name once.
There is one subscription per channel and owner; ~sub~ again replaces its
purpose, ~until~, and ~--include-self~. Subscriptions do not expire on
quiet. They end with ~unsub~ or ~--until~. A subscriber that fails the
liveness check or the notify command gets the same fallback and
undelivered handling as a watch owner.

~--owner~ on ~post~ and ~sub~ must be a key in ~targets~ or a name from
~agentbus list~. An unknown owner is refused with that list.
~--owner-unchecked~ accepts it anyway. If ~agentbus~ cannot be queried,
the command warns and accepts the owner. ~sub~ checks the owner before
resolving the channel.

* Server status and inbound messages

| Command | Does |
|---------+------|
| ~serve~ | Run the server: Socket Mode, catch-up, and the sweep. |
| ~status [--json]~ | Show the server heartbeat. |
| ~inbound [--since WHEN] [--json]~ | List recorded DMs and mentions, oldest first. |

~serve~ writes a heartbeat to the ~status~ row when it starts, on every
connection change, event, catch-up, and sweep, and at least once a
minute. The row holds the pid, the start time, the connection state
(~connected~, ~reconnecting~, or ~down~), the last event time, the time
and result of the last catch-up (after a connect) and the last periodic
sweep, and the count of undelivered notifications. When ~post.mode~ is
set it also holds the result of the last outbox poll. ~serve~ marks
itself ~down~ when it exits.

A failing outbox poll, such as one where ~decide~ is not found, shows
as ~outbox poll: failing since <time>: <error>~. ~status --json~ has it
as ~outboxPoll~ with ~ok~, ~lastOk~, ~lastError~, and ~failingSince~.
The next successful poll clears it.

~status~ reports ~stale~ when the heartbeat is older than twice its
interval, which means ~serve~ died or hung without marking itself
down. It exits 1 when the server is ~down~ or ~stale~, any
notification is undelivered, or the latest outbox poll failed, and 0
otherwise (~reconnecting~ included), so a script can check it:

#+begin_src sh
slackwatch status >/dev/null || notify-send slackwatch "$(slackwatch status)"
#+end_src

A notification is undelivered when its last attempt failed, for a watch
or a channel subscription alike. ~ls~ flags only the watches; ~status~
counts both. Inspect the attempts in the ~deliveries~ table.

~WHEN~ is a duration back from now (~24h~), a ~YYYY-MM-DD~
date (from the start of that local day), or RFC 3339. Without it,
~inbound~ lists everything. The ~--json~ form is an array of objects
with ~channel~, ~ts~, ~author~, ~text~, and ~kind~ (~dm~ or ~mention~).

** Running as a systemd user service

[[file:contrib/slackwatch.service][contrib/slackwatch.service]] is an example user unit. It restarts on
failure and logs to the journal. It holds no token: it points at the
config, and the config points at the token file.

#+begin_src sh
cp contrib/slackwatch.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now slackwatch.service
journalctl --user -u slackwatch.service -f
#+end_src

Edit the binary and config paths in ~ExecStart~ to match your install.

A user service does not read your shell profile, so its ~PATH~ is
short. When ~post.mode~ is set, ~serve~ runs ~decide~, which must be on
that ~PATH~. The example unit sets
~Environment=PATH=%h/go/bin:%h/.local/bin:/usr/local/bin:/usr/bin:/bin~.
If you keep your own unit, add a drop-in instead:

#+begin_src sh
mkdir -p ~/.config/systemd/user/slackwatch.service.d
cat > ~/.config/systemd/user/slackwatch.service.d/path.conf <<'EOF'
[Service]
Environment=PATH=%h/go/bin:%h/.local/bin:/usr/local/bin:/usr/bin:/bin
EOF
systemctl --user daemon-reload
systemctl --user restart slackwatch.service
#+end_src

Or set ~decideCommand~ in the config to decide's absolute path, such as
~"/home/me/go/bin/decide"~. When ~decide~ cannot be found, ~serve~ keeps
watching, and ~slackwatch status~ shows the failing outbox poll and
exits 1.

* Agent skill

~slackwatch skill~ prints a ~SKILL.md~ that teaches an agent the posting
and watching workflow: how to send a Slack post, what to do when a
~[slackwatch <event>]~ notification arrives, and how to follow a thread
it did not post. It needs no token and no running server, and reads only
the optional config.

When ~outbox~ is set, the skill tells agents not to post themselves and
to send each draft to the outbox with ~agentbus send <outbox>~. When it
is unset, the skill says to post only after the user approves the exact
text and destination, then run
~slackwatch add <permalink> --owner <you> --source outbox~.

When ~post.mode~ is set, the skill tells agents to submit drafts with
~slackwatch post~ instead, whether or not ~outbox~ is set, and not to
reply in the decide thread of an outbox draft. In handoff mode it also
tells the posting agent what to do with ~approved post ready: <id>~.

#+begin_src sh
slackwatch skill > ~/.claude/skills/slackwatch/SKILL.md
#+end_src

* Posting

~slackwatch post~ takes a draft from any agent and posts it only after
the user approves the exact text and destination in ~decide~. Posting is
off until ~post.mode~ is set; without it, ~post~ refuses.

| Command | Does |
|---------+------|
| ~post --to DEST --text-file F --owner T --purpose S [--ref R ...] [--supersedes ID] [--owner-unchecked] [--json]~ | Store the draft and file its decide item. Prints the outbox id. ~--supersedes~ cancels that older draft once this one is stored. |
| ~outbox ls [--state S] [--json]~ | List outbox records. |
| ~outbox show <id> [--json]~ | Show a record, ending with its exact text. |
| ~outbox posted [--manual] <id> <permalink>~ | Report a handoff post, or with ~--manual~ a post made by hand. |
| ~outbox recheck <id>~ | Read a mismatch post back again with the current config. A pass moves it to ~posted~ and replies on the decide item. A failure prints the remaining problems and exits non-zero. |
| ~outbox poke <decide-id>~ | Handle the answer to a decide item now. |
| ~outbox cancel <id> [--reason S]~ | Withdraw a draft that is not posted. |
| ~outbox retry <id>~ | Post a failed direct record once, or return a failed handoff record to ~awaiting-handoff~. |
| ~pin~ | Check the write token with ~auth.test~ and pin it in the config. |

~DEST~ is a channel id, a ~#name~, or a message permalink, which posts
into that thread.

1. *Submit.* ~post~ stores the destination, the exact text, its SHA-256,
   the owner, the purpose, and the refs as a ~pending~ record.
2. *Ask.* It runs ~decide ask --owner <post.decideOwner> --kind relay
   --option post:"Post as written" --option drop:"Don't post" --rec post
   --free-text~. The question shows the destination (and the thread
   permalink), the text in a quoted block, the owner, the purpose, and
   the first 8 hex digits of the hash. ~decide~ runs without
   ~HERDR_PANE_ID~ and ~DECIDE_AS_HANDLE~, so the item has no agent
   ~notifyPane~ even when an agent runs ~slackwatch post~ from its pane.
3. *Answer.* ~serve~ polls ~decide show --json~ for every pending record
   every 30 seconds. ~decide~'s ~notifyTemplate~ can run
   ~slackwatch outbox poke <decide-id>~ for an immediate pickup when the
   owner is ~post.decideOwner~, so a reply lands with slackwatch and not
   in an agent's pane (see below); polling stays the source of truth.
4. *Accept.* slackwatch reads the user's pick from the item's thread
   messages, not from its state or ~answer~: a later message reopens the
   item, and a later free-text message replaces ~answer~. A human
   message is one with author ~human~ and no ~by~; a message sent with
   ~by~ is an agent's, whatever its ~via~, and does not count. slackwatch
   acts on the latest human message. It posts only when that message
   picks ~post~ (~optionKey~ exactly ~post~) with ~via~ ~ui~ (a message
   without ~via~ does not count), the stored text still matches its
   hash, and the record is still ~pending~. Agent replies after the pick
   do not cancel it.
   - A free-text message is the edit path: the record becomes
     ~needs-redraft~ and the owner gets the text as an ~outbox-redraft~
     notification. The owner submits a new ~post~ with ~--supersedes <id>~.
   - ~drop~ makes the record ~dropped~ and tells the owner.
   - A human message after a ~post~ pick, such as ~drop~ or free text,
     takes precedence and goes through those paths.
   - Any other ~post~ pick, such as one given with the decide CLI,
     makes the record ~rejected~ and alerts the owner and
     ~fallbackTarget~.
   - A decide item closed or withdrawn before an accepted pick makes
     the record ~cancelled~.
   - Every outcome closes the decide item with ~decide done~.
5. *Post.*
   - *handoff:* the record becomes ~awaiting-handoff~ and ~post.agent~
     gets ~approved post ready: <id>~. That agent reads the record with
     ~outbox show~, checks its own Slack identity, posts the text
     verbatim, and runs ~outbox posted <id> <permalink>~. slackwatch
     reads the message back with the read token and checks that the
     author is ~post.expectUser~ and the text matches.
   - *direct:* after the identity check below, slackwatch calls
     ~chat.postMessage~ with the text, a blank line, and ~post.footer~.
6. *Watch.* The post is watched with ~--source outbox~ for the owner,
   with the purpose and refs, and the decide item is closed with the
   permalink.

The handoff comparison strips the footer. ~footerPattern~ finds where
the footer starts, and everything from that match through the end of
the message is dropped, plus one Slack marker (asterisk, underscore, or
strikeout) immediately before the match and the whitespace before that
marker. An inline footer " *Sent using* <@U1>" is dropped by
~Sent using\*? <@U1~. Slack's ~&amp;~, ~&lt;~, and ~&gt;~ escaping is
undone, and trailing whitespace on each line and at the end is trimmed.
In handoff mode a connector link ~<url|label>~ is read back as ~url~
when the label is the URL, the URL without its scheme, or a truncated
prefix of either ending in …, and runs of blank lines on either side
count as one line break. Any other difference is a mismatch, including
a bold or italic change and an unrelated link label. On a mismatch the watch is still registered
for the owner and flagged, the record becomes ~mismatch~, and the owner
and ~fallbackTarget~ get both texts. slackwatch never edits or deletes
the post.

While a record is ~awaiting-handoff~, an own post in its destination
whose text matches is linked to it: it is watched for the owner instead
of becoming an unowned footer watch. ~outbox posted~ then confirms the
link; naming a different message makes the record a ~mismatch~.

When an approved draft is posted by hand, for example because ~serve~
could not reach decide, ~outbox posted --manual <id> <permalink>~
records it. It accepts a ~pending~ or ~awaiting-handoff~ record. For a
~pending~ record it first reads the decide item and applies the same
acceptance rule as step 4; when the rule refuses it, it fails with
~no ui approval found for <id>: <reason>~ and changes nothing. A
manual post never bypasses approval. The read-back, author, and text
checks are the handoff ones: a match makes the record ~posted~, watches
it for the owner with ~--source outbox~, and closes the decide item
with the permalink; a difference makes it ~mismatch~ and alerts. The
record notes ~manual: true~.

The decide items slackwatch files belong to slackwatch, and agents do
not reply in their threads (the skill says so). To send an answer on
those items to slackwatch at once, give ~decide~'s ~notifyTemplate~
(in ~$XDG_CONFIG_HOME/decide/config.json~ on the machine that holds the
ledger) a branch for ~post.decideOwner~ that runs ~outbox poke~. It
must run where slackwatch's state lives. Every other owner keeps the
usual pane prompt:

#+begin_src sh
if [ "$DECIDE_OWNER" = slackwatch ]; then
  slackwatch outbox poke "$DECIDE_ID"
else
  herdr ${DECIDE_MACHINE:+--machine "$DECIDE_MACHINE"} agent prompt "$DECIDE_PANE" "$DECIDE_THREAD_HEADER $DECIDE_ANSWER"
fi
#+end_src

As one JSON string:

#+begin_src json
{"notifyTemplate": "if [ \"$DECIDE_OWNER\" = slackwatch ]; then slackwatch outbox poke \"$DECIDE_ID\"; else herdr ${DECIDE_MACHINE:+--machine \"$DECIDE_MACHINE\"} agent prompt \"$DECIDE_PANE\" \"$DECIDE_THREAD_HEADER $DECIDE_ANSWER\"; fi"}
#+end_src

Direct mode checks its identity before it posts:

- ~slackwatch pin~ runs ~auth.test~ with the write token. When the user is
  ~post.expectUser~, it writes ~post.pinSalt~ (generated when unset) and
  ~post.tokenPin~, the hex SHA-256 of the salt followed by the token,
  into the config, and re-enables posting. It rewrites the config with
  sorted keys.
- Before every post, the token's pin must match ~post.tokenPin~. This is
  local, with no API call.
- When ~serve~ starts and whenever the token changes, ~auth.test~ must
  report ~post.expectUser~.
- A failed check disables posting until ~slackwatch pin~ runs again and
  alerts ~fallbackTarget~. Approved records wait in ~approved~ and post
  on the next poll (or ~outbox poke~) after the pin.
- When ~post.footer~ is set, ~footerPattern~ must find the start of that
  footer and remove it, so readers can tell an agent post from a typed
  one. Normalizing ~text~ plus the footer must yield ~text~. Otherwise
  ~post~ refuses and ~serve~ does not start posting.

A ~failed~ record can be resumed with ~outbox retry <id>~. It re-runs
the acceptance checks: the latest human message is a ~post~ pick with
~via ui~, the stored text still matches its hash, and the destination
in the decide question is unchanged. A failed check leaves the record
~failed~ and prints which check failed. Direct mode also checks the
identity pin, then searches the destination for a message from
~post.expectUser~ with this text in the last 15 minutes. A match is
registered as ~posted~ and nothing new is sent. Otherwise it posts
once, reads the message back, and moves the record to ~posted~ or
~mismatch~. Handoff mode does not post: the record returns to
~awaiting-handoff~ and ~post.agent~ gets ~approved post ready: <id>~
again.

When ~chat.postMessage~ returns ~not_in_channel~, the ~outbox-failed~
notice (the decide reply and the notification) says the posting
account is not a member of the channel and names ~outbox retry~.
~channel_not_found~, ~is_archived~, and ~restricted_action~ name a
short fix and the same command. Any other error is reported as Slack
returned it. The stored reason stays the Slack error.

| State | Meaning |
|-------+---------|
| ~pending~ | Waiting for the decide answer. |
| ~approved~ | Accepted in direct mode, not posted yet (for example while posting is disabled). |
| ~posting~ | A direct post is in flight. Never retried, so never posted twice. |
| ~awaiting-handoff~ | Accepted in handoff mode, waiting for ~outbox posted~. |
| ~posted~ | Posted and watched. |
| ~needs-redraft~ | Answered with free text; the owner has the notes. |
| ~dropped~ | Answered ~drop~. |
| ~rejected~ | Not posted: the user's latest pick was not a ~post~ from the decide UI, or the text changed. |
| ~mismatch~ | The handoff post differs from the approved text, author, or destination. |
| ~cancelled~ | Withdrawn with ~outbox cancel~, or its decide item was closed without an answer. |
| ~failed~ | ~decide ask~ or ~chat.postMessage~ failed. ~outbox retry~ resumes it. |

~status~ shows the posting mode and counts the ~pending~,
~awaiting-handoff~, and ~needs-redraft~ records. It exits 1 while direct
posting is disabled.

* Config

The config is ~${XDG_CONFIG_HOME:-~/.config}/slackwatch/config.json~.
~--config <path>~ or ~SLACKWATCH_CONFIG~ overrides that path. A missing
file means all defaults. An unknown key is an error.

| Key | Default | Meaning |
|-----+---------+---------|
| ~notifyTemplate~ | none | Shell template run for a reply. |
| ~livenessTemplate~ | none | Optional template that checks an owner is alive. |
| ~notifyTimeout~ | ~"30s"~ | Time limit for each notify, check, or liveness command. |
| ~notifyCheckCommand~ | none | Optional command run after a failed notify attempt. Exit 0 counts as delivered. |
| ~notifyRetryAfter~ | ~["2s", "5s"]~ | Wait before each retry. An empty list disables retries. |
| ~targets~ | none | Map of name to address. |
| ~fallbackTarget~ | none | Target used when delivery fails. |
| ~footerPattern~ | none | Optional regexp that finds where a footer starts. The match through the end of the message is dropped, plus one marker (asterisk, underscore, or strikeout) and the whitespace before it. An inline footer " *Sent using* <@U1>" matches ~Sent using\*? <@U1~. |
| ~notifySelf~ | ~false~ | Also notify for the token owner's own replies. |
| ~sweepInterval~ | ~"6h"~ | Time between slow sweeps. |
| ~quietExpiry~ | ~"336h"~ | A watch with no reply from others for this long closes. |
| ~reopenWindow~ | ~"720h"~ | A reply this soon after a watch closes reopens it. |
| ~unownedGrace~ | ~"10s"~ | Wait this long before the ~unowned~ notification for a footer post. |
| ~excerptLimit~ | ~300~ | Maximum characters of reply text in a notification. |
| ~dbPath~ | ~${XDG_STATE_HOME:-~/.local/state}/slackwatch/slackwatch.db~ | SQLite database. |
| ~tokenFile~ | none | File that holds the Slack tokens. |
| ~channelCacheTtl~ | ~"168h"~ | How long a cached channel id is trusted. ~"0s"~ trusts nothing. |
| ~channelLookupWait~ | ~"60s"~ | Longest a name lookup waits out Slack rate limits. ~"0s"~ fails on the first rate limit. |
| ~outbox~ | none | Where agents send Slack drafts, such as an agentbus name. ~slackwatch skill~ names it when ~post.mode~ is unset. |
| ~decideCommand~ | ~"decide"~ from ~PATH~ | Command for every ~decide~ call: an absolute path, or an argv list such as ~["ssh", "box", "decide"]~. |
| ~post.mode~ | none | ~handoff~ or ~direct~. Unset means posting is off. |
| ~post.agent~ | none | Handoff target for approved posts, resolved through ~targets~. |
| ~post.expectUser~ | none | Slack user id every post must come from. |
| ~post.decideOwner~ | ~"slackwatch"~ | Owner of the decide approval items. |
| ~post.writeTokenFile~ | none | Direct mode: file holding only the write token. |
| ~post.footer~ | none | Direct mode: text appended to every post. When set, startup checks that normalizing "text" plus the footer yields "text". |
| ~post.pinSalt~ | none | Direct mode: salt of the token pin. ~slackwatch pin~ sets it. |
| ~post.tokenPin~ | none | Direct mode: pin of the write token. ~slackwatch pin~ sets it. |
| ~inbound.target~ | none | Required when ~inbound~ is set. Agent notified of a new DM or mention. Looked up in ~targets~. |
| ~inbound.kinds~ | ~dm~ and ~mention~ | Which stored inbound messages to notify. |
| ~inbound.ignoreAuthors~ | none | Authors, such as bots, that are stored but not notified. |
| ~inbound.ignoreChannels~ | none | Channels dropped entirely: not stored, not notified, and not logged beyond a count. |

Durations use Go syntax, such as ~"90m"~ or ~"6h"~.

Tokens are not in the config. ~tokenFile~ is a JSON object with the
app-level Socket Mode token and the read-only user token:

#+begin_src json
{"appToken": "xapp-...", "userToken": "xoxp-..."}
#+end_src

~serve~ refuses to start when ~tokenFile~ is readable by group or others.
Run ~chmod 600~ on it. Token values are never logged.

* Notifications

~notifyTemplate~ runs with ~sh -c~, like ~decide~'s. Every field is an
environment variable and is never written into the command string.

| Variable | Value |
|----------+-------|
| ~SLACKWATCH_EVENT~ | ~reply~, ~unowned~, ~orphaned~, ~channel~, ~reopened~, ~inbound~, or an outbox event below |
| ~SLACKWATCH_OWNER~ | The owner name as stored. |
| ~SLACKWATCH_TARGET~ | The resolved address. |
| ~SLACKWATCH_POST_LINK~ | Permalink of the watched post. |
| ~SLACKWATCH_REPLY_LINK~ | Permalink of the reply. |
| ~SLACKWATCH_CHANNEL~ | Channel id. |
| ~SLACKWATCH_PURPOSE~ | The watch purpose. |
| ~SLACKWATCH_REFS~ | Refs, separated by spaces. |
| ~SLACKWATCH_AUTHOR~ | Reply author. |
| ~SLACKWATCH_TEXT~ | Reply text, cut to ~excerptLimit~ characters. |
| ~SLACKWATCH_WATCH_ID~ | Watch id, empty for a channel subscription. |
| ~SLACKWATCH_OUTBOX_ID~ | Outbox record id for an outbox event, else empty. |
| ~SLACKWATCH_NOTIFY_ID~ | Idempotency key for this attempt chain, ~slackwatch:<watch>:<event>:<ulid>~. Retries of one note reuse it. |
| ~SLACKWATCH_MESSAGE~ | A ready-made paragraph that quotes the excerpt as Slack data, not instructions, and ends with a ~slackwatch show <id>~ hint. |
| ~SLACKWATCH_TS~ | Message ts for an ~inbound~ event. |
| ~SLACKWATCH_THREAD_TS~ | Thread ts when an inbound message is in a thread. |
| ~SLACKWATCH_PERMALINK~ | Permalink of an inbound message. |
| ~SLACKWATCH_KIND~ | ~dm~ or ~mention~ for an inbound event. |

- An owner is looked up in ~targets~. An owner that is not there is used
  as a raw address. ~fallbackTarget~ is looked up the same way.
- When ~livenessTemplate~ is set, it runs first with the same environment.
  A non-zero exit means the owner is gone. The watch is orphaned without
  retrying the notify command.
- ~SLACKWATCH_NOTIFY_ID~ is one key for the attempt chain. Pass it through
  when the receiver can dedupe, for example
  ~agentbus send --client-id "$SLACKWATCH_NOTIFY_ID"~. A command that
  ignores the variable is still retried. Those retries are not deduped.
- A non-zero exit or a timeout retries the same command with the same
  key. ~notifyRetryAfter~ is the wait before each retry. The default is
  2s then 5s.
- When ~notifyCheckCommand~ is set, it runs after a failed attempt, with
  the same environment. Exit 0 means the note was stored, delivered,
  held, or queued. For example ~agentbus status "$SLACKWATCH_NOTIFY_ID"~.
- The watch becomes ~orphaned~ when every retry and the optional check
  fail, or when the liveness check says the owner is gone. The template
  then runs again with ~SLACKWATCH_EVENT=orphaned~ for ~fallbackTarget~
  and a new key. A notification with no owner goes straight to
  ~fallbackTarget~. An ~inbound~ note uses the same template, retries,
  ~SLACKWATCH_NOTIFY_ID~, and ~notifyCheckCommand~. If its target never
  accepts it, the note goes to ~fallbackTarget~ as ~orphaned~ and the
  attempts are recorded. No watch changes state.
- If that also fails, or there is no ~fallbackTarget~, slackwatch logs an
  error and the failed row stays undelivered, so ~ls~ flags the watch.
- Every attempt is a row in ~deliveries~, with its exit code, its
  ~SLACKWATCH_NOTIFY_ID~, and the first 4 KiB of stdout and stderr.
- One notification per event, reply, and target. An owner and a channel
  subscriber that resolve to the same target are notified once.

Outbox events carry their own ~SLACKWATCH_MESSAGE~:

| Event | Goes to | When |
|-------+---------+------|
| ~outbox-ready~ | ~post.agent~ | A handoff post was approved: ~approved post ready: <id>~. |
| ~outbox-redraft~ | owner | The user answered with notes; ~SLACKWATCH_TEXT~ holds them. |
| ~outbox-dropped~ | owner | The user answered ~drop~. |
| ~outbox-cancelled~ | owner | The decide item was closed without an answer. |
| ~outbox-rejected~ | owner and fallback | The answer did not pass the acceptance rule. |
| ~outbox-mismatch~ | owner and fallback | A handoff post differs from the approved text. |
| ~outbox-failed~ | owner and fallback | ~chat.postMessage~ failed. A fixable error names the cause and ~outbox retry~. |
| ~posting-disabled~ | fallback | The direct-mode identity check failed. |

Example templates. Pass ~SLACKWATCH_NOTIFY_ID~ through when the
receiver can dedupe. A desktop popup, where every target is the same
machine, ignores the key. Retries still run:

#+begin_src json
{
  "notifyTemplate": "notify-send \"slackwatch $SLACKWATCH_EVENT\" \"$SLACKWATCH_MESSAGE\"",
  "fallbackTarget": "me"
}
#+end_src

A message bus that stores the key. A retry is a no-op when the first
attempt landed, and the check counts a stored or queued message as
delivered:

#+begin_src json
{
  "notifyTemplate": "agentbus send --client-id \"$SLACKWATCH_NOTIFY_ID\" \"$SLACKWATCH_TARGET\" \"$SLACKWATCH_MESSAGE\"",
  "notifyCheckCommand": "agentbus status \"$SLACKWATCH_NOTIFY_ID\"",
  "fallbackTarget": "me"
}
#+end_src

A file per target, so each owner reads its own inbox:

#+begin_src json
{
  "notifyTemplate": "printf '%s\\n\\n' \"$SLACKWATCH_MESSAGE\" >> \"$HOME/slackwatch-$SLACKWATCH_TARGET.txt\"",
  "targets": {"agent-1": "agent-1", "me": "me"},
  "fallbackTarget": "me"
}
#+end_src

** Delivery guarantees

- A reply to an open watch is notified to its owner. A failed attempt
  is retried, then sent to ~fallbackTarget~ if it still fails. Replies
  that arrive while ~serve~ is down are found by the catch-up after it
  reconnects.
- A notification is never dropped silently. If neither the owner nor
  the fallback gets it, an error is logged, the row stays undelivered,
  ~ls~ flags the watch, and ~status~ exits 1 with the count.
- A delivered notification is not sent again, but a crash between
  running the command and recording it can repeat one. Write templates
  that tolerate a repeat.
- Acks, reactions, edits, and deletes never notify. The token owner's
  own replies notify only with ~notifySelf~.

* Database

SQLite in WAL mode, so the server and the CLI can open the same file at
once. Each open applies any pending migrations. ~PRAGMA user_version~
records how many have run.

| Table | Holds |
|-------+-------|
| ~watches~ | One watched thread or DM. Unique per ~(channel, thread_ts)~. |
| ~watch_posts~ | The registered posts under a watch. |
| ~replies~ | Replies seen in watched threads, and messages in subscribed channels (no watch). Unique per ~(channel, ts)~. |
| ~reactions~ | Reactions on watched posts. |
| ~inbound~ | DMs and mentions addressed to the user. ~notified~ is 1 once an ~inbound~ notification was committed. |
| ~subs~ | Channel subscriptions. |
| ~cursors~ | Last seen ts per scope. |
| ~deliveries~ | Notify attempts, delivered or not. |
| ~status~ | One heartbeat row for the server. |
| ~outbox~ | Drafts submitted with ~slackwatch post~ and their state. |
| ~posting~ | Why direct posting is disabled, empty when it is not. |
